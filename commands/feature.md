# 通用功能开发工作流

你要带用户走完一条**带门禁**的开发流水线。核心原则：

- **先理解再动手** —— 不要在没有读代码、没有澄清需求的情况下写实现。
- **门禁不可跳过** —— 标了「等用户确认」的阶段必须真的停下来等，不能自问自答。
- **产物落盘** —— 每个阶段的产物写进仓库文件，不只在对话里。
- **用 TodoWrite 跟踪** —— 进入本工作流时立刻建 todo 列表，逐阶段更新。

初始需求：$ARGUMENTS

---

## 开始前：读项目约定

**第一件事**：检查项目根是否存在 `.claude/agentforge-conventions.md`。

- **存在** → 读取它。后续所有路径（PRD 目录、Spec 目录、基础分支）与验证命令**以它为准**。
- **不存在** → 使用各技能的通用默认值，并在**第一次汇报时明确说明**
  「未找到项目约定文件，正在使用默认路径」，建议用户参照 AgentForge 的 `docs/conventions.md` 模板创建。

约定文件决定了这条流水线怎么落到你的项目上。**不要跳过这一步就去猜 PRD 该放哪。**

---

## 阶段总览

| # | 阶段 | 使用 | 产物 | 门禁 |
|---|---|---|---|---|
| 0 | 研究 | `research` 技能 | 调研笔记 | — |
| 1 | 需求澄清 | `grilling` 技能 | 澄清共识 | **等用户确认** |
| 2 | PRD | `pm` 技能 | PRD 文档 | **等用户审批** |
| 3 | 原型（可选） | `prototype` 技能 | HTML 原型 + `prototype.md` | **等用户审批** |
| 4 | 架构设计 | `arch-spec` → `arch-backend`/`arch-frontend` | Spec + ADR | **等用户审批** |
| 5 | 实施 | `implement` + `tdd` 技能，`coder` 子 agent | 代码 + 测试 | 测试全绿 |
| 6 | 质量门 | `cleaner` + `reinforcer` 子 agent | 复杂度/突变报告 | 无高危项 |
| 7 | 代码评审 | `code-review` 技能 | 评审意见 | 无阻塞问题 |
| 8 | 提交 | `git-commit` 技能 | 提交 | **等用户确认** |

**按需裁剪**：小改动（修 bug、单文件调整）可从阶段 5 直接进入，但**阶段 6、7 不可跳过**。
用户明确要求只做某一阶段时（如「只评审」「只做架构」），只跑那一段。

**关于阶段 2/3/4 的技能**：`pm`、`prototype`、`arch-spec`、`arch-backend`、`arch-frontend`
编码的是**具体项目的文档约定**（PRD 模板、Spec 结构、原型规格），因此**不在 AgentForge 插件里**，
由项目自行提供（可参考 `presets/kuavo-datahub/`）。

若这些技能未安装：

- 用户只是要走流程 → 用通用方法完成该阶段，产物放进约定文件声明的目录；
- 用户需要项目的专有模板 → **如实告知该技能未安装**，不要假装按模板产出了。

## 阶段 0：研究

**何时需要**：涉及不熟悉的第三方 API、库版本、协议行为，或需要外部事实支撑决策时。

**动作**：
1. 调用 `research` 技能，针对具体问题查高可信度一手来源（官方文档、源码、规范）。
2. 把发现写成 Markdown 落盘，**不要只在对话里回答**。
3. 关键结论标注来源链接和版本号。

**跳过条件**：需求完全在已知代码库范围内，无需外部事实。

---

## 阶段 1：需求澄清

**目标**：把模糊需求逼成明确共识。

**动作**：
1. 调用 `grilling` 技能，对用户的计划和假设**连珠炮式追问**。
2. 追问要具体，不要问「你有什么要求」这种空问题。聚焦：
   - 边界条件、异常路径、失败时的行为
   - 与既有功能的交互、向后兼容
   - 明确**不做什么**（scope boundary）
   - 性能、安全、数据迁移等非功能约束
3. 每轮追问后总结已达成的共识。

**门禁**：**必须等用户明确回应后才能进入阶段 2。**
若用户说「你决定就好」，给出你的推荐方案并**取得明确确认**，不要默认通过。

---

## 阶段 2：PRD

**目标**：把共识固化成可审批的文档。

**动作**：
1. 调用 `pm` 技能撰写 PRD。
2. 澄清已达成共识时**一次性落盘** PRD（不要挤牙膏式多轮输出半成品）。
3. PRD 必须包含：背景与目标、用户故事、验收标准、**范围外事项**、优先级（RICE）。

**门禁**：落盘后在对话中呈现核心摘要，明确询问「PRD 是否确认？」，**等用户批准**。

---

## 阶段 3：原型（可选）

**何时需要**：需求涉及前端页面或交互变更。

**动作**：
1. 调用 `prototype` 技能，按 T1/T2/T3 三档产出静态 HTML 原型 + `prototype.md` 字段状态清单。
2. 原型的作用是**让 API 契约和组件树有依据**，不是为了好看。

**门禁**：等用户审批原型后再进入架构设计。

---

## 阶段 4：架构设计

**目标**：产出能让 `coder` 直接实施的 Spec。

**动作**：
1. 调用 `arch-spec` 技能做全栈架构：API 契约、数据模型、认证鉴权、部署架构、前后端分工。
   - 触碰既有架构决策时，读 `docs/adr/` 索引感知约束。
   - **有争议的技术选型必须写 ADR**，不要只写在对话里。
2. 按需分别调用 `arch-backend` / `arch-frontend` 做深化设计。
3. Spec 必须包含**防误改清单**和**验收标准** —— 这是给 `coder` 和 `qa` 的输入契约。

**门禁**：呈现方案与取舍（至少给出「最小改动」和「干净架构」两种取向的对比），
给出**你的推荐及理由**，**等用户选定方案**。

---

## 阶段 5：实施

**目标**：按 Spec 落地代码与测试。

**前置**：阶段 4 的方案已获用户批准。**没有批准不要开始写实现。**

**动作**：
1. 调用 `implement` 技能作为编排入口。
2. 复杂或可并行的任务委托 `coder` 子 agent（它带 `mcp__codegraph__*`，适合先定位再改）。
3. 涉及行为变更时调用 `tdd` 技能，走 red-green-refactor。
4. 严格遵循代码库既有约定；不要引入 Spec 之外的重构。

**出口条件**：测试全绿。**测试没绿不许进入阶段 6。**

验证命令以约定文件的 `verify` 字段为准；未声明时自动探测构建文件
（`package.json` / `pom.xml` / `pyproject.toml` / `build.gradle`），
并**在报告中说明实际用了什么命令**，不要含糊带过。

---

## 阶段 6：质量门

**目标**：确认「代码能跑」之外的质量事实。

**动作**（两个子 agent 都要跑）：
1. `cleaner` 子 agent —— 用 CRAP 指标（复杂度 × 覆盖率）定位难维护的函数。只报告不改码。
2. `reinforcer` 子 agent —— 突变测试，通过「改动被测代码看测试是否失败」验证测试是否真的在验证逻辑，找出存活突变体。只对改动模块跑，不全量。
3. 汇总两份报告，列出高危项并给出修复建议。

**出口条件**：无高危存活突变体，无新增高 CRAP 函数。
**若用户要求快速交付**，可降级为「只报告不修复」，但必须**显式说明降级了**。

---

## 阶段 7：代码评审

**目标**：从固定点审查改动。

**动作**：
1. 调用 `code-review` 技能，沿两个轴审查：
   - **Standards** —— 是否遵循本仓库成文的编码标准
   - **Spec** —— 是否忠实实现了原始 issue/spec 的要求
2. 按严重程度分级呈现，明确指出哪些建议修、哪些可延后。
3. **问用户怎么处理**（现在修 / 稍后修 / 就这样），不要自作主张。

---

## 阶段 8：提交

**动作**：
1. 调用 `git-commit` 技能：分析改动、生成符合项目规范的 commit message、检查禁止提交的文件。
2. 提交前**呈现 commit message 和将提交的文件清单**。

**门禁**：等用户确认后再执行提交。**不要自动 push。**

---

## 收尾

1. 更新 todo 列表，全部标记完成。
2. 汇总：做了什么、关键决策与理由、改了哪些文件、遗留问题、建议的下一步。
3. 如果本次产生了可复用的经验（踩坑、约定、非显然的约束），**建议把它固化成技能或 ADR** —— 用 `codebase-design` 或直接更新仓库文档。
