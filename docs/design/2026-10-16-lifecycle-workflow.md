# AgentForge 全生命周期工作流设计草案

状态：讨论稿，未批准、未实施。日期：2026-10-16。

本文描述目标行为，不宣称当前技能已经实现。当前实现以 `docs/architecture.md` 和技能正文为准。

## 1. 最终目标与本轮范围

将 AgentForge 建设为覆盖需求澄清、方案设计、任务规划、开发实施、质量验收、发布上线和上线验证的工程工作流体系。Agent 在宿主能力和用户授权范围内推进工作；每次阶段交接都有可核对的输入、结果与证据；中断后能恢复，失败时能回退，关键决策可追溯。

最终完成依据是真实项目的端到端交付及失败恢复验证，不以新增多少技能、文档写齐或结构校验通过替代。

本轮只设计总体流程、节点契约和场景推演。不修改现有技能、provider、清单或业务代码，不执行发布操作。后续实施范围在设计讨论后确定。

## 2. 设计前提与待决策事项

暂按“技能和工作协议定义方法，宿主提供执行能力”设计，与当前架构一致。不预设独立调度引擎、数据库、控制台或固定模型；逻辑状态与存储格式分开。

这项前提待用户选择：保持技能形态、引入独立引擎，或先技能后演进。无论选哪种，节点契约均应成立。

其他待讨论项：

- 首个真实验证项目及发布目标，决定具体部署、监控和回滚适配。
- 状态载体：优先复用目标项目现有任务系统或文档；是否提供默认本地记录模板，留待主流程确认。
- 首版端到端支持的宿主范围。当前三端适配不能推导所有新流程已经跨宿主验证。
- 发布后观察窗口及业务成功指标，由具体项目定义，不采用全局固定分钟数或错误率。

这些问题不阻止工作流设计，但不能被 Agent 默默当成已批准的产品决策。

## 3. 总体流程

按交付目标选择入口及终点，不强制所有任务从需求访谈开始。

```text
N0 任务接入与现状核验
  → N1 需求与验收定义
  → N2 方案设计
  → N3 实施规划
  → N4 开发与集成
  → N5 质量与需求验收
  → N6 发布准备
  → N7 部署与变更执行
  → N8 上线验证与观察
  → 完成交付，或按约定保留后续事项
```

这条顺序表示依赖，不代表每个节点都必须另开一次对话或生成一个文件。已有合格产物可以复用；小任务可在一个交付记录中满足多个节点，但不能省略相应的正确性和授权判断。

| 路径 | 入口与推进 | 可结束的位置 |
|---|---|---|
| 新功能全流程 | N0 → N1 → N2 → N3 → N4 → N5 → N6 → N7 → N8 | 上线验收及观察条件满足 |
| 存量功能修改 | N0核验已有需求和设计；有效部分复用，变更部分回N1/N2 | 用户要求的交付终点；全流程仍到N8 |
| 明确的小改动 | N0确定目标、验收及授权，合并精简N1–N3，再N4/N5 | 明确请求的终点，不冒称已上线 |
| 仅调查或设计 | N0后进入对应节点，输出发现或设计 | 调查/设计交付后结束，不自动实施 |
| 已有成果续接 | N0验证真实状态及证据，进入尚未满足的节点 | 按原交付范围完成 |
| Bug或故障 | N0 → 症状诊断 → 确定期望及方案 → N3/N4，随后N5–N8 | 诊断、缓解或完整修复，必须如实区分 |

遇到关键需求歧义回N1；设计不成立回N2；依赖或任务切分错误回N3；实现缺陷回N4。环境或授权缺失进入等待，不用修改产品范围来制造完成。

## 4. 节点契约

共通要求：每个节点知道目标与责任人，引用有效输入，列明动作和副作用，交付可核验结果，并给出下一步。缺失关键证据时只推进不受影响的部分。

### N0：任务接入与现状核验

- 目标：确认用户要交付什么、当前做到哪里、有哪些真实执行能力。
- 输入：原始请求、项目路径和指令、已有需求/设计/任务、代码与环境状态。
- 动作：确认任务类型、范围和交付终点；核验Git及用户已有改动；发现测试、构建、发布入口与权限；识别已有批准和材料冲突。
- 产物：简短任务摘要、基线、能力与授权范围、缺口、建议入口。已有记录就更新，不重复建档。
- 出口：下一步具体动作可确定且在授权范围内；影响业务含义或危险操作的歧义明确挂起。
- 边界：不从“全流程覆盖”推导当前用户要求部署；不因工具存在就推导使用权，不自动初始化或清理项目。
- 失败路径：项目不可读、目标不明或材料冲突时记录具体阻塞；允许继续不依赖该信息的只读分析。

### N1：需求与验收定义

- 目标：形成可验证的预期行为，明确不做什么。
- 输入：用户意图、现有业务约定、N0现状；按需调查事实。
- 动作：确定角色、场景、业务规则、成功条件、约束、范围及非目标；只追问影响行为或验收的缺口。
- 产物：编号需求及验收条件、来源、待决问题、变更记录。复用已有Spec/工单，不要求统一新建SPEC.md。
- 出口：当前实施范围内的关键规则无未决歧义；需求表达和授权可从用户指令或既有有效记录核对。
- 边界：不从代码反推正确需求；不把用户未选的建议写成决定；不强制每条明确需求再批准一次。
- 失败路径：业务依据冲突回用户决策；外部事实不明按需调用research。已明确的独立范围可继续设计。

### N2：方案设计

- 目标：确定满足需求的实现方案，以及可接受的风险与验证方式。
- 输入：有效需求、现有架构和技术约束、相关数据/接口/运维条件。
- 动作：确定模块职责、接口、数据及状态、副作用和错误处理；涉及兼容、权限、性能、迁移时设计对应措施；只比较有实质取舍的替代方案。
- 产物：与需求对应的设计、关键决策及依据、测试策略、迁移与回退要点、未解决风险。
- 出口：关键契约足以实施；影响用户行为、兼容性、成本或危险操作的决定已有依据与所需授权；普通实现细节可留给实施者。
- 边界：architecture-scout只发现值得深入的机会，不能替代方案设计；原型实验不自动变为已交付实现。
- 失败路径：需求本身不可行回N1；技术未知按需调查或隔离实验；不因设计困难直接扩大重构范围。

### N3：实施规划

- 目标：把方案转为可安排、可验收和可恢复的工作。
- 输入：有效需求/设计、项目验证命令、资源约束及授权范围。
- 动作：按业务结果拆任务；明确依赖、文件及环境归属、验收和验证；确定串并行、集成责任、风险审计和发布准备任务。
- 产物：任务及依赖、任务状态、资源所有权、验证计划、所需人工交接。不必为小任务创建任务树。
- 出口：下一任务有可读输入、明确范围、实际可用的验证方式；关键外部依赖有负责人或阻塞说明。
- 边界：独立上下文不等于隔离文件系统；并行不按目录数量机械触发；不把没有验证入口的任务标成可自动验收。
- 失败路径：契约不清回N2；环境缺失记录为待解决任务；无法安全并行就串行。

### N4：开发与集成

- 目标：交付满足任务契约、可检查的实现与测试。
- 输入：有效任务、设计、测试用例、代码基线及允许修改范围。
- 动作：按行为风险建立验证；Bug先见目标失败，再按批准方案修复；新增行为优先测试先行；运行相关检查；主Agent整合接口和真实集成路径。
- 产物：代码/配置/测试变更、实际验证记录、任务与集成结果、未解决项。
- 出口：任务验收有证据、集成可用、改动在范围内；随后进入独立的N5，不把子任务自报完成当整体完成。
- 边界：test-design只设计，测试编写执行由实施承担；审计者只报告；不未经授权提交、推送或发布，不弱化测试/门槛换绿。
- 失败路径：局部错误回原任务，集成冲突由主Agent处理；新根因、契约或范围变化回相应上游节点。既有具体批准可复用，不为每个局部修正重复询问。

### N5：质量与需求验收

- 目标：证明这一候选版本符合需求并达到项目交付门槛。
- 输入：固定的候选代码/配置基线、需求及设计版本、项目检查项和N4验证记录。
- 动作：检查需求覆盖和跨模块路径，执行尚未覆盖的必需检查，按风险选代码评审、复杂度、突变、安全、性能和运行验证；复用仍有效的证据。
- 产物：需求→验证证据对应表、阻断项、非阻断项、缺失证据、可进入发布准备的结论。
- 出口：必需检查完成且通过；例外由有权接受该风险的人明确决定，记录原因、范围和后续责任。未执行不得写通过。
- 边界：无需求依据的Spec轴必须降级；缺少工具不等于无需检查；“有条件接受”不改写底层失败结果；不要求全部建议清零。
- 失败路径：实现缺陷回N4，设计失配回N2，验收规则矛盾回N1；工具缺失先解决或明确交接，不能自动删除必需门槛。

### N6：发布准备

- 目标：形成对明确候选版本、目标环境和执行步骤的可审查发布安排。
- 输入：N5结果、发布目标、环境现状、部署入口、迁移/开关/监控条件及操作权限。
- 动作：确定构建产物、版本、发布顺序、兼容窗口、数据备份/迁移、灰度、观察、回滚或前滚恢复；明确哪些操作不可逆。
- 产物：发布清单、环境与产物标识、执行及恢复步骤、停止条件、授权状态、人工操作交接项。
- 出口：发布安排完整、执行与恢复方式可核对；缺少的权限或授权明确列出。准备文档可以完成，但进入N7前必须确认执行能力、必要权限与具体发布授权均就绪。可复用用户明确给出的部署指令，不固定再问一次。
- 边界：测试环境批准不自动覆盖生产；代码修复批准不覆盖部署；代码可回滚不代表数据已可恢复；只写回滚命令不等于验证可用。
- 失败路径：环境不可达或凭证缺失等待；恢复方案不可行则回设计/发布准备，必要时由用户决定降低风险的发布方式。

### N7：部署与变更执行

- 目标：按已授权安排改变目标环境，并记录真实执行状态。
- 输入：有效发布安排与授权、确定产物、当前环境基线、N5证据。
- 动作：执行前复核环境与产物未漂移；按依赖执行部署、迁移或开关变更；逐步记录开始、结果及可恢复位置。
- 产物：操作与结果、部署/迁移标识、目标环境实际版本、偏差和恢复动作记录。
- 出口：已核实目标环境完成预期变更，进入N8；执行结果未知时不能进入“上线成功”。
- 边界：不超出授权环境/范围；不因为超时直接重试可能产生重复副作用的操作；不把提交或CI开始当部署完成。
- 失败路径：先确定真实环境状态，再按已授权恢复路径处理；回滚/前滚若超出授权或无法判断后果，停止受影响动作并交接；恢复后也要验证。

### N8：上线验证与观察

- 目标：确认用户实际访问的路径与系统运行达到已约定标准。
- 输入：部署记录、目标环境与版本、关键用户路径、指标及观察窗口。
- 动作：核对真实环境版本、冒烟及关键业务路径、错误/延时/业务信号和数据一致性；观察到约定窗口，检查恢复后状态（如发生恢复）。
- 产物：带版本、环境、时间范围的上线验收记录；是否继续放量、恢复、保持观察或完成；剩余事项的责任人。
- 出口：所需路径与指标验证完成，观察窗口满足且无阻断问题。没有监控/时间/能力完成时，交接并保持未完成。
- 边界：健康检查200、部署命令成功或一次请求通过不能替代完整验收；回滚成功表示环境恢复，不表示新功能上线交付完成。
- 失败路径：达到停止条件则走已授权恢复；原因不清进入诊断；观察未结束则等待或交给指定人员，不能伪造持续观察。

## 5. 贯穿流程的职责与授权

### 职责

| 参与方 | 责任 | 边界 |
|---|---|---|
| 用户/指定业务负责人 | 决定业务取舍、范围及被明确保留的风险 | Agent的推断不能替代其决定 |
| 主Agent | 维护有效状态、选择下一节点、交接任务、检查证据与集成 | 子Agent的完成声明不能直接变成整体通过 |
| 实施者 | 在任务范围内实现、验证和回报 | 不能自行扩大范围或接受业务风险 |
| 评审/审计者 | 根据固定对象给证据与发现 | 不擅自修改业务代码，不代替业务验收决策 |
| 发布操作者 | 对指定环境执行并报告实际结果 | 角色可以是Agent、用户或CI；工具可用不等于授权 |
| 宿主与项目工具 | 提供执行、权限、隔离、状态或检查能力 | 技能文字不能创造这些能力 |

一个人或Agent可承担多个责任，但必须区分其当前角色及动作；独立审查是否具备独立上下文如实记录。

### 授权范围

授权来自用户明确指令、有效的既有批准或项目约定；无需为每个节点设置固定人审。记录批准者、原始依据、适用方案/版本、动作、环境和有效条件。只保存定位与摘要，不保存凭证值。

以下要区分：业务预期已确认、设计方案已确定、允许修改工作区、允许提交/推送、允许预览/测试部署、允许生产部署/数据变更。它们可以在同一条具体指令中同时获得，也可以分别获得。

发现授权不覆盖下一动作时，只停该动作。委派不会扩展授权；沉默、超时和自动续跑不构成批准。当前Bug技能要求具体方案确认，此设计保留其现有边界；若未来调整，需明确列为行为契约变更。

用户收回或收窄授权后，不再启动被撤销范围内的新动作；已执行或进行中的操作单独核对。撤回授权不代表外部操作自动取消，也不自动授权新的破坏性恢复动作。对于已批准的发布，执行前仍需核对目标环境、产物与操作是否落在批准范围内。

## 6. 状态、交接与证据有效性

### 最小逻辑记录

这是语义字段，尚未决定JSON/YAML、文件目录或数据库实现。

| 记录 | 必需信息 |
|---|---|
| 工作项 | 标识、目标/非目标、交付终点、当前节点、负责人、状态、下一动作 |
| 输入版本 | 需求、设计、代码及配置、目标环境，相关引用与版本 |
| 任务 | 依赖、允许改动/资源所有权、验收、验证、完成及未完成项 |
| 决策/授权 | 来源、决定者、具体内容、适用范围/版本/环境、有效条件 |
| 验证 | 对象、命令/操作、输入条件、结果、时间、原始证据位置及限制 |
| 外部操作 | 意图、操作标识、目标、执行前后状态、结果、重试/恢复条件 |
| 交接 | 已完成、未完成、阻塞原因、责任方、恢复所需条件 |

代码基线不能只写HEAD：有工作区修改时需同时识别diff及有关未跟踪文件。构建产物、配置和环境也可能独立变化；发布验收引用真正使用的产物和配置标识。

### 状态语义

每个节点/任务区分：待执行、执行中、等待用户、等待外部、失败待处理、已完成、不适用、已失效。执行中必须有当前会话/工具等实际执行依据；没有依据的旧状态按恢复程序核对，不能假定仍在运行。

顶层完成按原始交付终点判断。“代码验收完成”“发布待用户操作”“部署结果未知”“观察未结束”分别报告，不合并成全流程完成。取消由用户或明确项目决策触发，不作为规避失败的替代。

### 节点完成与流程推进

把“产物完成”和“下一动作可执行”分开记录。例如N6发布安排已经完整，但生产授权尚缺：N6可记为产物完成，顶层记为等待用户，N7保持待执行。不能为了表示等待而否认已经完成的准备工作，也不能把准备完成当作部署许可。

主Agent每次选择下一动作时按以下顺序判断，判断结果应能给出依据：

1. 核对用户最新指令、当前交付终点及取消/撤权情况。
2. 核对已经启动的工具、CI和外部操作；有未知副作用时先查状态，不抢先重做。
3. 检查下一动作依赖的需求、设计、代码、环境和证据仍有效。
4. 判断节点是否在范围内、是否已有合格结果可复用。
5. 检查执行能力、资源所有权及具体授权，再启动动作。
6. 记录动作结果、受影响状态及下一步；仅在原交付终点所有必需条件满足后结束。

| 状态变化 | 必要依据 | 不允许的替代依据 |
|---|---|---|
| 待执行 → 执行中 | 前置条件满足，动作已实际启动，执行主体可识别 | 已写计划或已排队 |
| 执行中 → 已完成 | 结果可核对，节点退出条件满足，证据对应当前对象 | 进程退出、子Agent自报或文档勾选 |
| 任意相关状态 → 等待用户/外部 | 指明缺什么、责任方和恢复条件 | 泛称“需要确认”而没有具体缺口 |
| 执行中 → 失败待处理 | 已确认本次动作失败，保留实际结果和副作用 | 未收到输出就断定失败 |
| 已完成 → 已失效 | 相关输入或对象变化，使原结果不再支持当前结论 | 无关文件变化一律作废 |
| 已失效/失败待处理 → 待执行 | 已确定修正或补证范围，保留上次尝试记录 | 删除失败历史后重新勾选 |
| 节点 → 不适用 | 明确原范围不包含它，或其义务确实不存在，记录原因 | 没有能力、没有授权、验证失败 |

资源归属和执行主体是工作协议要求，不宣称Markdown提供了锁或并发控制。宿主没有可靠的资源占用机制时，主Agent串行安排冲突动作；不能在文档中宣称拥有不存在的隔离保证。

### 尝试、重试与恢复

一个逻辑任务可以多次尝试；失败尝试、对应对象、动作与结果保留，当前尝试单独标识。恢复现有执行优先于新建执行，只有确认原执行不再活动，且副作用状态可判断后，才决定是否重试。

对于部署、迁移、通知等外部写操作，执行前至少持久记录操作意图、目标、产物/参数摘要、可查询标识及核验方式；执行后补结果。若外部系统只能在启动后返回标识，应明确这个缺口，并准备按目标实际状态查询的替代办法。

技能不能保证跨系统“恰好执行一次”。缺少操作标识、幂等支持或状态查询能力时，未知结果可能只能交接给操作者；不得为追求自动推进而盲重试。只读查询或已有可靠幂等机制的动作也需限制重试，连续无新信息时转为具体阻塞。

恢复先保留当前环境与用户改动，再选择：继续原尝试、在确认状态后重试、执行授权内恢复、或交接。不把回到前一逻辑节点理解为自动撤销已发生的数据和环境变更。

### 交接包

交接只携带当前有效的目标、输入版本、已定契约、范围/授权、产物与证据索引、未知项和下一动作，不要求复制完整聊天记录。下游先核对输入是否有效，再决定复用或补证。

跨会话交接必须有持久入口；小任务同会话可用简短记录。优先复用项目现有任务系统及文档，后续再确定默认存储策略，不直接新增多份重复真源。

### 失效传播

| 变化 | 必须重新判断的对象 |
|---|---|
| 业务规则/范围改变 | 受影响设计、任务、用例、验收、发布安排及批准范围 |
| 接口/数据/迁移设计改变 | 依赖任务、集成验证、相关审查与发布恢复方案 |
| 代码、依赖、配置改变 | 覆盖该变化的验证证据及候选产物；已有正确证据不全量作废 |
| 发布产物或目标环境漂移 | 发布准备、兼容/恢复假设及上线验收 |
| 执行结果未知 | 先核对外部状态；不通过重新运行证明上次没有执行 |

仅标记受影响内容及原因，其他独立工作可继续。不能拿不同版本的评审拼成完整通过；也不因一个文案修正重跑所有昂贵检查。

## 7. 失败、恢复与例外

- 实现错误：回实施修复，保持原需求与设计；修后只复核受影响证据及项目必需检查。
- 设计假设错误：回N2，评估对需求、任务和批准的影响，避免在实现层连续堆补丁。
- 关键业务歧义：回N1，由有权决定者澄清；独立部分继续。
- 工具/环境缺失：报告实际缺口。若属于必需验证，修复环境、取得合适证据或交给人；不能由Agent自行改成可选。
- 验证失败：保留失败事实和原始证据；风险接受单独记录，不把失败重命名为通过。
- 部署部分成功：区分已完成步骤、未执行步骤、未知步骤；先核对目标环境，再继续或恢复。
- 共享状态冲突：暂停冲突范围，确定唯一所有者并整合；不能靠“独立Agent”推断安全。
- 中断恢复：读取持久入口和实际Git/进程/CI/部署状态，核对是否已有副作用；重新定位第一个未满足节点，而非从头盲跑。
- 紧急缓解：与根因修复分为两个可追踪工作项。得到具体授权后可走精简方案及发布路径，但仍记录影响、恢复和上线验证；缓解不能写成永久修复。

## 8. 与现有技能的关系及能力缺口

节点描述业务阶段，技能描述解决问题的方法，两者不是一对一关系。一个节点可组合多个技能，同一技能也可支持多个节点。

| 能力 | 已有基础 | 待设计/补齐 |
|---|---|---|
| 任务入口和跨阶段推进 | implementation-workflow的任务理解 | 生命周期入口、续接、状态与交接，不抢走实施细节 |
| 需求/验收 | research和test-design的依据要求 | 需求澄清、规格表达、范围变化 |
| 方案设计 | research；architecture-scout机会调查 | 实施方案、接口/数据/兼容/迁移及设计验收 |
| 规划与实施 | implementation-workflow、bug-debugging、test-design | 接入上游契约、持久进度与授权传递 |
| 验收 | diff-review、complexity-audit、mutation-testing | 汇总需求验收、安全/性能/运行证据与必需门槛 |
| 发布与观察 | 当前无完整专用流程 | 环境/产物/迁移/灰度/恢复/观察与外部操作核验 |

不在本文决定新增技能名称、数量或目录，也不为了凑齐节点立即拆成九个技能。确定节点契约后，再按独立可用性、复用及上下文成本决定包装。

## 9. 设计验证与后续实施门槛

配套场景见 `2026-10-16-lifecycle-walkthroughs.md`。它是纸面推演，不能证明真实Agent执行遵从。

设计进入实施前应能回答：每种任务怎样进入和结束；各节点消费什么并交付什么；谁负责决定与执行；什么变化使下游失效；中断和部分副作用如何恢复；没有能力或授权时如何交接。

后续行为验证至少分开评估：选路是否正确、契约/授权是否遵守、产物和结果是否正确、失败恢复是否可靠、真实端到端是否完成。结构测试通过不能替代这些证据。

真实项目验收要求：需求可追溯到测试与上线结果；部署对象可追溯到验收版本；至少验证一次发布失败或结果未知的恢复；记录宿主、模型、项目、命令、环境及限制。不为制造演示而对生产系统注入故障，应使用可控测试环境。
