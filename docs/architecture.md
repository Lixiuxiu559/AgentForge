# AgentForge 架构

## 技能作为方法真源

十三个技能保存在 `skills/<name>/SKILL.md`，配套方法和脚本放在各自 `references/` 与 `scripts/`。不维护自定义 agent 定义，也不把同一套方法复制成宿主专用角色提示词。

技能包含任务边界、执行方法、派发条件、上下文传递与回报格式。主 Agent 根据任务选择方法，需要隔离或并行时调用宿主通用子 agent 工具。Skill 本身不提供执行引擎；没有宿主派发能力时只能在主上下文执行，并如实报告限制。

## 需求定义与实施边界

`pm` 负责把产品想法或需求变更整理为 PRD：问题与目标、范围、业务规则、用户故事、验收标准、假设与开放问题。采用按需澄清，只追问会影响业务规则、范围或验收的缺口；需求明确时直接产出，不设强制访谈或审批门。PRD 默认生成可离线阅读的 prd.html，正文包含可引用的规则和验收锚点，对话只给链接与摘要；保存优先用户或目标项目约定，无约定时使用技能约定的目标项目需求目录。用户指定其他格式及既有正本保持兼容，不强制维护重复 Markdown。PRD 可作为后续设计与实施的输入，但不自动启动这些流程。

## 项目知识与交付流程

`wiki` 是跨阶段的项目知识能力：阅读、初始化、维护、机械检查及变更同步分析。它为需求、设计、实施和验收提供可追溯的背景，但不接管这些阶段，不成为所有任务的强制前置步骤。知识内容由目标项目维护，技能与只读脚本随插件分发。已有布局优先；可选项目配置声明模块路径映射及选定的文档结构约定，不绑定语言、框架、角色或宿主。

脚本通过显式目标根目录读取文档或 Git 范围，不从安装路径推导项目、不调用外部模型。检查命令只读，review 是唯一显式写入复核记录的命令。机械结果与语义结论分别报告，未映射、语法覆盖不足、执行错误不能写成完整通过。Agent 维护时核对规范来源与代码证据，保留人工内容、版本适用范围和未决冲突；已实现与已部署分开记录。`pm` 定义需求，`research` 处理需多步取证的问题，`wiki` 维护这些已确认知识的项目表达。

Wiki 模板与默认内容契约放在技能 `assets/` 中，随技能一起分发。新建且无约定时使用 small 或 modular 骨架，默认结构检查以同目录 schema 为依据；项目自有配置保存所选规范。已有项目默认使用 project 模式，可显式声明必需文档、章节和导航入口，避免通过自动套用模板改变原约定。模板指导生成，确定性工具校验结构，来源真实性及业务一致性仍由 Agent 核实。

Wiki 模块按知识的业务或能力边界组织，与源码允许多对多映射。mapping 报告只读检查真实文件覆盖和共享比例，不按固定阈值判定语义质量。规则模板区分预期约定、实现观察和运行验证；完整旧标题仅保留结构兼容并在 coverage 中报告。初始化按用户目标交付到明确的维护程度，未知局部保留，不把发布治理改造当作文档生成前置条件。

新鲜度记录按模块保存实际复核者、原因、证据和来源及文档的内容/模式指纹；配置变化也会使旧记录失效。读取前检查，开发收尾先核对语义再记录 updated、no-change 或 blocked，交付前检查结构与同步。gate 对索引或提交树读取对应版本的配置与记录，拒绝用工作区新记录替代旧候选。PR 工作流接入检查；远端必需状态与分支保护不由本地文件自动设置。

## 统一架构设计

`architecture-design` 承担本次范围内系统设计的完整性责任，承接 PRD、原型或明确技术需求；先比较真实可行的方案，由用户决定关键取舍或明确授权选择，再建立整体边界、关键流程、数据归属和共享契约，验证关键假设并完成适用专项。小型／单端任务直接完成；复杂且独立的专项可由宿主子 agent 并行设计，主 Agent 持有共享契约、决策记录并集成复核，子 agent 不能代替用户选择重大路线。

正式设计默认交付 spec.html，专题可拆为相互链接的 HTML；架构图、流程图、ER 图等在页面直接可见，并保留可编辑图源，视觉与语义核对分别记录。核心正文为可直接读取的语义 HTML，不依赖在线 CDN，也不强制重复 Markdown。设计准备状态、用户选择和实施授权分别记录，使用摘要提供基线、契约、适用范围、验收与开放问题。本技能独立交付，不指定或调用下一技能；用户要求修订时依据新证据处理，不强制从实施流程返回。

PM、架构、测试设计和实施编排没有固定调用依赖。各技能依据用户当前可用材料独立完成任务，用户决定是否组合、是否跳过某种设计及使用顺序；使用已有材料不等于依赖其生产技能。实施可接收明确需求、PRD、技术方案或测试用例的任意组合，缺少用例时在任务内补足必要验证，缺少普通局部设计时在授权内处理。关键取舍仍由用户决定，不自动补跑其他设计技能。

## Worktree 创建与删除边界

`worktree add` 接受 from 与新分支两个参数，按用户选择使用本地提交或获取到的远端提交，在目标项目主工作树的 `worktree/<新分支>/` 创建工作目录，保留分支层级。创建前检查本地与所选远端的目标分支、目录和父路径冲突，根目录忽略规则保护工作树不被主仓库纳入版本管理。add 遇到已有分支停止，不自动恢复。`worktree remove <分支>` 精确核对约定路径、实际分支与提交，检查包括忽略文件的未提交内容后移除工作树并验证分支提交仍保留；数据风险未处理时停止，不自动强制删除，remove 无需远端。两种操作都不删除或推送分支；通过原生 Git 执行，不依赖宿主特有 worktree 工具。技能安装路径不作为目标项目路径。

## 调试与实施的确认边界

`bug-debugging` 面向具体症状，允许模型按请求自动选用；诊断完成后展示根因状态、证据、修复方案、影响与验证办法，等待用户明确同意该方案再实施。初始修复请求不代表批准尚未展示的方案。诊断期间在临时目录或隔离副本中实验；修改用户工作区进行取证需具体诊断授权，不能据此推导修复授权。

`research` 为调试提供限定范围的证据，主 Agent 抽查关键结论并复用调查，不重复全量调查。简单修复由调试技能直接完成，复杂实施交给 `implementation-workflow` 并携带已批准方案、证据和验收条件；从实施进入调试时确认后返回原编排，避免递归交接。已有具体批准不重复询问，方案发生实质变化才重新确认。确认规则是技能行为约定，不是工具层沙箱。

## 测试设计与实施

`test-design` 独立设计用例、评估业务场景与断言覆盖，默认交付 test-design.html；不编写或执行测试、不派发测试编写任务，也不指定后续流程。仅有需求或 PRD 时可先设计业务场景，技术入口与测试设施缺失时说明限制，不要求补架构方案。HTML 包含具体用例、规则对应关系、覆盖缺口及执行证据状态；已有设计只在规则、材料或范围变化及发现具体缺口时更新。

## 委派协议

1. 主 Agent 确定目标项目、范围、基线、依赖和验收条件。
2. 为独立任务构造自包含说明，传目标项目与技能资源的绝对路径；资源不可读时传必要方法全文。
3. 实际调用宿主通用派发工具，创建独立上下文。任务标签不对应注册的角色类型，不设置固定模型或工具白名单。
4. 子 agent 只执行所分配范围，不递归启动完整编排；返回完成、部分完成或失败，以及证据、实际验证和未验证项。
5. 主 Agent 等待结果、处理缺失与失败、检查集成，再汇总。调查只抽查关键证据，避免重新做一遍全部调查。

并发仅适用于无依赖且不会冲突的任务。独立上下文不等于独立文件系统；源码文件、构建目录、数据库和测试报告都需要明确所有权或互斥。没有并发名额时可串行委派，宿主没有派发能力时由主 Agent 串行执行。

评审三轴使用同一代码基线、不同检查方法，互不参考结论。审计只报告是行为约定，不是沙箱权限。覆盖率和突变工具可能生成临时产物，不能因为不提交修复就视为无副作用。

## Claude Code 装配

`.claude-plugin/plugin.json` 与 `marketplace.json` 提供分发元数据，技能由宿主发现。`architecture-scout` 在说明中限定用户主动调用；Claude Code 侧由模型遵循该约定。没有根级 `agents/` 注册资产。

## Codex 装配

`.codex-plugin/plugin.json` 指向同一份 `./skills/`；`.agents/plugins/marketplace.json` 把仓库根目录作为可安装插件源。这里只声明技能，不添加 MCP、app 或自定义子 agent。

`skills/architecture-scout/agents/openai.yaml` 是该技能的 Codex 调用策略文件，`allow_implicit_invocation: false` 保留仅用户主动调用的语义。这个 `agents/` 路径是技能元数据目录，不是子 agent 定义。

同一技能的 `dsh-model-invocable: false` 保留 DSH 的模型目录限制。Codex 插件校验器不接受 Claude Code 的 `disable-model-invocation: true`，所以共享 frontmatter 不再使用该字段。

Codex 安装后加载插件副本；修改仓库文件不会自动更新已安装副本。更新 marketplace/插件并开启新任务后再验证技能发现、reference 路径与实际委派行为。独立上下文和并行仍由当前 Codex 宿主提供。

## Qoder 装配

`.qoder-plugin/plugin.json` 声明插件元数据与 `./skills/`。仓库清单是构建输入；安装使用 `npm run package:qoder` 生成的 `dist/qoder/agentforge-<version>.zip` 或其解压目录，不直接安装仓库根。ZIP 根直接包含 `.qoder-plugin/plugin.json`、`skills/`、LICENSE、独立 README 与最小 `package.json`，不附加外层目录，也不包含其他宿主的插件清单或 DSH 桥接层。

`tools/package-qoder.mjs` 在临时副本中处理宿主差异：为 `architecture-scout` 写入 `disable-model-invocation: true` 和 `user-invocable: true`，移除 DSH 调用策略字段与 Codex 的 `agents/openai.yaml`。共用技能源文件不变，技能正文、references、assets 和执行脚本随包保留。该策略配置用于保留仅用户主动发起架构调查的约定；真实客户端的自动触发与手动调用行为仍须在宿主中验证。

包内 `package.json` 只声明插件名称、版本、`private: true` 和 `type: commonjs`，为 `crap.js` 建立模块边界，避免解压到 `type: module` 项目时继承上层配置而导致 `require` 报错；`.mjs` 工具仍按 ES module 执行。这是生成的运行元数据，不是仓库的 DSH 包配置，不带 `src/` 或 npm 依赖。

Qoder 负责技能发现、模型执行、缓存、权限及通用子 Agent 委派；本项目不新增 MCP 或自定义 Agent。缺少委派能力时沿用技能的串行执行约定。脚本运行依赖可用 Node.js，Git 操作还依赖 Git；构建另外需要系统 `zip`。安装方式与验收范围见 [Qoder 说明](qoder.md)。

## DSH 装配

`package.json` 声明 `dsh.bundle.patch`，`cordis.patch.yml` 加载 `src/index.js`。桥接代码只使用 Node 内置模块，不依赖 DSH 内部 npm 包。

- `name` 与 npm 包名 `dsh-agentforge` 一致。
- `inject = ['skills']`，`apply(ctx)` 只注册技能提供者。
- provider 名称为 `agentforge`；不注册同名工具。
- `list()` 每次扫描包根下的技能目录，返回元数据与调用策略。支持直接子目录的 `SKILL.md` 和顶层 Markdown，忽略隐藏项、嵌套技能及无效元数据。
- `get(candidate)` 按需读正文，设置绝对 `path` 与 `resourceBase`，保留调用策略。
- 兼容正文中的 `${CLAUDE_PLUGIN_ROOT}` 占位符；reference 文件以技能目录为基准解析，不假定目标项目包含插件资源。
- 包根从模块位置推导，与宿主工作目录无关。新增/删除/修改技能在下次读取时反映；宿主可能另有缓存。
- 注册生命周期由 Cordis 管理；桥接代码更新需要重启 profile。

通用子 agent 工具、上下文创建、并发额度和运行状态由宿主提供。AgentForge 不再做工具名映射、模型选择、persona 构造或 subagent provider 路由。

## 迁移

移除 `agents/*.md`、DSH `agentforge` 工具及其 `agent` 枚举参数。旧角色调用改为相应 Skill 加宿主通用派发；映射见 README。旧的 `config.toolName`、`config.provider`、`config.agents` 不再使用。

这是现有调用契约的移除，正式发布遵循仓库的破坏性变更规则。历史 CHANGELOG 和研究报告保留原时点事实；当前行为以本文件与技能为准。

## 验证边界

`tools/doctor.mjs` 验证四端结构、清单、版本、技能引用、发布资产与入口契约。Node 内置测试验证在仅有 skills 服务时加载 DSH 插件、动态扫描、按需加载、资源路径与 invocation 策略。Qoder 打包回归核对 ZIP 布局、策略转换、资源完整性与源文件保持不变。CI 在 Node 22/24 上运行。

这些检查验证包内行为，不替代 Claude Code / DSH / 其他宿主的真实派发测试；不声称每个宿主都具备相同并发或上下文能力。

## 组件与数据流

本项目的架构约定与实现分层如下，2026-10-29 按 src/index.js、cordis.patch.yml、四端清单、Qoder 打包脚本、package.json 及技能目录补充静态说明；宿主实际执行结果另行记录。

| 组件 | 职责与边界 |
|---|---|
| skills 目录 | 技能正文、references、assets 和脚本；共用方法真源，不提供独立常驻 Agent 服务 |
| DSH provider | src/index.js 依赖宿主 skills 服务注册 provider；list 扫描目录并读 frontmatter，get 按 locator 返回正文、资源目录和路径 |
| Codex / Claude Code 清单 | 声明插件或技能目录供相应宿主发现；清单存在不能证明用户安装成功 |
| Qoder 打包层 | 从共用技能生成独立 ZIP，仅在副本转换平台调用策略、排除其他宿主元数据 |
| 宿主 | 提供模型、工具、执行与可用的委派能力；用户目标项目与技能安装目录分离 |
| Wiki CLI | 读取显式项目根与配置，check/mapping/changes/freshness/gate 只读，review 显式保存项目记录；不提供外部模型或部署服务 |
| 分发工具与 CI | 校验、版本准备和按触发条件发布；实际安装和运行结果需另行取证 |

DSH 路径为：宿主加载 bundle → apply 注册 provider → list 暴露候选 → get 按需读取正文与资源位置 → 宿主执行技能方法。Codex/Claude Code 通过各自清单发现共用技能；Qoder 构建输入 → 临时副本转换 → ZIP 导入 → 宿主发现技能，具体缓存与调度由宿主决定。Wiki 路径为：Agent 在目标项目取证并维护知识 → CLI 对目标项目文件或候选 Git 树执行机械检查 → 项目本地保存知识及复核记录。源码未定义独立数据库、消息队列或自营在线 API；目标项目的数据和外部服务不因此成为本插件的托管资源。

## 架构核验范围

本页区分方法约定和静态实现观察，当前组件链路由本地 provider 测试与 CLI 回归覆盖其隔离场景；真实宿主缓存、安装 UI 和用户环境未在本轮运行。Wiki 初始化还需评估架构、部署/环境和运维覆盖，沿用既有文档；可按 structure.documents 的显式 type 启用专用模板检查，未选型的旧页面保留项目章节。环境运行状态以各条观察时间与证据为准，不能由清单版本或整个页面日期推导。环境和运维入口见 [Wiki](wiki/README.md)。
