## 用途与边界

技能定义执行方法，主 Agent 结合用户请求选用；它们不会注册固定模型或统一的自定义角色。审计的“只报告”、调试的修复确认等属于技能行为约定，不是工具层权限机制。

| 技能 | 主要交付与边界 |
|---|---|
| [pm](../../../../skills/pm/SKILL.md) | 按需澄清并默认交付 HTML PRD；不自动进入架构设计和实施 |
| [prototype](../../../../skills/prototype/SKILL.md) | 将 PRD 或明确页面需求转为 HTML 原型与字段／状态清单；不实施生产前端或定义 API |
| [architecture-design](../../../../skills/architecture-design/SKILL.md) | 比较可行方案，用户决定关键取舍；独立 HTML 设计、可见图示、风险验证和使用说明，复杂专项委派后统一集成 |
| [research](../../../../skills/research/SKILL.md) | 多步取证与比较；简单定位和常规信息确认不启动完整调查 |
| [test-design](../../../../skills/test-design/SKILL.md) | 独立交付 HTML 用例与验证办法；不要求架构方案，不编写或运行测试 |
| [bug-debugging](../../../../skills/bug-debugging/SKILL.md) | 具体症状取证、根因和方案；具体方案获同意后修复 |
| [architecture-scout](../../../../skills/architecture-scout/SKILL.md) | 用户主动发起架构机会调查；允许没有候选 |
| [implementation-workflow](../../../../skills/implementation-workflow/SKILL.md) | 评估依赖、组织实施、集成验证及按风险审计 |
| [diff-review](../../../../skills/diff-review/SKILL.md) | Correctness、Standards、Spec 三轴独立评审 |
| [complexity-audit](../../../../skills/complexity-audit/SKILL.md) | 复杂度与覆盖率风险报告；工具不足如实降级 |

## 主要流程

1. 依据请求选择技能，复用现有需求、调查和验证证据。
2. 只在需要独立上下文、且宿主确有派发工具时委派；并行任务必须无未解决依赖、无同文件或产物冲突。
3. 实施者负责代码和实际测试；测试设计与审计分别交付其约定结果。
4. 调试保留方案确认边界；已有批准不重复询问，部署和外发仍受实际授权约束。
5. Wiki 可由用户或 agent 独立调用，阅读／检查保持只读；其他技能不调度 Wiki，不在执行或收尾时附带新鲜度检查或维护。明确生成或维护请求应直接交付开发知识：以代码为依据，语言按用户指定 > 已有 catalog > scan 建议 > 对话语言确定，用户指定的文档语言同时决定路径语言（除非另行指定），生成前请用户确认目录；保留项目约定，主 Agent 整合共享关系；小修正不强制委派。不要求产品确认或逐段核验台账；沿用项目已启用的新鲜度和检查机制，只为实际核对范围保存声明。
6. 主 Agent 核对返回产物、实际执行证据及缺口后交付；技能交付不自动触发下个阶段。

`worktree add` 正常路径只询问 from 使用本地还是远端；未配置 origin 且有多个远端时补问远端；远端名须出现在 git remote 中且不以 - 开头，fetch/ls-remote 将其放在 -- 之后，所有仓库命令显式指定主工作树根。目标分支在本地或所选远端已存在即停止，远端查询失败不能当作不存在。linked worktree 内调用仍定位主工作树，父路径不能穿过其他工作树或符号链接。`worktree remove <分支>` 不查询远端，删除前核对目录与分支一致，未提交、未跟踪或忽略内容非空时停止；删除后验证分支提交未变。具体执行与失败边界见技能正文。

Qoder 沿用同一套方法与授权边界；构建副本为 architecture-scout 写入仅用户主动调用策略，主源仍保留 Codex/DSH 元数据。具体转换和验证边界见[分发模块](../distribution/README.md)，不能由元数据推导真实模型行为。

`prototype` 可承接 PM 的 PRD，也可从明确页面需求开始；按 T1/T2/T3 裁剪投入，沿用目标项目的视觉语言。明确需求直接出稿，关键业务缺口按需澄清；交付离线 HTML 与 prototype.md，不迁移 PRD、不强制建立审批门，也不自动实施。静态或本地模拟仅供走查，真实权限与服务行为不由原型证明。

`architecture-design` 先比较真实可行方案及优缺点、成本和风险，给出推荐后由用户决定关键取舍；已有明确选择或授权沿用，普通细节不重复确认。用户未决定时只推进独立取证或候选探索，不能以推荐项为定案深化。之后完成整体与必要专项、质量场景和关键风险验证，复杂且独立的任务使用宿主子 agent，主 Agent 独占共享契约并负责对齐。正式交付默认为 spec.html，按场景提供直接可见的架构图、流程图、ER 图、时序／状态／部署图并保留可编辑图源；图源未转换成图形时标明未完成，已有图形但无浏览器时标明视觉未验证，渲染成功不代表语义正确。

设计准备程度区分草案、可实施、局部可实施及受阻，与用户决策和实施授权分别记录。使用摘要提供基线、契约、范围、依赖与验收，便于用户自由选用；本技能不指定后续流程，用户要求修订时再核对相关证据和取舍。无全栈 Spec 的单端需求也可设计。

PM 默认交付 prd.html，架构默认交付 spec.html，测试设计默认交付 test-design.html；HTML 保留完整语义正文、导航及可引用锚点。四项能力独立使用，不自动相互调用、不要求固定前置技能或文档。测试设计可仅基于需求，实施可接收需求、设计、测试用例的任意组合；缺少某类文档不能直接视为阻塞，只有影响结果的关键问题才需澄清。用户决定顺序与组合，既有格式约定保持兼容。
