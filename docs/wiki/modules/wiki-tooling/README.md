## 用途与边界

Wiki 支持用户或 agent 独立调用；阅读／检查保持只读，其他技能不调度或附带 Wiki 检查和维护。Wiki 内容保存在目标项目，技能资源随插件分发。脚本只做扫描和机械检查，不调用模型、不生成业务事实；review 仅显式保存复核声明。

技能按目录中是否存在 `catalog.json` 分成两套结构：

| 结构 | 入口 | 用途 |
|---|---|---|
| 新结构（catalog.json，version 2） | [SKILL.md](../../../../skills/wiki/SKILL.md) 的生成／阅读／更新／检查四个任务；[generate.md](../../../../skills/wiki/references/generate.md)、[writing.md](../../../../skills/wiki/references/writing.md) | 从零生成按开发问题组织、关键结论附源码行号的 Wiki，既供 Agent 按 summary 选页，也供人阅读 |
| 旧结构（wiki.config.json） | [freshness.md](../../../../skills/wiki/references/freshness.md)、[tools.md](../../../../skills/wiki/references/tools.md) 的旧结构一节 | 已有 Wiki 继续按 structure、mapping、freshness、review、gate 维护；本仓库自用 Wiki 仍是这种结构 |

新结构的 `status`／`finalize` 增量更新与旧结构迁移尚未实现，设计与分期见 [重构方案](../../../design/2026-10-30-wiki-refactor.md)。

## 主要流程

新结构生成：

1. `scan` 只读输出 Git 可见文件清单、编程语言分布、入口候选、目录体量、已有文档及语言建议。语言按已有 catalog > 项目文档正文 > 代码注释与提交信息判定，信号不足时返回 null，由对话语言兜底；`pathLanguage` 跟随已有文档路径的中文／ASCII 风格，无参考时等于 `language`。扫描结果只是建议：用户指定文档语言而未单独指定路径语言时，路径随之使用该语言，并在规划阶段列出将改名的页面与外部入链。`scan`、`check` 未传 `--root` 时取当前 Git 根。
2. Agent 读入口代码与已有文档，规划 `catalog.json`（页面 id、标题、路径、摘要、来源、子页），请用户确认后逐页按 `assets/pages/` 四个模板生成；派发子 Agent 时必须传入 `language`。
3. 写 README 导航后运行 `check`：catalog 格式、页面存在（planned 可缺）、来源存在、H1 与引用块摘要和 catalog 一致、正文主要语言（仅中英文）、标题与 `<summary>` 未残留模板“中文 / English”双语、未收录页面、从 README 可达；来源超过 15 个文件的页面列入 `coverage.catalog.oversized` 作为拆页提示，不影响退出码；生成流程要求规划阶段就运行 check，确认目录前拆分或收窄超出的页面。
4. 写作要求以代码为准：来源是文档时不转述原文，只写跨文件关系、生效位置与修改时需同步之处；关键实现写到判定条件、失败表现与边界，追不到证据处就近标“推断”。

旧结构维护：

1. 读取项目指令、现有入口及相关未提交内容，确定开发知识范围和模块职责。
2. 以当前代码、配置、调用关系与工程脚本解释架构、业务实现、部署和运维，关键结论附来源。
3. 实质性多模块维护由模块编写者取证、独立上下文复审，主 Agent 整合导航与跨模块关系；运行中的子 Agent 默认最多 3 个，宿主更低上限优先。这是技能的调度约定，工具脚本不启动或限制宿主 Agent。
4. mapping 检查路径覆盖，`--document` 直接列本页覆盖／缺口／歧义；check 检查结构与链接。工具不自动证明正文语义，也不代写知识。
5. 已接入项目在读取前检查 freshness，收尾核对实际 diff 及相关知识，再保存实际范围的 review；gate 按所选候选及项目策略检查同步状态。

当前 AgentForge 自用 Wiki 采用 modular 旧结构，本模块单独拆出规则和代码映射；文件／目录沿用现有英文路径，modules、README.md、reviews.json、wiki.config.json 保留固定名称。旧模板 `assets/templates/` 继续服务旧检查，删除安排在迁移之后。

### 架构与运行知识

初始化逐项评估项目概览、业务/能力、架构、部署环境、运维排障；已有文档可链接复用，缺口或不适用说明原因。新增五类按需模板，通过 structure.documents.type 显式选型，不按路径强套旧文档。环境页检查环境、观察时间和证据来源字段，未知可明确记录；脚本不会证明上线健康或感知外部漂移。本仓库沿用外部架构/发布手册并新增环境与维护页作为实际应用。

### 交付与知识状态

技能提供开发知识的写法与检查工具，不组织产品审批。持续维护、持续同步与强制门按项目实际接入分别说明；没有PRD也可以交付准确实现知识。源码行为、测试执行和运行观察按实际证据范围表达，不能将脚本存在写成已部署。

mapping和单页包只读路径及所选知识页，不读源码内容。工具直接列coverageSummary/coverageMessage及覆盖、缺口、部分覆盖、歧义、知识引用与未解析候选；执行者自行读代码核实，普通维护不填逐段记录。知识写法、证据边界及必要技术缺口统一见正文核对方法。

### 正文与来源的核对

重要实现结论沿实际调用链追源，核对入口、配置覆盖、生效条件和异常，不扩大平台或渠道范围。维护时通读受影响整页，直接改错误原句/表格/步骤，将新知识融入合适章节，同步概述、职责、数量和步骤，整理标题、列表、表格、代码块及导航链接，合并重复与归档过时说明；保留有效人工解释和有价值的历史，不全库格式化。读回最终正文与 diff 并检查跨页重复事实；来源进入实际所属模块，导航和运行时路径不机械当依赖。check 只做支持范围内的结构／链接检查，不自动排版或证明语义一致；阅读／检查发现的问题仅报告。复审不要求凑问题或逐句复述实现。

### 待确认项的语义准入

待确认项只列合理查证后仍影响开发理解、修改或本次操作的技术问题，并交代影响、已有依据与下一步查证。已知边界、未执行验证、临时会话状态和未被要求的未来能力分别归位；没有符合项就明确写无。未演练恢复等风险仍保留在操作旁，不能为减少问题而删掉。模板保留章节，脚本不按关键词判断语义。
