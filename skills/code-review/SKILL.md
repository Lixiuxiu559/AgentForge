---

对 `HEAD` 与用户给定的固定点之间的 diff 做双轴审查：

- **Standards**——代码是否符合本仓库成文的编码标准？
- **Spec**——代码是否忠实实现了原始 issue / spec？

两个轴以**并行子代理**运行，互不污染对方的上下文，然后本技能汇总它们的发现。

## 流程

### 1. 确定固定点

用户说的任何东西都是固定点——commit SHA、分支名、tag、`main`、`HEAD~5` 等。如果用户没指定，问。

一次性捕获 diff 命令：`git diff <fixed-point>...HEAD`（三点，与 merge-base 比较）。同时通过 `git log <fixed-point>..HEAD --oneline` 记下 commit 列表。

在继续之前，确认固定点能解析（`git rev-parse <fixed-point>`）且 diff 非空。坏的 ref 或空 diff 应该在这里失败——而不是在两个并行子代理里失败。

### 2. 识别 spec 来源

按此顺序寻找原始 spec：

1. Commit message 中的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等）——用 `glab issue view <number> --comments` 获取。
2. 用户作为参数传入的路径。
3. 项目约定中声明的 PRD / spec 目录下与分支名或功能匹配的文件（约定见 `.claude/agentforge-conventions.md` 的 `prd-dir` 与 `spec-dir`；未声明时先 `Glob` 找 `**/prd/**`、`**/specs/**`、`.scratch/**`）。
4. 什么都没找到就问用户 spec 在哪。如果他们说没有，**Spec** 子代理将跳过并报告 "no spec available"。

### 3. 识别标准来源

仓库里任何记录代码该怎么写的文档 —— 优先用 `.claude/agentforge-conventions.md` 的 `coding-rules` 字段，未声明时用 `Glob` 搜索 `**/*coding-rules*`、`**/CONTRIBUTING.md`、`**/docs/**/*standard*`。找不到就如实说明"仓库未记录成文标准"，只跑味道基线。

在仓库文档的基础上，Standards 轴始终携带下面的**味道基线**——一组固定的 Fowler 代码味道（《Refactoring》第 3 章），即使仓库什么都没记录也适用。两条规则约束它：

- **仓库优先。** 成文的仓库标准总是胜出；凡它认可基线会标记的东西，压制该味道。
- **永远是判断。** 每个味道都是带标签的启发式（"可能的 Feature Envy"），绝不是硬违规——并且，像这里的任何标准一样，跳过工具已经强制的东西。

每个味道读作*它是什么* → *怎么修*；对着 diff 匹配它：

- **Mysterious Name（神秘命名）**——函数、变量或类型的名字不揭示它做什么或持有什么。 → 重命名；如果想不出诚实的名字，设计是模糊的。
- **Duplicated Code（重复代码）**——同一种逻辑形状出现在改动中的多个 hunk 或文件。 → 抽出共享形状，两处调用它。
- **Feature Envy（依恋情结）**——一个方法访问另一个对象的数据多于访问自己的。 → 把方法移到它依恋的数据上。
- **Data Clumps（数据泥团）**——同样的几个字段或参数总是一起出现（一个想诞生的类型）。 → 捆成一个类型，传它。
- **Primitive Obsession（基本类型偏执）**——一个基本类型或字符串顶替了一个值得拥有自己类型的领域概念。 → 给这个概念自己的小类型。
- **Repeated Switches（重复开关）**——对同一类型的同一个 `switch`/`if` 级联在改动中反复出现。 → 用多态替换，或一个两边共享的 map。
- **Shotgun Surgery（霰弹式修改）**——一个逻辑变更迫使在 diff 中散落许多文件做编辑。 → 把一起变化的东西聚到一个模块。
- **Divergent Change（发散式变化）**——一个文件或模块为几个不相关的原因被编辑。 → 拆分，让每个模块只为一个原因变化。
- **Speculative Generality（投机性通用）**——为 spec 没有的需求添加的抽象、参数或钩子。 → 删除；内联回去直到真实需求出现。
- **Message Chains（消息链）**——调用方不该依赖的长 `a.b().c().d()` 导航。 → 在第一个对象上用一个方法隐藏这段路径。
- **Middle Man（中间人）**——一个类或函数大部分只是转发。 → 砍掉它，直接调真实目标。
- **Refused Bequest（被拒绝的遗赠）**——一个子类或实现者忽略或覆盖了它继承的大部分。 → 放弃继承，用组合。

### 4. 并行生成两个子代理

**Standards 子代理 prompt**——包含：

- 完整的 diff 命令和 commit 列表。
- 你在第 3 步找到的标准来源文件列表，**加上第 3 步的味道基线全文**——子代理没有其他途径获得它。
- 简报："报告——在相关的每个文件/hunk 上——(a) diff 违反成文标准的每一处：引用标准（文件 + 规则）；(b) 你发现的任何基线味道：命名并引用 hunk。区分硬违规和判断——违反成文标准可以是硬的，但基线味道永远是判断，且成文的仓库标准优先于基线。跳过工具已强制的东西。400 词以内。"

**Spec 子代理 prompt**——包含：

- diff 命令和 commit 列表。
- spec 的路径或获取的内容。
- 简报："报告：(a) spec 要求但缺失或部分实现的需求；(b) diff 中没被要求的行为（范围蔓延）；(c) 看起来实现了但实现方式可疑的需求。每个发现引用 spec 原行。400 词以内。"

如果 spec 缺失，跳过 Spec 子代理并在最终报告里注明。

### 5. 汇总

在 `## Standards` 和 `## Spec` 两个标题下呈现两份报告，逐字或轻度清理。**不要**合并或重排发现——两个轴是刻意分离的（见*为什么是双轴*）。

以一行总结结尾：每个轴的发现总数，以及*各自轴内*最严重的问题（如果有）。不要在轴之间选一个总赢家——那正是这个分离要防止的重排。

## 为什么是双轴

一次改动可能过一轴、挂另一轴：

- 遵循每条标准但实现了错误的东西 → **Standards 过，Spec 挂。**
- 完全按 issue 要求做但打破项目惯例 → **Spec 过，Standards 挂。**

分开报告，防止一轴掩盖另一轴。
