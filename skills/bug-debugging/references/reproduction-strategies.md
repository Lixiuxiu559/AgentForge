# 复现与观测的选择

## 按现有入口选择最便宜的可靠信号

| 已有条件 | 优先办法 | 必须观察什么 |
|---|---|---|
| 失败测试 | 运行该测试，再检查断言与触发路径 | 是目标断言失败，还是测试环境失败 |
| API / CLI | 脱敏 fixture + 请求或命令 | 状态码、返回值、顺序、副作用等实际约定 |
| UI | 已有浏览器工具重放操作，记录关键状态 | 用户可见结果；底层单测不能代替 UI 场景 |
| 只能在线上观察 | 脱敏日志、trace、请求时间线、离线重放 | 同一请求/实体跨边界的状态变化 |
| 难以直接运行整个系统 | 针对相关模块的一次性 harness 或隔离副本 | 必须保留导致失败的调用顺序与依赖行为 |
| 版本回归 | 同一输入在已知正常版本与异常版本上对比 | 环境、数据和依赖是否一致 |
| 人工才能确认 | 给出具体操作与失败判据，请用户回传结果 | 记录为用户观测，不声称由 Agent 运行 |

先使用项目已有工具，不为了符合流程安装整套测试框架。复现命令应短、可重复且退出状态明确；快和确定是优化目标，不能因此丢掉真实触发条件。

## 最小化时保留触发链

逐次去掉无关输入、操作和依赖，每次重新观察相同症状。特别注意跨请求缓存、重试、权限切换、测试污染和先后顺序；只测最后一次调用可能会把问题抹掉。

保留原始失败场景、最小场景及正常对照。发现缩减改变了错误类型，就退回最近仍复现目标症状的版本。不要修改断言、吞掉异常或用与真实约定无关的 mock 制造“通过”。

## 偶发、并发与时序问题

记录执行次数、失败次数、种子/并发度、等待条件和环境。通过可控调度、屏障、重放等提高复现率；负载实验只在适合的本地或隔离环境运行。注意插桩自身可能改变时序。

修复前后使用相同条件和可解释的运行预算；报告“运行 N 次出现 K 次失败”，不要把零次失败解释为永不发生。优先构造能控制触发顺序的回归测试，同时保留真实场景验证。

等待异步结果时观察实际完成条件，设置符合业务时限的超时，失败输出包含最后状态。轮询间隔随操作成本选择；不要照搬固定毫秒数，也不要通过增加 sleep 或全局超时掩盖因果问题。

## 性能回归

先固定数据规模、环境、冷热状态、并发和测量指标，再建立正常/异常基线。按问题选 profiler、查询计划、计时或资源采样，避免大量日志干扰测量。报告重复测量及波动，不根据一次耗时宣称优化有效。

只有已有可靠好坏判据、可用的好坏版本时才使用 bisect；在隔离副本中运行，环境不支持的提交应标记跳过，不能当作坏提交。不要在用户的脏工作区来回切版本。

## 无法复现的出口

说明已运行什么、实际观察到什么、哪些证据不可得。选择能区分当前解释的最小补充输入，例如同一次请求的两端日志、失败时配置或脱敏 fixture；不要一次索要所有日志和整个环境。

可以交付有证据支持的原因和后续验证方法，但不能标为已验证，也不能为通过复现门而制造无关失败。涉及生产插桩或共享环境操作时，先给出具体操作、影响和清理办法并获得授权。
