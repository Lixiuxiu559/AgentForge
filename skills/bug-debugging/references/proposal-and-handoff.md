# 修复前说明与确认后的交接

## 展示给用户的内容

简单问题用几句话，复杂问题可以用下列结构；不要把模板中没有意义的项硬填成风险。

```text
原因：[发生条件 → 内部偏差 → 用户看到的结果]
证据：[源码/日志位置与实际实验结果]；状态：[已验证 / 有证据支持 / 未确定]
方案：[修改哪些行为与模块，为什么有效]
取舍：[有实际差异的替代方案和推荐理由；无实质取舍可省略]
影响：[受影响调用方、兼容性或数据变化；必要时说明回退方式]
验证：[旧版本的目标失败、新版本的预期结果、原始场景及相关正常场景]
请确认是否按这个方案实施；也可以补充约束或提出其他方案。
```

提交前应已完成权限范围内的取证，方案具体到用户能判断修复行为。不要用“先优化一下”“加个判断试试”索取空泛同意。证据不足时把下一步写为取证或缓解方案，不伪装成已知根因的修复。

## 什么算批准

- 用户针对已展示的方案说“同意”“按方案 A 改”或等价的明确指示。
- 同一会话中已经批准的具体方案可以续用；上下文压缩后保留方案摘要、用户批准内容、范围和未确认项。
- 初始“修好它”、仅对原因表示“明白”、子 agent 的赞同、等待超时或用户尚未回应，都不能代替批准。
- 用户附带新约束时判断它是否改变方案。实质变化先展示更新后的方案并确认；不影响已批准行为的局部实现选择由 Agent 完成。

等待期间不启动正式修复、迁移或持久配置更改。收到批准后，继续完成批准范围内的实施和验证，不再次询问“要不要开始”。

已批准实施中自身引入的错误可在原方案范围内继续纠正；若验证中发现另一个独立缺陷，先报告，不顺手扩大修复范围。

## 交给 implementation-workflow 的最小上下文

| 内容 | 交接要求 |
|---|---|
| 目标与范围 | 目标项目绝对路径、版本/基线、涉及模块、用户现有改动 |
| 根因 | 症状、触发链、置信度与证据索引 |
| 复现 | 已实际运行的命令/操作、输入、结果、环境和限制 |
| 批准 | 已展示方案、用户批准内容及附加约束；是否允许行为或接口变更 |
| 验收 | 回归测试、原始场景、需要保留的正常行为 |
| 当前状态 | 临时产物、已完成检查、尚未验证项 |

已经由实施工作流进入调试时，确认后返回原工作流继续，不递归启动一套新编排。实施子任务只能执行获批范围；遇到根因或方案变化就回报主 Agent。

交接不默认创建提交、PR、部署或发送外部消息。原请求已包含这些动作时，按其授权与项目约定处理。
