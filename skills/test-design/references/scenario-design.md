# 按业务规则推导场景

## 参数与边界

先确认参数契约：必填还是可选、类型与转换规则、范围、精度，以及约束由哪一层负责。代表值应来自这些约定。

假设已确认 R1：“外部请求的购买数量必须是整数且在 1～5 之间，非法输入不得创建订单或扣减库存”。可以设计：

| 用例 | 输入 | 预期结果 |
|---|---|---|
| T1 正常值 | 2 | 按数量 2 创建订单并更新库存 |
| T2 下边界 | 1 | 接受，实际数量为 1 |
| T3 上边界 | 5 | 接受，实际数量为 5 |
| T4 低于下界 | 0、-1（分别执行） | 按约定拒绝，订单和库存不变 |
| T5 高于上界 | 6 | 按约定拒绝，订单和库存不变 |
| T6 非整数 | 1.5 | 按约定拒绝，订单和库存不变 |
| T7 缺失值 | null、未传字段（分别执行） | 按必填契约拒绝，副作用不发生 |

错误码、提示和是否允许字符串数字等未给出的约定应单独标明待确认，不能照抄现有实现补成业务事实。如果只有“大于 0”的约定，不能擅自增加整数或上限规则。

对整数使用相邻整数，对金额使用约定的最小货币单位，对浮点数使用符合业务精度的边界值；避免用不现实的极小值制造无关测试。无穷大、NaN、空字符串或数组是否需要设计，取决于入口可接受的数据表示。

## 状态、角色与副作用

用“当前状态 + 角色/权限 + 事件 → 新状态/拒绝 + 副作用”表达场景，明确非法转换后的状态应保持什么。覆盖关键合法转换、非法转换和失败后的恢复；同一角色在不同状态下可能拥有不同操作权限。

涉及数据写入、库存、通知或外部调用时，除了返回值，还要描述最终状态和不得发生的副作用。现有单元 mock 只能证明调用约定时，不能声称真实事务、持久化或外部系统一致性已经得到验证。

按业务风险选择重复提交、并发和多次调用的场景；不存在相应契约时记录待确认。不要仅测试一个孤立方法调用，遗漏“先执行 A，再执行 B”才触发的状态变化。

## 组件与页面

根据项目已有组件测试能力，从用户操作和业务状态设计用例，使用现有稳定的交互入口，不绑定无关的内部函数名或 DOM 结构。

| 关注点 | 可设计的业务场景 |
|---|---|
| 初始状态 | 正确的数据、默认值和可操作项；必要时覆盖空数据 |
| 输入与校验 | 合法输入完成操作；非法输入有约定提示且不发送不应发送的请求 |
| 提交中 | 可见的等待状态和操作限制，按契约处理重复点击 |
| 请求失败 | 不出现成功结果，保留必要输入，按约定允许重试或退出 |
| 请求成功 | 正确的数据与页面状态变化、相关组件更新 |
| 状态或角色差异 | 允许的业务动作及被禁止的动作符合约定 |
| 多次异步操作 | 若有切换对象或查询竞争，旧响应不错误覆盖当前对象 |

每项只在与当前功能有关时展开。截图、快照、按钮存在或回调被调用可以作为部分证据，不能独自证明业务正确。

说明模拟边界：可模拟外部请求结果以观察页面行为，不模拟掉本次要验证的校验、计算或状态转换。模拟接口不能证明真实后端契约；这类限制留在验证缺口中，不要求自动搭建其他测试设施。

## 断言与组合选择

预期结果必须能够区分正确和错误行为。正常场景检查具体结果；失败场景检查约定错误、状态保持和禁止的副作用；不要使用被测函数本身生成预期值。

优先关键边界、规则交互和高影响失败。相同预期不一定意味着可合并：缺失值可能走默认逻辑，零可能是合法数字但违反业务范围。可以用一个参数化用例承载多个代表值，但清楚列明每个输入的依据和预期。
