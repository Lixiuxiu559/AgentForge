# 原型清单与走查

`prototype.md` 与 HTML 成对维护：HTML 表达视觉，清单说明字段语义、操作条件和状态。按需求规模组织，不要求固定章节数量。

## 待验证问题与观察

记录本轮要帮助决定的问题、需求依据、对应页面／方案／场景及判断依据。问题应能通过走查观察，例如“提交失败后，用户能否看到失败原因、保留输入并重试”；需求已明确时直接提取，不为了填表新增业务规则。

交付时补记实际观察、结论依据和未验证部分，区分作者自查、用户反馈与待用户选择。没有用户反馈时可以给出设计建议，不能写成用户已选定；本地模拟只能说明交互表达，不能证明真实服务、权限或后端业务规则成立。

## 页面与依据

列出页面／区域、页面类型、入口、需求依据和对应 HTML。弹窗或内嵌面板不强造路由；新路由只有明确约定才当作已确定事实，其余标为建议。需求依据可为 PRD 条目或用户对话中的具体要求。

T2 写清所在页面、保留的上下文和新增／修改／删除内容，避免局部原型被误解为整页改版。

## 多方案探索（按需）

布局或流程已确定时不强制生成备选。探索时先记录共同需求、样式基线、模拟数据和比较状态，再用简表说明各方案的结构差异、适用理由、取舍及对应的 HTML 入口。差异应围绕待验证问题，例如同一组筛选与批量操作采用不同信息层级，而非用不同颜色冒充不同方案。

共同字段和规则只写一份，方案特有的字段、操作与必要状态单列；先做到足以比较，不为未选方案复制完整清单。已有项目沿用同一主题和视觉规则，T2 的保留区域不随方案变化；不得借探索改写业务规则或扩展页面范围。

方案使用稳定名称，在离线 HTML 中提供切换或对照入口；切换器与说明位于独立演示区，不作为业务页面控件。切换时恢复约定的可比模拟数据与状态，或明确展示各自初始条件，避免残留状态掩盖布局差异。无需改动生产路由、启动应用或引入服务。

记录已收到的方案选择及理由，组合方案时明确采用的部分；未有选择时保留备选、建议和待定项，可直接交付，不替用户宣布胜出方案。选定后同步细化对应 HTML 与清单，不自动将原型转为生产代码。

## 样式基线与差异

已有项目在绘制前记录本次适用的规则，按实际涉及的维度裁剪；新项目将本节作为设计建议，不伪造现有规范。

| 维度 | 记录内容 |
|---|---|
| 参照范围 | 目标应用／模块、页面路径或截图标识、主题、视口；选择该参照的原因 |
| 页面骨架 | 导航与侧栏、内容宽度、页边距、标题和工具栏位置、表单分组与操作位置 |
| 视觉规则 | 字体与层级、背景／文本／边框／主色、间距、圆角、阴影；实际值或 token 及来源 |
| 控件与密度 | 相关按钮、输入框、表格、弹窗等的尺寸与状态、行高、操作折叠、图标及响应式约定 |
| 复用与差异 | 对应组件／样式／资源路径、原型采用方式、需求导致的变更、离线替代和缺失依据 |

仅记录影响本次绘制的规则，不全仓盘点组件。来源要能定位到文件中的变量／选择器／组件或截图区域；区分源码事实、视觉观察、估计值与设计建议。例如表格行高须来自目标表格的实际规则或截图估计，不能仅凭“使用某组件库”填入默认值。

交付时补记对照的页面与状态、视口及主题、已修正的偏差和剩余差异；无法获取真实渲染时明确写明仅核对源码基线。基线和差异记录放在清单或演示说明区，不塞进业务页面布局。

## 字段与操作

按展示列、筛选项和表单分别列信息，适用时使用下列列项：

| 对象 | 应说明的信息 |
|---|---|
| 展示字段 | 语义名、显示名、类型、值域、格式、空值及超长展示 |
| 筛选项 | 控件、值域、默认值、匹配方式、重置行为 |
| 表单字段 | 控件、类型、必填、默认值、校验、创建／编辑差异 |
| 操作 | 所在位置、可见／禁用条件、触发、确认、成功／失败反馈、后续去向 |

已有字段沿用项目名称与实际值域；新字段使用业务语义命名，不把建议名宣称为 API 或数据库字段。每个重要枚举与业务限制保留依据；未知项在使用处标注，并在开放问题中解释影响。

展示文本与数据值分开。示例形式为 `pending → 待处理`，仅在确有来源或明确标为新设计建议时使用；不要从显示文案反推真实枚举。权限可描述业务角色条件，无依据时不生成权限码。

## 状态与流程

列出状态、触发条件、展示、可用操作和恢复路径，并关联可查看该状态的 HTML 位置。按适用性检查：

- 正常、加载、空数据、筛选无结果、加载失败与重试。
- 无权限或只读，不同角色的操作差异。
- 超长文本、标签溢出、零值、大数据量与操作折叠。
- 表单校验、提交中、防重复操作、提交失败保留输入、取消与成功后的去向。

无需为不适用状态虚构业务分支。静态页面可用独立区块展示；本地模拟可用切换器展示，均不代表真实服务端校验或权限控制。

跨页流程描述起点、动作、条件与结果；覆盖本次关键失败／取消路径。记录未模拟的行为，避免将“有按钮”误认为“交互已验证”。

### 可重置的引导场景（按需）

围绕待验证问题选择有解释价值的流程，例如正常提交、失败后保留输入并重试、取消后返回；不为凑场景虚构业务分支。每个场景记录业务名称、前置条件与初始模拟数据、逐步动作、应观察的界面变化及 HTML 入口。

引导步骤必须执行本地模拟动作，而非只高亮说明文字；展示当前步骤、相关业务状态和关键变化，保留自由操作以便用户尝试其他路径。场景入口、重新开始和切换场景均恢复该场景的已知初始数据、表单输入、提示、加载／错误状态和演示进度；有延迟模拟时同时取消未完成回调，防止旧结果覆盖重置后的界面。

自由操作导致引导前置条件不成立时，明确提示重新开始或回到可继续的步骤，不将错误状态标为完成。跨页场景只在本地原型页面间导航，并保证返回、重置和重新进入可重复运行；场景控件仍放在独立演示区，不改变产品页面的操作布局。

## 设计决策与开放问题

记录影响理解或实施的设计选择、理由及依据；区分已有约定和本轮建议。复用组件写名称与来源即可，不写 JSX、hook 或 API 设计。

开放问题交代缺口、影响及所需确认，关键业务规则未确定时标记草案。用户未审阅的产物如实标为待走查，不写“已批准”。

## 交付核对

核对页面和需求对应、字段／操作／状态在清单和 HTML 中一致、本地资源与导航有效。浏览器实际检查代表性页面和状态，检查目标尺寸下的可读性、遮挡、滚动与键盘焦点。

启用探索时，检查各方案入口、切换／对照及共同数据和状态是否可比；启用引导时，从初始状态完成代表性流程，再在中途、失败后及自由操作后检查重新开始和场景切换。有延迟模拟时在等待中重置，确认旧结果不再影响界面。按待验证问题记录实际观察与判断，不将作者自查、未运行场景或待用户判断写为已获验证。

已有项目对照相同视口和主题的参照页／截图，核对骨架、字体、颜色、间距、控件形态与密度；T2 特别检查保留区域是否发生无依据的改版。将差异归为需求变更、已说明的技术限制或意外偏差，修正意外偏差后交付。交付说明实际检查结果及未覆盖范围；未能对照真实页面时不宣称风格一致性已实测，本地模拟不作为生产能力验收。
