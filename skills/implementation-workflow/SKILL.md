# 实施编排工作流

多模块、跨端、复杂重构或用户要求并行时，拆分可验收任务，决定依赖顺序，实施后集成、验证并按风险审计。简单配置、文档和单文件低风险修复直接处理。

## 执行流程

### 1. 理解任务

读取项目指令文件（`AGENTS.md`、`CLAUDE.md`）、需求或 Spec、相关代码与测试、构建与测试命令、当前 git 状态。

输出简短任务理解：目标、涉及模块、约束、验收标准、暂不处理的范围。

先解决会影响验收的关键歧义，再派发。

若大型改动的主要阻力来自模块边界尚不清楚，可建议用户**开工前**单独运行 `architecture-scout`；等待候选被选定、设计获确认后再拆实施任务。不要在每次实施后自动进行全仓架构扫描。

### 2. 评估规模与风险

按可独立验收的结果拆任务；权限、金额、状态机、公共接口等变更优先安排验证与审计。小任务直接实施，不为并行而拆分。

### 3. 拆分任务

每个子任务须能独立验收；任务卡见 `references/task-card-template.md`。

拆分原则：

- 一个任务一个可验收结果
- 同一文件只由一个并行任务负责
- 共享接口、数据模型、公共类型先确定，再并行实现使用方
- 按业务结果切分，不按目录机械切分

细节见 `references/task-decomposition.md`。

### 4. 判断并行还是串行

**只有同时满足**以下条件才并行：无未解决依赖、不修改同一文件、不共享冲突状态、各有独立验收标准、并行收益大于调度与集成成本。

无法确认是否安全时**默认串行**。

判断规则与反例见 `references/parallel-execution.md`。

### 5. 派发实施子任务

需要独立上下文时，用宿主通用子 agent 工具实际派发；无派发能力则自行执行并说明。任务卡包含目标项目绝对路径、范围、已定约束、资源路径、验收标准和验证命令。子 agent 不继承主对话；传入必要方法，并要求只完成本任务。

等待实际结果，区分完成、部分完成和失败；记录改动文件、执行的验证与未解决问题。缺失或中断不能计为完成。并发名额不足时串行派发，仍可保留独立上下文。

### 6. 集成检查

并行任务返回后，主 Agent 亲自检查：

1. 改动是否落在声明范围内
2. 是否有同文件冲突或互相覆盖
3. 公共接口、命名、错误处理是否一致
4. 是否遗漏任务之间的集成代码
5. 测试是否覆盖真实集成路径
6. 子 agent 报告的验证是否实际执行且结果可信

**子 agent 的「已完成」不等于整体已完成。**

### 7. 统一验证

按项目实际工具运行单元测试、集成测试、Lint、类型检查、构建，必要时端到端测试。

记录实际执行的命令与结果。失败优先修复，不绕过、不伪造。

失败归属判断：子任务内部错误 → 重新派发原实施子任务；集成冲突 → 主 Agent 修复；测试或环境问题 → 标记为环境阻塞。

### 8. 选择性质量审计

根据变更风险读取 `references/quality-gates.md`，选择 `diff-review`、`complexity-audit` 和 `mutation-testing`；记录跳过或降级原因。派发时传目标目录、代码基线、范围和对应技能资源的绝对路径。评审与审计只报告，修复后重新运行相关验证。

覆盖率、构建和突变工具可能共享产物；输出路径冲突时串行。工具缺失或基线不可靠时如实说明，不将未验证写成通过。

### 9. 汇总

报告包含：任务拆分与完成状态、执行方式（串行/并行）、修改内容、实际验证命令与结果、质量审计的运行/跳过/降级结论、未解决问题与环境阻塞。
