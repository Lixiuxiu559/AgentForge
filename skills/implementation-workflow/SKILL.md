# 实施编排工作流

## 目标

将一个编码任务安全地推进到可验证完成：

```text
理解任务 → 评估规模与风险 → 拆分任务 → 判断并行/串行
→ 派发 implementer → 集成检查 → 统一验证
→ 按风险调用审计 agent → 汇总结果
```

你负责**编排和决策**，不把所有工作机械地交给子 agent，也不为了并行而并行。

## Agent 分工

### `implementer`

负责实际编码：

- 阅读代码
- 修改实现
- 编写或修改测试
- 运行局部验证
- 报告改动和未解决问题

### `complexity-auditor`

负责代码复杂度风险审计：

- 分析复杂度和覆盖率
- 定位高风险函数
- 建议拆分或补测试
- **只报告，不修改代码**

### `mutation-auditor`

负责测试有效性审计：

- 运行适用的突变测试
- 识别存活突变体和无覆盖代码
- 建议补充业务断言
- **只报告，不修改代码或测试**

## 阶段 0：判断任务是否适合本工作流

先判断任务类型和规模：

### 直接执行，不拆分

满足以下任一条件时，不要启动多个 agent：

- 文档、注释或简单配置修改
- 单文件、低风险、小范围修复
- 简单测试补充
- 机械版本号或格式调整
- 任务总工作量小于一个 implementer 的合理执行范围

可以由主 Agent 直接完成，或只派发一个 `implementer`。

### 使用本工作流

以下场景适合完整编排：

- 涉及多个模块或多个目录
- 前后端、多个服务或多个包同时修改
- 需要新增接口、数据模型或跨层功能
- 复杂重构
- 需要并行实现多个相互独立的任务
- 用户明确要求并行开发或质量审计

## 阶段 1：理解任务

在拆分前，先读取必要上下文：

1. 项目级指令文件：`AGENTS.md`、`CLAUDE.md` 等
2. 需求、Issue、Spec、ADR 或用户提供的验收标准
3. 相关目录、入口文件、接口和现有测试
4. 构建文件和测试命令
5. 当前 git 状态和最近相关改动

不要在不了解代码结构的情况下直接拆任务。

输出一份简短的任务理解：

- 目标
- 涉及模块
- 已知约束
- 验收标准
- 暂不处理的范围

如果需求存在会改变架构或行为的关键歧义，先向用户确认，不要把歧义扩散给多个子 agent。

## 阶段 2：评估规模与风险

### 规模

| 规模 | 特征 | 推荐执行方式 |
|---|---|---|
| small | 单文件或单模块小改动 | 主 Agent 或 1 个 implementer |
| medium | 多文件、一个明确模块 | 1 个 implementer，必要时审计 |
| large | 多模块、跨端、多个独立交付物 | 拆分后并行 implementer |

### 风险

| 风险 | 特征 | 质量门建议 |
|---|---|---|
| low | 文档、简单配置、机械修改 | 常规测试即可 |
| medium | 普通业务逻辑、接口或重构 | 建议 complexity-auditor |
| high | 权限、状态机、金额、规则引擎、核心数据流 | complexity-auditor + mutation-auditor |

高风险判断优先看**行为影响**，不要只看改动行数。

## 阶段 3：拆分任务

每个子任务必须写成可以独立执行和验收的任务卡：

```markdown
### 任务 A：<清晰的任务名称>

目标：
- 要完成什么

允许修改：
- src/feature/**
- tests/feature/**

禁止修改：
- 与本任务无关的模块
- 其他并行任务负责的文件

前置依赖：
- 无 / 依赖任务 B 的接口定义

验收标准：
- 条件 1
- 条件 2

验证命令：
- <实际命令>
```

拆分原则：

- 一个任务应有一个清晰结果，不要把半个功能交给一个 agent。
- 同一文件只能由一个并行任务负责。
- 共享接口、数据模型和公共类型必须先确定，再并行实现使用方。
- 测试任务可以和实现任务并行，前提是接口和行为契约已经明确。
- 不要按目录机械切分，要按可验收的业务结果切分。

## 阶段 4：判断并行还是串行

### 允许并行

只有同时满足以下条件才并行：

- 任务之间没有未解决的前置依赖
- 不会修改同一个文件
- 不共享会产生冲突的临时状态
- 每个任务有明确的独立验收标准
- 并行带来的收益大于调度和集成成本

典型可并行任务：

```text
后端模块 A ─┐
前端页面 B ─┼─ 并行 implementer
测试模块 C ─┘
             ↓
          主 Agent 集成
```

### 必须串行

以下情况不要并行：

- 一个任务要先定义另一个任务使用的接口
- 多个 agent 要修改同一文件
- 数据库/配置/公共类型尚未确定
- 任务之间共享同一个测试 fixture 或运行环境
- 需要先解决一个根因，再处理依赖它的错误
- 并行后的合并成本可能高于节省的时间

典型串行流程：

```text
定义接口 → 后端实现 → 前端接入 → 集成验证
```

如果无法确认是否安全并行，默认串行。

## 阶段 5：派发 implementer

派发前为每个任务提供完整、自包含的上下文：

- 任务目标
- 已确认的设计和约束
- 允许修改的文件范围
- 禁止修改的文件范围
- 验收标准
- 验证命令
- 需要返回的报告格式

Claude Code 侧使用 `implementer` 子 agent。推荐的派发意图：

```text
使用 implementer 子 agent 执行任务卡中的编码任务。
只修改允许范围内的文件，完成后运行指定验证并报告实际结果。
```

并行派发时：

- 一次只派发真正独立的任务
- 不让子 agent 自己重新拆分并修改任务边界
- 保留每个子 agent 的任务编号
- 等所有并行任务返回后再进入集成阶段

如果目标运行环境没有可用的 `implementer` 子 agent，则由主 Agent 串行执行同一任务卡，不要假装已经完成了委派。

## 阶段 6：集成检查

并行任务完成后，主 Agent 必须亲自检查：

1. 每个任务的改动是否落在声明范围内
2. 是否存在同文件冲突或互相覆盖
3. 公共接口、类型、命名和错误处理是否一致
4. 是否遗漏任务之间的集成代码
5. 测试是否覆盖真实集成路径
6. 子 agent 报告的验证是否实际执行且结果可信

不要把子 agent 的“已完成”当成整个功能已完成。

## 阶段 7：统一验证

按项目实际工具运行：

- 单元测试
- 集成测试
- Lint
- 类型检查
- 构建
- 必要的端到端测试

记录实际执行的命令和结果。失败时优先修复，不要绕过或伪造结果。

统一验证失败后，优先由主 Agent判断失败归属：

- 某个子任务内部错误 → 重新派发原 implementer 修复
- 集成冲突 → 主 Agent协调修复
- 测试或环境问题 → 明确标记为环境阻塞

## 阶段 8：选择性质量审计

不要每次都运行全部审计 agent。根据风险选择：

### 调用 `complexity-auditor`

适合：

- 修改复杂业务逻辑
- 修改大型 service、controller、parser 或状态机
- 新增大量条件分支
- 重构核心模块
- 用户明确要求复杂度审计

跳过：

- 文档和简单配置
- 简单字段修改
- 低风险样式调整

### 调用 `mutation-auditor`

适合：

- 修改权限、状态机、计费、金额、规则引擎
- 修改核心业务判断
- 新增或大幅修改测试
- 用户明确要求测试有效性审计
- 项目已有可用的突变测试工具和配置

跳过：

- 文档、配置、版本号和样式修改
- 没有可用突变测试工具的项目
- 与业务逻辑无关的简单重命名

审计 agent 只报告，不修改代码。修复由 `implementer` 执行。

## 阶段 9：最终报告

汇总：

```markdown
## 实施结果

### 任务拆分
- 任务 A：完成 / 未完成
- 任务 B：完成 / 未完成

### 执行方式
- 串行 / 并行
- 使用了哪些 implementer
- 哪些任务发生了重试

### 修改内容
- 文件和功能摘要

### 验证结果
- 实际运行的命令
- 测试、Lint、类型检查和构建结果

### 质量审计
- 是否运行 complexity-auditor
- 是否运行 mutation-auditor
- 主要发现

### 未解决问题
- 环境阻塞
- 未覆盖的范围
- 建议后续工作
```

## 核心原则

1. **并行不是默认行为**：只有独立任务才并行。
2. **任务必须有边界**：没有文件范围和验收标准，不派发并行任务。
3. **主 Agent 负责集成**：子 agent 的完成不等于整体完成。
4. **质量审计按风险调用**：不为了流程完整而运行昂贵工具。
5. **不为了并行而拆分**：调度和集成成本高于收益时直接执行。
