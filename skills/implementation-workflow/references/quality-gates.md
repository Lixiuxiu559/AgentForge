# 质量门决策

三个审计角色都是**只读报告型**，运行成本和判断维度不同。按风险选择，不要每次全跑。

## diff-review

审计三条轴：

- **Correctness**：改动是否引入可构造的 bug
- **Standards**：是否符合仓库规范和审计基线
- **Spec**：是否忠实实现需求

### 建议调用

- 公共 API、跨模块契约、权限、核心状态机
- 业务逻辑或错误处理发生变化
- 大型重构、多个 implementer 参与的集成
- 提交前需要确认改动符合需求与项目约定
- 用户明确要求代码评审

### 跳过

- 文档、单纯配置、版本号、样式
- 与业务行为无关的机械重命名
- 单文件低风险修改，且已有其他可靠验证

### 前置条件

- 有可比较的 git 基线和非空改动
- 没有 spec 时仍可运行 Correctness + Standards，但必须报告 Spec 轴降级
- 评审不依赖 Claude Code 内置 `/code-review`、DSH 专属命令或其他宿主能力

## complexity-auditor

审计复杂度与覆盖率风险，回答「这段代码是否难以安全修改」。

### 建议调用

- 修改复杂业务逻辑
- 修改大型 service、controller、parser、状态机
- 新增大量条件分支
- 重构核心模块
- implementer 报告中出现明显深层嵌套
- 变更规模较大
- 用户明确要求复杂度审计

### 跳过

- 文档、注释、简单配置
- 简单字段修改
- 低风险样式或文案调整
- 单文件小改动

### 前置条件

项目存在可用的复杂度或覆盖率工具，或可从现有报告推导。缺失时应说明降级等级（`complexity-only`、`file-level-risk`、`unavailable`），不要伪造 CRAP 值。

## mutation-auditor

审计测试有效性，回答「现有测试是否真的能发现错误」。

### 建议调用

- 修改权限、状态机、金额、计费、规则引擎
- 修改核心业务判断与边界条件
- 新增或大幅修改测试
- 用户明确要求验证测试有效性
- 项目已有可用的突变测试工具和配置

### 跳过

- 文档、配置、版本号、样式修改
- 纯重命名或机械调整
- 项目没有可用的突变测试工具
- 变更与业务逻辑无关

### 前置条件

项目存在可用的突变测试工具链（PIT / mutmut / go-mutesting / Stryker）及配置。缺失时明确报告，不要自动安装依赖。

## 组合建议

| 变更类型 | diff-review | complexity-auditor | mutation-auditor |
|---|---|---|---|
| 文档 / 配置 / 样式 | 跳过或检查契约一致性 | 跳过 | 跳过 |
| 简单字段或小修复 | 通常跳过 | 跳过 | 跳过 |
| 普通业务逻辑 | 建议运行 | 建议运行 | 通常跳过 |
| 复杂逻辑 / 大型重构 | 建议运行 | 建议运行 | 视测试情况 |
| 权限 / 状态机 / 金额 / 规则 | 建议运行 | 建议运行 | 建议运行 |
| 公共 API / 跨模块契约 | 建议运行 | 视复杂度 | 视测试情况 |
| 测试专项 | 按需 | 可选 | 有工具时优先运行 |

## 调用顺序

高风险变更建议：

```text
implementer 完成并统一验证通过
        ↓
diff-review             ← 正确性 / 规范 / 需求
        ↓
complexity-auditor      ← 结构复杂度风险
        ↓
mutation-auditor        ← 测试有效性
        ↓
implementer 修复（如有需要）
        ↓
重新验证相关部分
```

并非每次需要完整顺序，按变更类型表选择即可。

## 结果处理

- 三个审计角色**只报告，不修改代码**
- 修复由 `implementer` 执行
- 发现高危项时回到实施阶段修复并重新验证
- 跳过某个审计时，最终报告必须说明原因
- 不要求反复执行到零 finding；评审与审计都没有收敛保证

## 不要做的事

- 不要为了流程完整而运行昂贵工具
- 不要因为审计报告为空就认为质量一定达标
- 不要用审计结果替代统一验证
- 不要让审计角色直接改代码
- 不要把 Claude Code 内置 `/code-review` 当成必需依赖
