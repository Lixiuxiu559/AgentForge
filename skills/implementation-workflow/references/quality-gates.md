# 质量门决策

两个审计 agent 都是**只读报告型**，且运行成本不同。按风险选择，不要每次全跑。

## complexity-auditor

审计复杂度与覆盖率风险，回答「这段代码是否难以安全修改」。

### 建议调用

- 修改复杂业务逻辑
- 修改大型 service、controller、parser、状态机
- 新增大量条件分支
- 重构核心模块
- implementer 报告中出现明显深层嵌套
- 变更规模较大
- 用户明确要求复杂度审计

### 跳过

- 文档、注释、简单配置
- 简单字段修改
- 低风险样式或文案调整
- 单文件小改动

### 前置条件

项目存在可用的复杂度或覆盖率工具，或可从现有报告推导。缺失时应说明降级等级（`complexity-only`、`file-level-risk`、`unavailable`），不要伪造 CRAP 值。

## mutation-auditor

审计测试有效性，回答「现有测试是否真的能发现错误」。

### 建议调用

- 修改权限、状态机、金额、计费、规则引擎
- 修改核心业务判断与边界条件
- 新增或大幅修改测试
- 用户明确要求验证测试有效性
- 项目已有可用的突变测试工具与配置

### 跳过

- 文档、配置、版本号、样式修改
- 纯重命名或机械调整
- 项目没有可用的突变测试工具
- 变更与业务逻辑无关

### 前置条件

项目存在可用的突变测试工具链（PIT / mutmut / go-mutesting / Stryker）及配置。缺失时明确报告，不要自动安装依赖。

## 组合建议

| 变更类型 | complexity-auditor | mutation-auditor |
|---|---|---|
| 文档 / 配置 / 样式 | 跳过 | 跳过 |
| 简单字段或小修复 | 跳过 | 跳过 |
| 普通业务逻辑 | 建议运行 | 通常跳过 |
| 复杂逻辑 / 大型重构 | 建议运行 | 视测试情况 |
| 权限 / 状态机 / 金额 / 规则 | 建议运行 | 建议运行 |
| 测试专项 | 可选 | 优先运行 |

## 调用顺序

高风险变更建议：

```text
implementer 完成并统一验证通过
        ↓
complexity-auditor   ← 先看结构风险
        ↓
mutation-auditor     ← 再看测试有效性
        ↓
implementer 修复（如有需要）
        ↓
重新验证
```

先复杂度后突变的原因：结构风险会改变需要补测的位置；顺序颠倒容易产生返工。

## 结果处理

- 两个审计 agent **只报告，不修改代码**
- 修复由 `implementer` 执行
- 若审计发现高危项，回到实施阶段修复并重新验证
- 若选择跳过某个审计，**在最终报告中说明跳过原因**，不要静默省略

## 不要做的事

- 不要为了流程完整而运行昂贵工具
- 不要因为审计报告为空就认为质量一定达标
- 不要用审计结果替代统一验证
- 不要让审计 agent 直接改代码
