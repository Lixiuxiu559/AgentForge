# 任务拆分与依赖识别

## 拆分目标

拆分的目的是让每个子任务**可以独立执行、独立验收、独立回滚**，而不是把工作切成看起来很多的碎片。

一个合格的子任务：

- 有一个清晰、可验证的结果
- 有明确的文件边界
- 不依赖其他并行任务的中间产物
- 能独立运行验证命令

## 拆分维度

### 按业务结果拆

优先按「用户能验收的结果」拆：

```text
✅ 实现导出接口并返回正确结构
✅ 前端页面接入导出按钮并处理错误
✅ 为导出逻辑补充边界测试
```

不要按技术层次机械拆：

```text
❌ 写 service
❌ 写 controller
❌ 写 DTO
```

后者每个任务都无法单独验收。

### 按文件边界拆

同一文件只能由一个并行任务负责。若两个任务都需要改同一个文件，说明：

- 拆分粒度太细，应该合并
- 或存在未确定的公共抽象，应先抽取

### 按依赖顺序拆

先确定公共契约，再并行实现使用方：

```text
1. 定义接口 / 数据模型 / 公共类型
        ↓
2. 并行：后端实现 ┐
        前端接入 ┼─ 各自独立
        测试补充 ┘
        ↓
3. 集成验证
```

## 依赖识别

拆分后逐对检查任务关系，任一项为「是」则存在依赖，不能并行：

| 检查项 | 说明 |
|---|---|
| 文件重叠 | 两个任务修改同一文件 |
| 契约依赖 | 一个任务使用另一个任务尚未定义的接口或类型 |
| 数据依赖 | 一个任务的输入是另一个任务的输出 |
| 状态共享 | 共享测试 fixture、数据库、临时环境或全局配置 |
| 顺序语义 | 必须先解决根因才能处理依赖它的现象 |
| 验证耦合 | 两个任务必须一起才能运行验证 |

## 文件边界写法

每个任务显式声明：

```markdown
允许修改：
- src/feature/**

禁止修改：
- 其他并行任务负责的目录
- 公共配置与依赖清单
- 与本任务无关的模块
```

边界要写成**路径 glob**，不要写「相关文件」这类模糊表述。

## 需要谨慎的情况

### 数据库迁移

迁移通常影响多个使用方，建议单独串行执行，不要与其他改动并行。

### 依赖清单与锁文件

`package.json`、`pom.xml`、`go.mod`、锁文件属于高冲突文件，同一时间只允许一个任务修改。

### 公共类型与接口

公共类型的变更会波及所有使用方。先单独完成并验证，再并行推进使用方。

### 测试 fixture

多个任务共享 fixture 时，fixture 变更应先单独完成。

## 拆分反例

```text
❌ 三个 agent 同时改同一个 service 文件
❌ 一个任务「实现整个功能」，没有边界
❌ 一个任务「顺便重构一下无关代码」
❌ 拆分后每个任务都无法单独验证
❌ 任务之间需要频繁互相等待
```

## 拆分结果检查

拆分完成后自问：

1. 每个任务能否单独运行验证命令？
2. 是否存在任意两个任务会修改同一文件？
3. 是否有任务依赖另一个任务尚未产出的接口？
4. 并行收益是否明显大于调度与集成成本？
5. 如果全部并行，集成时需要解决多少冲突？

任何一项答案不理想，就调整拆分方式或改为串行。
