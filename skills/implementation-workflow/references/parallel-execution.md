# 并行执行规则

## 允许并行的条件

必须**同时**满足：

1. 任务之间没有未解决的前置依赖
2. 不会修改同一文件
3. 不共享会产生冲突的临时状态
4. 每个任务有明确的独立验收标准
5. 并行收益大于调度与集成成本

典型可并行结构：

```text
后端模块 A ─┐
前端页面 B ─┼─ 并行 implementer
测试模块 C ─┘
             ↓
        主 Agent 集成
```

## 必须串行的情况

| 情况 | 原因 |
|---|---|
| 需要先定义接口再实现使用方 | 契约未定，并行会产生不一致实现 |
| 多个任务修改同一文件 | 会互相覆盖 |
| 数据库迁移、公共类型、依赖清单 | 高冲突，且影响面广 |
| 共享测试 fixture 或运行环境 | 结果互相干扰 |
| 需要先定位根因再修依赖现象 | 顺序语义不可颠倒 |
| 集成成本可能高于节省的时间 | 并行无收益 |

典型串行结构：

```text
定义接口 → 后端实现 → 前端接入 → 集成验证
```

**无法确认是否安全并行时，默认串行。**

## 不建议并行的信号

- 需要在派发前给子 agent 写很长的共享上下文
- 子 agent 之间需要互相等待或通信
- 任务边界只能靠「大概不冲突」判断
- 同一份 spec 需要被多个 agent 重复解读且解读可能不同
- 需要并行 agent 共享同一份临时数据

出现任一信号，改为串行或重新拆分。

## 派发要求

每个并行任务必须携带：

- 任务编号与名称
- 目标
- 已确认的设计与约束
- 允许修改的路径
- 禁止修改的路径
- 验收标准
- 验证命令
- 返回格式

子 agent **不得自行改写任务边界**，不得顺手重构无关代码。

## 集成检查清单

并行任务全部返回后，主 Agent 逐项确认：

- [ ] 每个任务的改动都落在声明范围内
- [ ] 没有同文件冲突或互相覆盖
- [ ] 公共接口、类型、命名、错误处理一致
- [ ] 任务之间的集成代码已补齐
- [ ] 测试覆盖真实集成路径，而非各自孤立路径
- [ ] 子 agent 报告的验证确实执行过且结果可信
- [ ] 没有遗留调试代码、临时代码或无意义 TODO

## 集成失败的处理

| 失败类型 | 处理方式 |
|---|---|
| 子任务内部错误 | 重新派发原 implementer 修复该任务 |
| 任务间接口不一致 | 主 Agent 确定统一契约后修复 |
| 集成冲突 | 主 Agent 直接解决，不再并行 |
| 测试或环境问题 | 标记为环境阻塞，明确说明 |
| 验收标准未达成 | 回到拆分阶段重新定义任务 |

## 成本判断

并行不是免费的，调度成本包括：

- 任务分析与拆分
- 任务卡编写
- 子 agent 启动与上下文成本
- 结果整理
- 冲突解决与集成验证

当任务总量小于一个 implementer 的合理执行范围时，直接串行更快。
