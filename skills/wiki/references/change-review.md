# 变更影响与知识同步

## 确定比较对象

使用 `references/tools.md` 的 `changes` 命令收集材料。提交前检查使用 `staged`；检查尚未暂存的改动使用 `worktree`；分支或合并请求比较使用 `range` 并给出明确 base 和 head。不能用干净工作区替代已提交分支的比较，也不能把工作区文件当作暂存版本。

若用户要求“当前所有未提交改动”，分别采集 staged 与 worktree，并保留两个范围。二者可能相互抵消，不能只比较最终工作区与 HEAD。记录实际解析出的提交基线；工作区或索引在分析期间改变时，重新采集相关范围。

## 关联知识

可选配置提供源文件到模块、文档的映射。它只产生候选，不证明语义影响。删除和重命名同时检查旧路径、新路径及原有引用。

没有配置或映射不完整时，按项目索引、code-map、已有注解和调用关系定位知识；项目已有 CodeGraph 且要求优先使用时遵循约定。不要为了本技能自动建立索引。无法定位的文件保留为 unmapped，说明是尚未关联还是确实与知识范围无关；不静默丢弃。

按 `references/content-verification.md` 核对重要结论的证据范围、实际配置生效链与本页来源映射；新增或移动的内容也应反查依据，不能因其他模块覆盖了文件就默认该页面会失效。

脚本收集文件变化信息后，还需读取所选范围的实际 diff、对应版本的内容、相关 Wiki 和需求或契约。脚本不提供完整语义审查，输出里没有业务差异不代表不存在影响。

## 判断后再更新

| 证据情况 | 处理 |
|---|---|
| 已确认变更已实现，Wiki 仍描述旧行为 | 在授权范围内更新，记录基线和适用状态 |
| 代码违反仍有效的契约 | 报告实现问题，不改 Wiki 来掩盖差异 |
| 代码变化但业务预期不明 | 标记实现观察与待确认项，不推导新业务规则 |
| 实现尚未发布 | 区分实现版本与部署状态，不宣称已对用户生效 |
| 仅内部重构 | 检查代码映射或依赖是否变化，不凭文件改动重写业务规则 |
| 来源缺失、比较失败、材料未完整读取 | 报告 partial 或 error 及缺口，不给出完整同步结论 |

同步建议至少包含受影响文档、具体变化、证据和未解决问题。用户要求直接更新时据此完成局部修改和验证；仅要求评估时交付建议。没有必要改动时明确说明，不制造变更。

项目已配置新鲜度记录时，开发收尾按 `references/freshness.md` 保存本次实际复核的 updated、no-change 或 blocked 声明及证据。先完成核对再记快照，不把缺少 Markdown 变更当作未同步，也不把随便修改一句文档当作已同步。复核后运行结构检查和对应候选的 gate；索引、工作区和提交树不得混用。
