# 初始化与增量维护

## 选择知识范围

优先读取项目已有索引、需求或契约、相关代码入口及测试。大型项目先覆盖用户指定模块和公共概念，不以扫描了少量代码为由声称已覆盖全项目。

初始化前按 `references/templates.md` 选择骨架：项目已经有目录、章节、元数据约定时优先沿用；无约定时采用默认 small 或 modular。默认模板位于技能自身的 `assets/templates/`，只取本次所需文档类型，按证据填充后保存到目标项目，并运行所选规范的检查。不要整目录复制所有模板或将模板占位符当作完成的知识。

按需要组织四类信息：

- 概览：用途、领域概念、参与者、主要流程和状态。
- 规则：约束、权限、计算方式、异常和业务边界。
- 代码映射：实现入口、职责、代码与概念的对应关系。
- 依赖：上下游、接口契约、数据来源和相关决策。

这些信息可以合并、拆分或裁剪。角色名称、规则编号及模块划分来自项目，不从模板引入。没有依赖、权限或业务公式时无需人为补齐。代码映射可使用项目已有链接或注解；没有注解时不要求改源码才能建立 Wiki。

## 事实与状态

将不同依据分开表述。例如：

```text
规则：重复请求应返回同一结果。
来源：docs/contracts/orders.md 的幂等约定。
适用范围：订单创建接口；契约版本 v2。
实现观察：src/orders.ts 在 commit abc123 中只有进程内缓存。
核验时间：2026-10-27（已对照上述契约与代码）。
待确认：跨进程幂等是否由网关提供；未核实生产部署版本。
```

已有项目可用表格、邻近注释或既有元数据承载这些信息，不要求新增统一 frontmatter。默认模板使用“文档信息”表及“依据与核验”“待确认项”章节，结构由 `assets/schema.json` 定义；不能为绕过检查将未核验内容标记为已核验。源码链接及提交号必须真实；不能用示例提交号填入交付物。文档来源是已批准契约还是草案、测试反映预期还是仅反映现状，应明确标出。

## 增量写入

1. 先读现有内容和相关未提交改动，确定需要调整的事实及来源。
   已配置新鲜度记录时，先按 `references/freshness.md` 检查本次模块的来源和文档是否仍匹配已复核快照；失效或未知时回到来源，不直接引用旧结论。
2. 仅修改受影响段落、链接和必要索引；保留人工解释、设计理由、历史决策及仍有效的内容。
3. 冲突未解决时记录双方依据及影响，不自动将其中一方覆盖成事实。初始化也不把猜测写成正式规则。
4. 修改后检查局部 diff、引用目标和相关术语；只更新实际核验过的范围及时间。

相同输入与相同证据再次执行应无需修改，不为“同步”重排全文、重写措辞或刷新日期。被中断后重新读取当前文件和 diff，从已完成内容继续，避免按旧上下文覆盖人工新增内容。

首次初始化至少有可用入口、所覆盖范围、已知事实和开放问题。资料不足时交付明确标注范围的草稿，不以空章节或未经核实的说明制造完整感。保存到目标项目；目录和文件名依项目约定决定。

项目选择持续维护新鲜度时，在初始化完成实际核对后建立首份复核记录；没有核实的模块保留 unknown 或 blocked，不为了初始全绿补造记录。后续维护只复核必要范围，配置策略或来源覆盖变化后依新范围重新核对。
