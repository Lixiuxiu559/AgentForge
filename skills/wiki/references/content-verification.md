# 正文、证据与来源覆盖核对

初始化和维护时对影响理解或操作的重要结论执行；不要求为每句话新增表格、扫描全部调用图或访问线上。保留项目原结构，利用现有来源链接、邻近说明和核验记录交代结果。

## 执行顺序与完成判据

优先按 SKILL.md 的单页流程执行：用 mapping --document 取得带行号核对包，每页完成追源、原句修改和读回，再处理下一页。长篇参考不是额外待办清单；关键执行顺序以入口三步为准。


对本次选定页面，先读全文而非只看 diff 或“待确认项”。列出会影响理解、操作或交付判断的重要断言：摘要/表格中的确定结论、路径/配置/返回行为、发布/回退状态，以及其引用的约定。没有改变措辞的旧断言也在本次核对范围内；局部请求只检查相关结论及其重复位置，不自动审计全仓。

逐项完成“原断言 → 原始来源及定位 → 来源实际支持的范围 → 正文处置 → 本页模块来源覆盖”。在工作记录或交付说明保留关键修正与具体缺口即可，不强制新建永久台账、字段或统一表格。复核记录的 evidence 路径列表不能替代这项推理。

1. 先追到决定行为的源码/契约或有时间范围的运行记录，再判断原断言正确、需收窄、需修正或仍未知。命名相似、注释、整篇分类标签及脚本 passed 都不足以完成这一步。
2. 修改真正作出断言的位置，包括摘要、表格单元格和操作步骤；只在末尾补“静态观察”“仅供参考”，却保留相反的确定性正文，不算修正。用户提供了上轮问题时逐项标明本次已修正、证据支持无需改或尚未解决，不能只归位待确认项就结束。
3. 反查每项修正和保留的重要断言所依赖的本页 sources，处理缺口，再核对重复位置及有效来源中的冲突。
4. 读回修改后的全文与实际 diff，完成对应检查，最后才保存 review。交付至少给出实际核对的代表断言及来源定位、映射增补/共享理由、剩余缺口和实际命令结果；未核对的部分不以“全 fresh”代称已完成。

## 先核对结论的适用范围

逐项问：描述哪个对象、环境、版本和时间？来源实际证明了什么？结论有没有把“部分”扩大为“全部”，或把观察变成约定？

- 单平台清单版本只能证明该次读到的声明，不能独立证明所有平台资产、下载可用性、签名或完整同步。
- 某渠道只保留最近若干版本，不等于项目全部分发渠道或用户本地都无法取得更早版本；回退还取决于数据兼容性。清理策略须写清作用对象，不从渠道策略推导产品承诺。
- 文件或配置存在、Secret 名称存在，不证明实际执行成功、配置有效或当前健康。缺少证据时收窄结论，不自动新增验证、审计或部署任务。
- 建议、通用经验和推断不能标为项目约定；只有有效项目来源或明确决策支持的规则才用约定，说明来源。材料互相冲突时保留双方效力及影响。

## 操作性描述沿实际生效链取证

涉及路径、端口、配置和恢复时，区分声明默认值、调用方覆盖、环境覆盖和实际观测，不只读取被调用函数的默认值。

例如工作目录、应用数据根和数据库路径是不同概念：追到启动调用方是否显式设置 cwd、子进程继承行为、配置文件相对哪个目录读取、数据库是否被绝对路径环境变量覆盖。正式/Dev/命令行或不同平台可能不同；未明确设置时写继承或未知，不根据用户数据目录猜测 cwd。若本次只整理通用知识、未要求确认具体实例或执行操作，未观测的实例取值作为观察限制及操作前定位条件，不自动生成长期待确认任务。

备份和排障说明按适用环境给出准确路径或可核实的定位方法。不同组件有同名配置文件时，分别追溯读写者和解析基准；应用壳设置、后端配置、环境覆盖及外部客户端设置不能合称一个 config.json。相对数据库默认值只在明确启动目录且无覆盖时成立，不写成所有命令行实例的固定绝对位置。相对路径须说明解析基准；涉及多个数据库、配置和外部客户端文件时分别说明范围。数据备份、应用替换和数据库恢复不能混同，未经验证的建议保留状态及风险，不据此读取用户实际凭据或运行危险命令。

## 从正文反查来源映射

有新鲜度配置时，以“知识页 → 重要结论 → 实际来源 → 所属模块映射”反向核对，而不只运行 mapping 后看有没有未映射仓库文件。

1. 找到支撑结论的真实来源：例如环境页使用的包版本与工作流，运维页使用的错误分类、配置及启动装配。使用已有调用/导入信息定位必要文件，不把整个目录自动算作所有结论的来源。
2. 核对这些来源是否进入该知识页对应模块的 sources，页面是否进入 docs；不能因文件属于别的模块，就假定本页也会失效。
3. 本次引入或发现的必要来源缺口，在授权维护范围补齐稳定文件/合理目录，并说明共享原因。只是“相关”或导航链接不一定构成语义依据，不为全绿扩大到整个仓库。
4. 外部平台、历史观测或无法本地跟踪的来源明确说明检测范围；过时的线上状态不会因仓库 fresh 自动变成当前结论。缺口无法补齐时具体说明，不默默宣称覆盖完整。

配置参与指纹比较不等于配置文件已具备变更路径归属。采用 gate 时，首次创建或修改 Wiki 配置也要关联到实际负责知识入口/维护约定的模块，说明它定义文档和来源范围；不能通过排除配置或扩大全仓来源来消除提示。

配置变化使原记录失效时，逐模块核对映射差异、旧记录的来源/文档快照及本次语义影响。对映射和内容均未变的模块，可据具体比较保留原核验范围并作 no-change；有变化的模块按新范围复核。不能因全局配置指纹变化就冒充全库重新核验，也不能为避免复核省略必要来源。

新增页、拆页或归位内容后重新检查映射；只把信息移动到“依据与核验”不免除依赖跟踪。配置变化后按新范围实际复核，不能用旧指纹或机械批量签认过门。若本次调整了来源映射，选择关键新增来源在隔离副本验证“目标页所属模块 stale → 字节/模式还原后 fresh”；既有自动化已验证同等关联时可复用并说明，无法演练则明确仅完成静态映射核对。

## 跨页一致性与交付

核对入口摘要、元数据、正文、表格、步骤与相关页面：一页写已观察而另一页仍写未观察、表格声称确定而说明承认未知，均需查明并局部校准。在所选范围搜索同一事实的重复断言及相反表述，不限于这次改动的 Wiki 行，也检查直接作为依据的现行产品/架构/发布材料。先比较各句的对象、条件、时间和证据效力；配置前提不等于“当前未配置”，较早的未验证记录也不否定后续观察，不因搜索到反义词就制造冲突。源文档一处已交付、一处仍待实施时，交代双方位置、基线与对当前结论的影响；只读或范围外来源不擅自改写，不能一面称来源已统一，一面略过冲突。能由明确基线识别的旧状态注明过时，不把所有文档疏漏升级成需产品重新决策。优先链接公共事实，避免重复复制细节后各自漂移；保留历史时间与实际核验范围，不通过统一措辞制造新事实。当前源码核验基线与沿用的历史运行观察分开标记；更新了当前实现结论却继续把整页绑定到旧源码基线，也会误导读者。

check 检查结构和支持的链接；mapping 报告路径覆盖；freshness 检查配置覆盖内容与复核声明指纹是否一致；gate 检查候选同步及变更覆盖。它们都不能确认正文语义与实现一致。 读回时也核对正文对这些工具能力的描述；不能在工具说明处承认 semantic: not_run，却在环境页或总结中写成“仓库检查已证明代码一致”。语义核对由 Agent 对照来源承担，明确哪些是本次查证、哪些仅继承历史观察、哪些未验证。

按风险选择验证：规范/模板变化用实际产物前向验证；重要映射变更可在隔离副本中修改已映射来源，确认对应知识模块变 stale、还原后恢复，避免把真实项目变更或刷新记录当作测试。只报告实际检查结果与剩余缺口，不为文档检查新增长期运行服务。
