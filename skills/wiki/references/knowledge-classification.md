# 知识分类与证据表达

对影响理解、修改或验收的重要条目，分别回答：它描述什么、依据是什么、做过什么核对、对哪里成立。普通说明不必逐句套表；分类可以放在邻近文字、表格列或项目已有元数据中。

## 信息类型

| 类型 | 可以表达什么 | 依据与限制 |
|---|---|---|
| 预期与约定 | 项目要求或已明确的目标行为 | 用户明确决策、有效接口契约、设计决策、需求说明或项目认定的其他来源；写明来源效力与适用范围 |
| 实现观察 | 指定版本代码实际表达的行为 | 源码、配置与调用路径；静态核对只支持已读范围，常量存在不代表所有入口均使用它 |
| 运行验证 | 在具体条件下实际观察到的结果 | 测试、命令、受控环境记录；标明输入、环境、版本与结果，不把一个样例扩大为所有路径成立 |
| 推断 | 根据已有事实提出的解释 | 明示推理依据、未证实条件及反证；不能放入有效约定冒充项目决策 |

未知与冲突是条目的状态，不是必须再创建一套模块。没有独立预期来源时，可以准确交付实现观察并记录“目标行为尚未确认”；代码与注释冲突时，核对调用路径、历史和有效契约后解释差异，仍无法判断的部分保留双方依据。

没有正式 PRD 不等于项目治理缺陷。小项目可以通过 Issue、用户决策、接口帮助或其他有效材料明确预期，不强制存在产品经理或审批角色。Wiki 负责查证和表达；存在实质业务选择时由项目决定，不能从当前代码推导应有行为。

## 查证与适用范围

重要结论至少保留：

- 可定位的来源：文件与相关符号、决策记录或受控运行记录。
- 实际核验方式：静态阅读、调用链核对、已有测试结果或本次实际执行；未执行的方式明确写未执行。
- 适用范围：相关模块、接口、提交或版本；运行观察另注明环境。
- 未确认条件或差异：只标出影响这条结论的缺口，不因一条未知降低整库所有事实的效力。

例如，下面两项可以同时成立：

```text
类型：实现观察
结论：当前实现将重复请求结果保存在进程内。
依据：已读取的缓存实现与调用入口，提交基线以实际文件记录。
核验方式：静态调用链核对；未执行跨进程验证。
待确认：若项目已承诺多进程幂等，需要核实是否由其他层处理；没有该承诺时只说明已读实现边界。

类型：预期与约定
结论：重复请求应返回同一业务结果。
依据：项目现有接口契约，注明实际版本及来源位置。
差异：现有实现观察尚不足以证明跨进程场景符合该约定。
```

示例不能作为项目事实复制；交付时必须替换为真实来源，无法取得时明确写未知。

建议或通用经验本身不是项目约定；观察范围限定到具体对象、平台与时间，不将单项清单或一个成功样例扩大为全环境结论。重要正文的查证与反向映射方法见 `references/content-verification.md`。

## 待确认项的准入与归位

“待确认项”收录会改变本文必要结论、当前范围内的决策或具体操作的未决问题，不是所有“不知道”“没验证”“以后可能做”的合集。逐项判断：

- 与当前文档及项目实际承诺或本次操作有关，能说清不解决会影响什么。
- 合理查阅已有来源后仍存在具体未知或有效依据冲突；可直接查明的先核实，不把取证工作转交读者。
- 问题可具体回答或验证，说明已知依据、剩余缺口及下一步查证方式；不凭空增加审批角色、负责人或截止日期。

没有符合项时写“无已知待确认项”，不要在这句话后继续堆放边界、免责声明或未执行清单；将其归回相关正文/核验范围。文档需要这个章节，不意味着必须制造问题；也不以问题数量减少为验收目标。待确认项存在不等于整个模块必须 blocked：按来源范围准确记录局部问题，只有它影响本次必要结论且项目策略确实要求阻断时才保存 blocked；不得为了保留一项编辑冲突就阻断仍可使用的实现知识。

| 内容性质 | 应放的位置 |
|---|---|
| 已明确不支持、已选定的单进程/本地边界 | 用途与边界、能力限制或架构说明；不要求设计范围外能力 |
| 本次未运行测试、未访问生产、未演练恢复 | 依据与核验、相关操作步骤的验证限制；不自动生成后续验证任务 |
| 尚未提出需求的监控、分支保护、未来平台支持 | 不自行创建待办；用户已有规划时链接既有规划/backlog，当前页面说明范围即可 |
| 某次未推送提交、临时端口或本机会话状态 | 对理解有用时放带时间和基线的观察/验证记录；不作为长期项目缺口重复列出 |
| 某结论缺少来源或业务依据相互冲突，且影响当前范围 | 局部保留未知/冲突；满足上述准入条件时进入待确认项 |

例如，本地单进程应用的“多实例一致性未设计”是已知边界；若项目明确要求多实例部署，而请求去重是否跨实例成立尚不明确，则是会影响部署决策的待确认问题。没有遥测的桌面应用无法统计其他用户机器健康，属于观测范围，不自动要求新增遥测。

未验证不等于无需警示：恢复方案未演练，应在恢复步骤旁显著保留，不能通过删掉待确认项把它说成可可靠恢复；只有本次要求验收恢复能力，或该缺口妨碍当前必要操作时，才额外列出具体待确认问题。未知的本机目录不因“源码里没找到”就进入问题清单；确实影响备份/迁移/删除安全时再定位来源，不擅自读取凭据或私人数据。

维护时将错放信息迁回合适位置，合并重复表述，并核对入口摘要与各页正文是否仍一致；不是把免责声明换个章节批量堆放。保留历史证据的时间范围，不把旧会话叙述更新成当前观察。问题被解决、项目选择不再做或已成为明确限制后，更新正文结论并退出待确认项，必要时链接原决策。

准入判断由 Agent 按实际语义负责；check 只验证章节和内容结构，不能凭关键词自动判定问题是否必要，也不证明语义通过。

## 文档摘要与条目结论

默认文档的“事实状态”是查证概况。部分核验文档可以包含已有充分依据的约定，也可以包含未运行验证的实现观察；这些条目分别标明，不能用整篇标签解释错放的结论。

默认规则模板分为“预期与约定”“实现观察”“运行验证”，未知与差异保留在相应条目，只有符合准入规则的问题才列入“待确认项”。没有预期或运行证据时写明具体缺口，不为填满章节编造批准记录或测试结果。既有项目保留自己的组织方式，补足等价的信息即可。

fresh 表示配置覆盖的内容仍匹配复核快照，与业务正确性、运行验证及已部署状态分别记录。开发分支实现、dev 测试通过或本地版本号都不能证明生产已生效；本次目标不涉及上线时，部署未知不会阻止项目知识交付。

semantic: not_run 只说明确定性脚本未做自动语义判定。Agent 仍须核对所写文字是否受来源支持，交付核对范围与局部差异；不能把结构通过当作内容正确，也不能用该字段回避本次已要求的内容核验。
