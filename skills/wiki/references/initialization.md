# 初始化交付与模块来源设计

先复用项目已有入口、约定和材料，再根据用户目标确定范围和交付程度。明确请求直接执行；缺口只在会改变本次交付或必要业务结论时澄清，不要求先完成产品治理或发布流程改造。

## 选择实际交付程度

| 目标 | 合格交付 |
|---|---|
| 一次性项目文档 | 可阅读入口、知识内容、来源、覆盖范围与未知项，并完成适用的结构/链接核对 |
| 可持续维护的 Wiki | 再提供可复用的模块边界、来源映射和维护说明，明确新鲜度是否启用、原因及现有替代机制 |
| 持续同步 | 再建立已核实范围的首份复核记录，明确读取前与开发收尾的触发方式、命令和实际验证结果 |
| 强制检查门 | 再明确项目选择的策略、候选范围和例外处理，并按授权完成实际接入验证 |

从用户表达和已有项目机制判断适当程度并说明，不把每个请求都降为一次性说明，也不默默增加 CI、部署权限或新的审批门。“持续维护”尚未启用来源指纹检测时必须明确，不能声称已有持续同步闭环。

技能本身不常驻运行，也不监听文件或定时更新。持续同步须将读取前、开发收尾的触发约定放入项目实际会使用的指令或维护流程，说明由谁执行、运行哪些命令；只安装技能、创建配置或留下命令示例，不等于流程已接入。自动运行只在项目实际接入的 CI/hook/调度触发时发生，不据“持续同步”这个名称假定存在自动化。

持续同步的真实复核记录可以覆盖已核对的实现观察及明确记录的未知项，不必等待所有业务预期拍板。未知不自动等于 blocked；只有仍未解决的冲突影响本次必要结论、且项目策略需要阻断时，才记录对应的阻断范围。不要为取得初始全绿签认尚未读过的来源。

强制门以实际范围为准：本地命令、CI 接入、服务端必需状态是不同结果。用户要求不可绕过的服务端门时，只增加工作流文件仍不能称完成；缺少权限或实际证据时说明尚未完成。已有项目要求的强制策略不因担心噪声而自行降级。

## 检查知识面的完整性

初始化先评估项目概览、业务/能力、架构、部署环境、运维排障五个知识面。在入口的覆盖说明中逐项记录已覆盖、部分覆盖、未覆盖或不适用及理由；不要求固定五个目录。用户限定某个业务主题时只评估相关范围，不擅自扩展到全项目运维。

技术项目同样需要说明组件与依赖、宿主或运行前提、安装/发布、验证与恢复边界；CLI、库、技能仓库没有自营生产服务时，可以说明不适用，不虚构 dev/prod、监控平台或数据库。沿用项目已有架构、发布和 runbook，入口链接并核对即可，不为补目录重复复制。取证和环境状态表达见 `references/system-knowledge.md`，专用模板及显式类型检查见 `references/templates.md`。

## 按知识边界划模块

业务应用优先围绕读者的问题、业务规则、流程和生命周期组织。库、CLI、基础设施或技能仓库可以围绕对外能力、技术概念和使用边界组织；不强加订单、产品角色或 Java 包模型。

判断一个主题是否值得单独成模块：它是否有独立且有用的规则或状态、读者是否经常单独理解或修改它、与相邻主题是否存在稳定边界。没有独立知识价值的小主题保留为章节；同一机制的参数差异可合并描述。业务名称不同并不足以证明必须拆分。

源码目录用于检验边界和定位实现。一项业务能力可能横跨后端、前端、数据库与测试；一个共享实现也可能关联多个 Wiki 模块。模块概览应说明负责什么、与谁相邻以及共享什么，不要求知识模块与目录一一对应。

例如，排位赛与娱乐赛若有独立报名、计分和结算规则，可分别组织；若主要是同一比赛机制的参数差异，可以合并为“比赛”的不同模式。共同轮换实现同时映射到相关模块；只有轮换自身有独立解释价值时才建立公共能力页，不为减少 stale 数量制造新模块。

大型项目可分批生成，但保留用户要求的完整范围。先建立覆盖清单，标明各模块已完成、仅有初稿、尚未核对或未覆盖，逐批推进；不能只完成少量高价值模块就称全项目初始化完成。

## 建立并核对来源映射

1. 从已选模块定位真实入口、规则来源和相关测试，优先使用有依据的文件或稳定目录边界。
2. 建立知识与源码的多对多关联。把共享文件显式关联到实际依赖它的模块，在概览或代码映射页解释共享原因及预期影响。
3. 按 `references/content-verification.md` 从正文重要结论反查来源是否被本页所属模块覆盖；关联到其他模块不足以保证本页能感知变化。新增页及归位内容同样检查，必要时在授权范围补齐映射，无法覆盖的明确说明。
4. 检查是否用过大的前后端目录代替模块分析；目录确实不可进一步合理区分时说明限制，不凭感觉宣称精确。
5. 在 Git 仓库根运行映射报告并抽查实际文件，再据语义调整。自动报告只能提供路径覆盖、共享来源及未映射候选，不能决定业务边界。

```bash
node /absolute/skill-directory/scripts/wiki.mjs mapping --root /absolute/project --config docs/wiki/wiki.config.json
```

mapping、changes 及新鲜度工具依赖 Git 仓库。没有 Git 时仍可按实际来源初始化、阅读及维护文档，check 不依赖 Git；来源对应关系人工核对，并明确无法启用这些指纹/候选检查。不为生成 Wiki 擅自 git init 或把子目录错误地当仓库根。

报告中的共享文件和比例用于判断维护影响；高重叠可能是真实公共能力，也可能是粗映射，需要结合来源解释，不能按统一阈值自动判错。未映射路径用于核对本次覆盖目标，并不意味着每个仓库文件都必须进入知识库；不要为清空报告将整个仓库加入所有模块。

映射由 Agent 生成时，覆盖合理性也是其交付责任。不能把粗映射交给用户后笼统称为“项目配置问题”；业务边界确有歧义时给出依据、候选及具体待确认项。现有项目已有可靠划分时沿用，不为采用默认骨架重组全库。

## 生成、验证与交付

按 `references/templates.md` 选择所需模板，按 `references/knowledge-classification.md` 填入重要结论的类型、来源、核验方式和适用范围，再按 `references/knowledge-maintenance.md` 保留有效旧知识及人工内容。

在入口的覆盖说明中记录实际交付程度、已完成与未完成范围、映射/新鲜度/检查门是否启用，以及相关命令或项目现有机制。资料不足时交付有明确边界的内容，局部记录未知；旧文档仍可能是有效契约，逐项核查而不一律降为历史线索。

运行项目约定的结构和链接检查，按 `references/content-verification.md` 核对重要结论与实际来源、入口摘要和相关页面是否一致；按知识分类参考复查待确认项的准入与归位，重要操作的未验证风险仍须局部可见。持续同步和强制门还应完成相应记录与候选验证。读回所选页面全文与重复位置后才保存复核；交付关键断言的来源定位、处置及本页映射结果，无需新建永久核对台账。结果要区分文档已生成、机械检查通过、Agent 已核对的内容、仍未知的事项及尚未接入的维护环节。

交付实际文件和验证结果后，将不阻塞本次目标的治理、发布证据或工具扩展建议列为后续事项，不用建议书替代请求中的 Wiki 产物。
