# 项目知识维护

让项目知识能被定位、核实和更新。知识覆盖项目概览、业务/能力、系统架构、部署环境和运维排障，按项目适用性组织。知识内容归目标项目所有，技能提供方法、检查工具和显式复核记录工具，不要求固定语言、框架、目录或外部模型服务。

## 选择任务

| 用户意图 | 执行方式 |
|---|---|
| read：理解项目或模块 | 先按 `references/freshness.md` 检查相关模块新鲜度，再读索引及相关文档；关键结论追溯来源，返回依据、适用版本和未知项 |
| init：建立知识库 | 按 `references/initialization.md` 和 `references/templates.md` 确定范围/布局，再执行下方单页流程 |
| maintain：更新指定知识 | 执行下方单页流程，保留人工内容和未解决分歧；特殊维护情况按需查 `references/knowledge-maintenance.md` |
| check：检查知识库 | 结构/链接检查按 `references/tools.md` 运行；要求正文核验时执行下方单页流程 |
| sync：分析变更影响并同步 | 按 `references/change-review.md` 确定 Git 比较范围，再执行下方单页流程；记录按 `references/freshness.md` 保存 |

不把每次阅读变成全库审计，也不因为编写代码就自动重建 Wiki。只读询问、检查和同步建议不隐含写入授权；用户已明确要求初始化或更新时直接完成范围内文档工作，不新增固定审批门。

缺少 PRD、部分规则有争议或部署状态未知时，继续交付有依据的内容，局部标记缺口。发布记录、审批流程或 CI 改造只有在本次目标需要时才纳入交付；不能用一份治理建议替代已授权的文档生成。

## 生成或维护：一次完成一页

本流程用于 init、maintain、sync，以及用户要求的正文核验；只读问答或单纯查链接不强制跑全流程。先确认技能安装目录、项目根及现有入口，项目已有目录、标题和术语优先。已有 Wiki 先检查新鲜度；关键结论即使 fresh 也要追源。

1. **列核对包**。读取本页全文，已有 Git 和映射配置时运行：
   ```bash
   node /absolute/skill-directory/scripts/wiki.mjs mapping --root /absolute/project --config docs/wiki/wiki.config.json --document docs/wiki/example.md
   ```
   使用输出 documentReview 的带行号段落逐块核对；references 列出字面路径候选、同名歧义和本页模块覆盖，不能代替寻找正文没提到的真实来源。没有 Git/配置时人工列相同任务，不为运行命令新建全库机制。
2. **追源并改原句**。对影响理解/操作的断言记录简短处置：正文位置、源码/契约位置、证据范围、保留/修正/未知。先看调用方覆盖与条件，区分平台、渠道、环境及时间。改摘要、表格或步骤中的原断言，不能只在末尾补免责声明。核对方法见 `references/content-verification.md`；知识分类与待确认项准入见 `references/knowledge-classification.md`。
3. **读回后复核**。完成一页后重读修改结果，搜索同一事实的重复表述及直接引用来源中的相反口径；将真正依赖的来源补入本页所属模块，导航链接不自动等于依赖。重跑单页核对包，交代重要残留和映射缺口，再进入下一页。所有本次相关页面完成后才运行 check、freshness/gate；实际复核后才写 review，禁止为了全绿补签。

交付时给出本次页面/关键段落的实际处置与来源定位，不要求把临时核对包或工作记录永久加入项目。纯机械检查通过不能写成语义核验通过。详细选型、初始化交付和系统知识按上方任务路由按需阅读，不先加载所有参考文件。

模块按读者问题、业务或对外能力划分，与源码多对多关联。无项目约定时才采用 small/modular 模板；已有项目沿用 project 约定。架构、部署环境及运维是应评估的知识面，不适用则说明，不推定实际上线。缺少 PRD 或线上证据时仍完成有依据的部分，不擅自启动发布、需求决策或代码修复。

## 交付与协作边界

按任务返回答案、修改文件或检查结果，并说明证据基线、实际检查范围、未确认项和未执行的验证。机械检查通过仅表示其覆盖的检查通过。

初始化还应交代一次性文档、持续维护、持续同步或强制检查门中实际完成到哪一级；持续同步应有真实首份复核记录和触发约定，强制门应有实际接入证据。脚本的 semantic: not_run 不免除 Agent 对所写结论进行语义核对的责任。

需求变更由用户或需求流程决定；疑难取证可调用可用的 `research`；实现缺陷交给修复流程。Wiki 为需求、设计、实现、测试和发布提供知识输入，不自动启动这些流程，也不把自身设为每次开发的强制阶段。

评估技能行为时使用 `references/evaluation-cases.md`；这些场景不要求日常使用时全部执行。
