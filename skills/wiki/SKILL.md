# 项目知识维护

让项目知识能被定位、核实和更新。知识内容归目标项目所有，技能只提供方法和只读辅助工具，不要求固定语言、框架、目录或外部模型服务。

## 选择任务

| 用户意图 | 执行方式 |
|---|---|
| read：理解项目或模块 | 先找现有索引，按问题读相关文档；关键结论追溯来源，返回依据、适用版本和未知项 |
| init：建立知识库 | 阅读 `references/knowledge-maintenance.md` 和 `references/templates.md`，已有约定优先；无约定时选择默认骨架和模板，生成有证据的初稿并检查 |
| maintain：更新指定知识 | 阅读 `references/knowledge-maintenance.md`，对照来源做局部修改，保留人工内容和未解决分歧 |
| check：检查知识库 | 阅读 `references/tools.md`，运行适用的结构检查；如用户要求内容核验，再抽查来源 |
| sync：分析变更影响并同步 | 阅读 `references/change-review.md`，确定 Git 范围，核对变更与知识；按已授权范围报告或更新 |

不把每次阅读变成全库审计，也不因为编写代码就自动重建 Wiki。只读询问、检查和同步建议不隐含写入授权；用户已明确要求初始化或更新时直接完成范围内文档工作，不新增固定审批门。

## 定位与证据

- 先确定目标项目根、用户关注范围和已有知识入口。沿用项目指令及目录约定；没有约定时，为初始化选择与项目现有文档一致的位置并说明。不要把 Wiki 写进插件安装目录。
- 概览、业务规则、代码映射、依赖是可用的知识视角，不强制拆成四个文件。小型库可以只有一篇文档，服务项目可按模块拆分。
- 新建且无既有约定时，使用 `references/templates.md` 的 small 或 modular 骨架，以及技能 `assets/templates/` 内对应模板；将选择写入项目自有检查配置并显式传给检查工具。已有项目使用 project 约定，需要自动检查时声明其必需文档和章节，不自动搬迁目录或补套默认格式。
- 区分已确认规则、当前实现观察、推断及待确认项。代码与文档冲突时，先核查依据；不能仅因代码不同就改写规则，也不能把“代码已实现”写成“生产已上线”。
- 对影响决策的结论保留来源、适用范围、基线和实际核验时间。阅读过文档不等于核实过事实；无法访问来源时保留未知，不刷新其核验时间。
- 技能资源从宿主提供的技能目录定位，目标根显式传给脚本。检查工具只处理结构和变更材料，不判断业务语义，不调用模型 API，不改目标文件。

## 交付与协作边界

按任务返回答案、修改文件或检查结果，并说明证据基线、实际检查范围、未确认项和未执行的验证。机械检查通过仅表示其覆盖的检查通过。

需求变更由用户或需求流程决定；疑难取证可调用可用的 `research`；实现缺陷交给修复流程。Wiki 为需求、设计、实现、测试和发布提供知识输入，不自动启动这些流程，也不把自身设为每次开发的强制阶段。

评估技能行为时使用 `references/evaluation-cases.md`；这些场景不要求日常使用时全部执行。
