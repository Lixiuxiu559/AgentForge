# 设计两次（Design It Twice）

当用户想为一个选定的深化候选探索替代接口时，使用这个并行子代理模式。基于 "Design It Twice"（Ousterhout）——你的第一个想法不太可能是最好的。

使用 [SKILL.md](SKILL.md) 中的词汇——**module**、**interface**、**seam**、**adapter**、**leverage**。

## 流程

### 1. 框定问题空间

在生成子代理之前，为选定的候选写一份面向用户的问题空间说明：

- 任何新接口需要满足的约束
- 它依赖的依赖，以及它们属于哪个类别（见 [DEEPENING.md](DEEPENING.md)）
- 一个粗略的说明性代码草图，把约束落地——不是提案，只是让约束变得具体的方式

把它展示给用户，然后立即进入第 2 步。子代理并行工作时，用户阅读和思考。

### 2. 生成子代理

并行生成 3+ 个子代理。每个必须为深化后的模块产出**截然不同**的接口。

给每个子代理一份独立的技术简报（文件路径、耦合细节、来自 [DEEPENING.md](DEEPENING.md) 的依赖类别、seam 后面有什么）。简报独立于第 1 步面向用户的问题空间说明。给每个 agent 一个不同的设计约束：

- Agent 1："最小化接口——目标是最多 1–3 个入口点。每个入口点最大化 leverage。"
- Agent 2："最大化灵活性——支持许多用例和扩展。"
- Agent 3："为最常见的调用方优化——让默认情况变得平凡。"
- Agent 4（如果适用）："围绕跨 seam 依赖设计 ports & adapters。"

简报中同时包含 [SKILL.md](SKILL.md) 词汇和 CONTEXT.md 词汇，让每个子代理以一致的架构语言和项目领域语言命名事物。

每个子代理输出：

1. 接口（类型、方法、参数——加上不变量、顺序、错误模式）
2. 使用示例，展示调用方怎么用
3. 实现把什么藏在 seam 后面
4. 依赖策略和 adapters（见 [DEEPENING.md](DEEPENING.md)）
5. 权衡——哪里 leverage 高，哪里薄

### 3. 呈现和比较

顺序呈现设计，让用户吸收每一个，然后用散文比较。按 **depth**（接口处的 leverage）、**locality**（变更集中在哪里）和 **seam placement** 对比。

比较之后，给出你自己的推荐：你认为哪个设计最强、为什么。如果不同设计的元素能很好地组合，提出一个混合方案。要有观点——用户想要一个明确的判断，不是一份菜单。
