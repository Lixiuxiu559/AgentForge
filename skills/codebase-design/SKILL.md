# 代码库设计

设计**深层模块（deep modules）**：大量行为藏在一个小接口后面，位于干净的 seam 上，可通过该接口测试。在代码被设计或重构的任何地方使用这套语言和这些原则。目标是给调用方 leverage，给维护者 locality，给所有人可测试性。

## 词汇表

精确使用这些术语——不要替换成 "component"、"service"、"API" 或 "boundary"。一致的语言就是全部要点。

**Module（模块）**——任何有接口和实现的东西。刻意与规模无关：一个函数、类、包，或横跨层级的切片。_避免_：unit、component、service。

**Interface（接口）**——调用方为了正确使用模块必须知道的一切：类型签名，还有不变量、顺序约束、错误模式、必需配置和性能特征。_避免_：API、signature（太窄——它们只指类型层面的表面）。

**Implementation（实现）**——模块内部的东西，它的代码体。区别于 **Adapter（适配器）**：一个东西可以是小适配器带大实现（一个 Postgres repo），或大适配器带小实现（一个内存 fake）。当 seam 是话题时说 "adapter"；否则说 "implementation"。

**Depth（深度）**——接口处的 leverage：调用方（或测试）每学习一个单位的接口，能练习多少行为。当大量行为藏在小接口后面时，模块是**深（deep）**的；当接口几乎和实现一样复杂时，模块是**浅（shallow）**的。

**Seam（接缝）**（_Michael Feathers_）——一个你可以在不编辑该处的情况下改变行为的地方；模块接口所居的*位置*。seam 放在哪里是它自己的设计决策，与它后面放什么不同。_避免_：boundary（与 DDD 的有界上下文 overloaded）。

**Adapter（适配器）**——一个在 seam 上满足接口的具体事物。描述*角色*（它占据什么槽位），不是实质（它里面是什么）。

**Leverage（杠杆）**——调用方从深度获得的东西：每学习一个单位的接口获得更多能力。一个实现回报 N 个调用点和 M 个测试。

**Locality（局部性）**——维护者从深度获得的东西：变更、bug、知识和验证集中在一处，而不是散在调用方之间。修一次，处处修好。

## 深与浅

**深层模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│   小接口             │  ← 少量方法，简单参数
├─────────────────────┤
│                     │
│  深实现              │  ← 复杂逻辑隐藏其中
│                     │
└─────────────────────┘
```

**浅层模块** = 大接口 + 少量实现（避免）：

```
┌─────────────────────────────────┐
│       大接口                     │  ← 大量方法，复杂参数
├─────────────────────────────────┤
│  薄实现                          │  ← 只是透传
└─────────────────────────────────┘
```

设计接口时，问：

- 我能减少方法数量吗？
- 我能简化参数吗？
- 我能在里面隐藏更多复杂性吗？

## 原则

- **深度是接口的属性，不是实现的。** 一个深层模块内部可以由小的、可 mock、可替换的部分组成——它们只是不属于接口。一个模块可以有**内部 seam**（对其实现私有，被它自己的测试使用）以及接口处的**外部 seam**。
- **删除测试。** 想象删除这个模块。如果复杂性消失了，它就是个透传。如果复杂性在 N 个调用方重新出现，它在挣自己的位置。
- **接口就是测试面。** 调用方和测试穿过同一个 seam。如果你想测试*越过*接口的地方，模块的形状可能错了。
- **一个适配器意味着假想的 seam。两个适配器意味着真实的。** 除非有东西真的在它上面变化，不要引入 seam。

## 为可测试性设计

好接口让测试自然：

1. **接受依赖，不要创建它们。**

   ```typescript
   // 可测试
   function processOrder(order, paymentGateway) {}

   // 难测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要产生副作用。**

   ```typescript
   // 可测试
   function calculateDiscount(cart): Discount {}

   // 难测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **小表面面积。** 更少的方法 = 更少的测试。更少的参数 = 更简单的测试 setup。

## 关系

- 一个 **Module** 恰好有一个 **Interface**（它呈现给调用方和测试的表面）。
- **Depth** 是 **Module** 的属性，对着它的 **Interface** 衡量。
- 一个 **Seam** 是 **Module** 的 **Interface** 所在之处。
- 一个 **Adapter** 坐在 **Seam** 上并满足 **Interface**。
- **Depth** 为调用方产出 **Leverage**，为维护者产出 **Locality**。

## 被拒绝的框架

- **深度作为实现行数与接口行数之比**（Ousterhout）：奖励给实现注水。我们改用 depth-as-leverage（深度即杠杆）。
- **"Interface" 作为 TypeScript 的 `interface` 关键字或类的公共方法**：太窄——这里的接口包括调用方必须知道的每一个事实。
- **"Boundary"**：与 DDD 的有界上下文 overloaded。说 **seam** 或 **interface**。
