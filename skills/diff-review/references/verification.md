# 三轴执行细节

## 能力必须自包含

三条轴全部由本技能自己完成。**不得把任何一条轴委托给宿主环境专有的命令、技能或工具链。**

判断标准：**在只有 git 和文件系统的环境里，本技能是否仍然完整可用？**

如果答案是"否"，说明设计引入了宿主依赖，需要修正。

这意味着：

- 不写"用某平台内置的评审命令做 Correctness 轴"
- 不写"如果环境支持就调用 X"
- Correctness 轴的判据必须是本技能自己的检查清单

## 三轴为什么建议分开执行

三条轴关心不同的材料：

| 轴 | 需要读 |
|---|---|
| Correctness | diff + 周边代码 + 调用方 |
| Standards | diff + 规范文档 + 工具配置 |
| Spec | diff + 需求文档 |

放在同一个上下文里跑会互相污染：Spec 的"这个需求没实现"会影响 Correctness 的判断（把"为了满足需求而不得不写的复杂分支"报成 bug），Standards 的规范条目会影响对代码结构的容忍度。

理想做法是**各由一个独立的执行单元完成，彼此看不到对方的结论**。

## 但不要假装已经派发

**关键约束**：只有当前环境确实提供了可用的派发通道时才并行。

如果不可用，就**自己串行跑完三轴**，并在报告里如实说明。

**绝对不要：**

- 声称派发了子任务但实际是自己跑的
- 为了"看起来正规"而虚构执行方式

报告里的执行方式必须如实。

## 派发时给什么

如果确实要派发，每个执行单元的 brief 必须**自包含**——它看不到主对话，也读不到本技能的其它 reference。

**Correctness 单元**：

1. 基线 commit 与 diff 命令
2. **检查清单全文**（它没有其它途径读到）
3. 任务：按清单逐类对照 diff
4. 硬性要求：每条给出触发路径，说不出触发路径的不要报
5. 字数上限

**Standards 单元**：

1. 基线 commit 与 diff 命令
2. 找到的规范文件清单
3. **12 条 smell 基线全文**
4. 任务：报硬性违规（引规范文件 + 规则）与 smell（引名称 + 代码片段）
5. 区分硬性违规与判断项
6. 字数上限

**Spec 单元**：

1. 基线 commit 与 diff 命令
2. spec 路径或内容
3. 任务：报（a）缺失/部分实现的（b）范围外改动（c）实现可疑的
4. 每条引 spec 原句
5. 字数上限

**字数上限是刻意的**：执行单元的默认失败模式是啰嗦。写死上限能显著提升报告可用性。

## 串行执行时的顺序

**Correctness → Standards → Spec**。

理由：

1. Correctness 最客观（有触发路径就是有，没有就是没有），先做能把最硬的结论定下来
2. Standards 需要读规范文档，是中等客观
3. Spec 需要理解整体意图，最后做能带着对代码的完整认识判断

三轴之间**刻意不互相参考结论**。写完一轴再开始下一轴，不要在写 Spec 时回头改 Correctness 的结论。

## 找不到 spec 时

跳过 Spec 轴，**不要**：

- 从代码反推需求
- 用 commit message 当 spec（除非它确实描述了需求）
- 发明验收标准

报告里写明"无 spec 可用"，并明确说明**本次只完成了两条轴**——让调用方知道评审不完整。

## 边界

本技能**不做**以下检查，遇到时不要顺手做：

| 检查 | 归属 |
|---|---|
| 复杂度指标、CRAP、覆盖率 | 复杂度审计能力 |
| 测试是否真正验证逻辑（突变测试） | 测试有效性审计能力 |
| 实施编排、任务拆分、集成验证 | 实施编排能力 |
| 调研取证 | 调研能力 |

各管一段。混着做会让报告失去聚焦，也使作者搞不清该找谁修。
