# 基线算法与评审范围

## 为什么要算 merge-base

直接用 `git diff <固定点>...HEAD`（三点号）在语义上已经等价于「固定点与 HEAD 的 merge-base」。
但显式算出 merge-base 有两个好处：

1. **评审期间固定点被推进也不漂移** —— 如果固定点是 `main` 这类活动分支，而评审过程中有人往 `main` push 了，`git diff main...HEAD` 的结果会变。先固化 `BASE=$(git merge-base <固定点> HEAD)` 就不会。
2. **后续命令可以复用同一个 `$BASE`**，避免各命令之间理解不一致。

```bash
git rev-parse <固定点>                    # 先确认 ref 可解析
BASE=$(git merge-base <固定点> HEAD)
git diff --stat "$BASE"
```

`git rev-parse` 失败时**停止**，不要继续往下跑——坏 ref 应该在流程最开头失败，而不是在生成了半份报告之后。

## 必须覆盖工作区改动

`git diff "$BASE"`（不带第二个 ref）对比的是**工作区**，因此同时包含：

- 已提交的改动
- 已暂存（staged）的改动
- 未暂存的改动

这是刻意的选择。很多评审场景是"刚改完，还没提交"——如果只评审已提交内容，会报出"无内容可评审"，而实际上有大量改动。

## 未跟踪文件必须单独处理

`git diff` **不显示未跟踪（untracked）的新文件**。这是最容易漏掉的一类改动。

必须另外查：

```bash
git status --short
```

`??` 开头的条目就是未跟踪文件。

**未跟踪文件的全部内容都算新增**，直接用 Read 读取，不要指望 `git diff` 能显示它们。

在报告里必须显式列出未跟踪文件的数量和文件名，让调用方知道这部分是怎么被评审的。

## 空 diff 的处理

当同时满足以下两点时：

1. `git diff "$BASE"` 为空
2. `git status --short` 没有未跟踪文件

**停下并报告「无内容可评审」**，说明对比的基线和当前状态。

不要虚构评审结果，也不要为了产出报告而评审与本次改动无关的历史代码。

如果 diff 为空但**有未跟踪文件**，则正常评审（这些文件就是本次改动）。

## 范围裁剪

范围由固定点决定，不要扩大：

- 不评审 diff 未触及的文件
- 不因为"路过看到"就报历史遗留问题
- 如果历史代码的问题影响了本次改动（例如本次改动依赖了一个坏接口），把它作为**本次改动的风险**报告，而不是独立的历史问题

## 常见错误

| 错误 | 后果 |
|---|---|
| 用 `git diff <固定点>..HEAD`（两点号） | 对比的是两个 commit 的快照，不是 merge-base，会包含固定点上的无关改动 |
| 忘记 `git status --short` | 漏掉所有新增文件 |
| 只评审 `HEAD` 已提交内容 | 报"无内容可评审"，而实际有未提交改动 |
| 固定点是活动分支但不固化 merge-base | 评审期间结果漂移 |
| ref 无效却继续 | 产出基于错误基线的报告 |
