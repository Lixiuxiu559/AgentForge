# 报告模板

严格按此结构输出。**三轴分开，不合并，不重排。**

````markdown
## 评审范围

- 固定点：<固定点原文>
- 基线 commit：<merge-base 短 hash>
- 改动：N 个文件，+X/-Y 行
- 未跟踪文件：N 个（<逐个列出文件名，或"无">）
- 规范来源：<文件列表，或"仓库未文档化任何规范">
- 工具已强制：<lint / 格式化 / 类型检查清单，或"未识别">
- spec 来源：<路径> / 无 spec 可用
- 执行方式：<串行三轴 / 派发执行单元>

## Correctness

- `<文件>:<行>` <问题描述>
  - **触发**：<什么输入 / 时序 / 状态>
  - **后果**：<会发生什么错误>
  - **严重度**：高 / 中 / 低

（无则写：未发现具有可构造触发路径的缺陷）

### 待确认

- `<文件>:<行>` <怀疑点>（未能构造触发路径，需要人工判断）

（无则写：无）

## Standards

### 硬性违规（违反仓库文档化规范）

- `<文件>:<行>` 违反 `<规范文件>` 的「<规则>」
  > <代码片段>

（无则写：未发现违反仓库文档化规范的地方）

### 判断项（Fowler smell 基线，非硬性违规）

- `<文件>:<行>` possible **<Smell 名>** —— <说明>
  > <代码片段>

（无则写：未发现明显的基线 smell）

## Spec

### 缺失或部分实现

- spec 原句：「<引用>」
  → <缺什么，位置>

（无则写：spec 要求的内容均已实现）

### 范围外改动（scope creep）

- <spec 未要求的行为>（`<文件>:<行>`）

（无则写：无范围外改动）

### 实现可疑

- spec 原句：「<引用>」
  → <可疑点>（`<文件>:<行>`）

（无则写：已实现部分未发现可疑之处）

### 无 spec 可用

（仅当找不到 spec 时写此节，并说明本次只完成了两条轴）

## 小结

- Correctness：<N> 条（高 <a> / 中 <b> / 低 <c>）
- Standards：<M> 条（硬性 <X> / 判断 <Y>）
- Spec：<K> 条
- Correctness 内最严重：<一条，或"无">
- Standards 内最严重：<一条，或"无">
- Spec 内最严重：<一条，或"无">
````

## 硬性规则

### 不写跨轴冠军

结尾**只有**每轴各自的最严重项。**不要**写"总体最严重的问题是 X"。三轴分离的意义就是防止一轴掩盖另一轴。

### 每条 finding 必须带位置、引用、后果

| 轴 | 位置 | 引用 | 后果 |
|---|---|---|---|
| Correctness | `文件:行` | 触发路径 | 错误行为 |
| 硬性违规 | `文件:行` | 规范文件 + 规则 | —— |
| 判断项 | `文件:行` | smell 名 + 代码片段 | —— |
| Spec | `文件:行` | spec 原句 | —— |

**没有引用或说不出后果的怀疑，不要出现在正文里。** 可以放到「待确认」并明确标注。

### 区分硬性违规与判断项

这两类**不能混在同一个列表**。硬性违规是成文标准的违反；判断项是启发式观察。混在一起会让作者误以为 smell 也是必须修的。

### Correctness 的触发路径是硬门槛

说不出"什么输入 / 时序导致什么后果"的，不能作为正式 finding。这是这条轴防止噪音的核心机制。

### 如实报告执行方式

串行就写串行，派发了就写派发。**不要为了显得正规而美化。**

### 如实报告降级

以下必须在报告里显式写明，不能静默省略：

- 找不到 spec → 只完成两条轴
- 没找到规范文档 → 只用 smell 基线
- 无法判断工具已强制什么 → 说明未做该判断

### 无内容可评审要明说

diff 为空且无未跟踪文件时：

```markdown
## 评审范围

- 固定点：<...>
- 基线 commit：<...>

## 结论

无内容可评审。基线 `<...>` 与当前工作区之间没有差异，也没有未跟踪文件。

如果预期有改动，请确认：
- 固定点是否正确
- 改动是否在另一个分支上
- 是否忘记保存文件
```

**不要虚构评审结果。**

## 篇幅

每条 finding 控制在三到五行。**宁少勿多**——宁可少报几条站得住的，也不要为了显得工作量大而堆砌猜测。
