# 判据：仓库规范与 Fowler smell 基线

## 一级判据：仓库文档化规范

仓库里任何说明"代码该怎么写"的文件都是规范来源。常见的：

- `CONTRIBUTING.md`
- `CODING_STANDARDS.md`、`CODING_RULES.md`
- `REVIEW.md`（评审专用指令）
- `.editorconfig`
- 架构文档里的约定章节
- 目录级 `CLAUDE.md` / `AGENTS.md`
- 语言/框架的 lint 配置（用于判断"工具已强制什么"）

**怎么用**：diff 里每一处违反规范的地方，引「规范文件 + 具体规则」。

**硬性违规**才报为确定问题——因为这是成文的、有共识的标准。

### 先确认工具已经强制了什么

在报告任何规范违规之前，先看项目有哪些 lint、格式化、类型检查工具。

**工具已经强制的内容一律跳过。** 重复工具的工作会让报告充满噪音，并让作者觉得评审"不看项目的实际情况"。

判断方法：看 `package.json` 的 scripts、`.eslintrc` / `biome.json` / `ruff.toml` / `checkstyle.xml` 等配置文件、CI 配置。

## 二级判据：Fowler smell 基线

仓库什么都没写时，用这 12 条兜底。每条写成「**是什么 → 怎么改**」，对照 diff 匹配。

| Smell | 是什么 | 怎么改 |
|---|---|---|
| **Mysterious Name** | 函数、变量或类型的名字没有揭示它做什么或装什么 | 改名；取不出诚实的名字说明设计本身浑 |
| **Duplicated Code** | 同一段逻辑形状出现在多个 hunk 或文件 | 抽出共享形状，两边调用 |
| **Feature Envy** | 一个方法访问别的对象的数据多于自己的 | 把这个方法搬到它羡慕的数据那边 |
| **Data Clumps** | 同几个字段或参数总是结伴出现（一个想诞生的类型） | 打包成一个类型再传 |
| **Primitive Obsession** | 用原始类型或字符串冒充一个值得有自己的类型的领域概念 | 给这个概念一个自己的小类型 |
| **Repeated Switches** | 对同一类型的 `switch` / `if` 级联在改动里重复出现 | 换成多态，或让两处共享一张表 |
| **Shotgun Surgery** | 一个逻辑改动迫使你在很多文件里散着改 | 把总是一起变的东西收进一个模块 |
| **Divergent Change** | 一个文件或模块因为几个不相关的原因被反复改 | 拆开，让每个模块只因一个原因变化 |
| **Speculative Generality** | 为 spec 没有的需求加了抽象、参数或钩子 | 删掉；等真实需求出现再 inline 回来 |
| **Message Chains** | 调用方不该依赖的长链 `a.b().c().d()` | 在第一个对象上用方法把这段走位藏起来 |
| **Middle Man** | 一个类或函数大部分只是在转发 | 砍掉，直接调真正的目标 |
| **Refused Bequest** | 子类或实现类忽略、覆盖了大部分继承来的东西 | 放弃继承，改用组合 |

## 两条绑定规则

这两条是**防止基线变成噪音**的关键，必须遵守：

### 1. 仓库覆盖基线

仓库文档化的标准**永远压过**基线。凡是仓库明确认可的做法，即使基线会标记它，**一律不报**。

有些项目故意使用基线会标记的写法（例如为了性能刻意重复代码、为了框架约定使用不同的命名风格）。报这些是把项目的有意决策当成错误。

### 2. 永远是判断项

每条 smell 都是**带标签的启发式**，绝不是硬性违规。报告里必须写成：

```text
possible Feature Envy
```

而不是：

```text
Feature Envy violation
```

## 两类 finding 必须分开

| 类型 | 来源 | 报告语气 |
|---|---|---|
| **硬性违规** | 仓库文档化的规范 | 确定问题 |
| **判断项** | 仅来自 smell 基线 | 启发式，标注 `possible` |

在报告的 Standards 轴里分成两节呈现。

## 每条 finding 必须带引用

| 轴 | 引用形式 |
|---|---|
| 硬性违规 | 规范文件路径 + 具体规则 |
| 判断项 | smell 名 + 代码片段 |
| Spec | spec 原句 |

**没有引用的怀疑不要报。** 引用的作用是让作者能自己核对，也是"这不是凭空猜测"的证明。

## 一条实用原则

**宁少勿多。** 一份 3 条都站得住的报告，比 15 条里一半是猜测的报告有用得多。

基线的作用是"仓库没写规范时仍然有个共同语言"，不是"把 diff 从头到尾挑一遍"。
