# 测试驱动开发

TDD 是红 → 绿循环。本技能是让这个循环产出值得保留的测试的参考：什么是好测试、测试放在哪里、反模式、以及循环的规则。每一节在每一次循环都适用——在循环之前和循环之中查阅它们，而不是之后。

探索代码库时，读 `CONTEXT.md`（如果存在），让测试名称和接口词汇与项目的领域语言一致，并尊重你所在区域的 ADR。

## 什么是好测试

测试通过公共接口验证行为，而不是实现细节。代码可以完全改变；测试不应该。一个好测试读起来像一份规格说明——"用户可以用有效购物车结账"准确地告诉你存在什么能力——并且能在重构中存活，因为它不关心内部结构。

参见 [tests.md](tests.md) 获取示例，[mocking.md](mocking.md) 获取 mock 指南。

## Seam——测试放在哪里

**seam** 是你测试所在的公共边界：你观察行为而不深入内部的接口。测试位于 seam 上，绝不针对内部。

**只在预先约定的 seam 上测试。** 在写任何测试之前，写下被测的 seam 并与用户确认。不在未确认的 seam 上写测试。你无法测试一切——预先约定 seam 是让测试投入落在关键路径和复杂逻辑上，而不是每个边缘情况。

问："什么是公共接口，我们应该测试哪些 seam？"

当接口本身的形态存疑时——模块有多深、seam 应该放在哪里、接口应该暴露什么——使用 `/codebase-design` 技能获取词汇。它是 module、interface、depth、seam、adapter、leverage 和 locality 这些术语的共同来源，是供查阅的参考，不是要运行的会话。

## 反模式

- **实现耦合**——mock 内部协作者、测试私有方法、或通过旁路验证（查询数据库而不是使用接口）。标志：测试在重构时坏了，但行为没变。
- **同义反复**——断言按代码的方式重新计算期望值（`expect(add(a, b)).toBe(a + b)`、手工按同样方式推导的快照、断言一个常量等于它自己），于是它按构造就通过，永远不可能与代码不一致。期望值必须来自独立的真值来源——一个已知正确的字面量、一个算例、spec。
- **水平切片**——先写所有测试，再写所有实现。批量测试验证的是*想象中*的行为：你测试的是事物的*形状*而非用户可见的行为，测试对真实变化变得不敏感，而且你在理解实现之前就锁定了测试结构。改为用**垂直切片**工作——一个测试 → 一个实现 → 重复，每个测试是一颗**曳光弹**，响应上一轮循环教给你的东西。

## 循环的规则

- **先红后绿。** 先写失败的测试，然后只写足够让它通过的代码。不要预期未来的测试或添加投机性功能。
- **一次一个切片。** 每个循环一个 seam、一个测试、一个最小实现。
- **重构不属于循环。** 它属于审查阶段（见 `code-review` 技能），不属于红 → 绿实现循环。
