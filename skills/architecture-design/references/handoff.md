# 方案完整度、使用与修订

## 设计深度与准备状态

架构师完成本次实施范围所需的关键决策：模块职责与依赖、共享契约、必要的数据物理设计与迁移、关键算法／一致性策略、页面与状态流，以及适用的质量和运行设计。可引用已有定义，不把它们重复复制到每份 Spec；可给关键伪代码或结构定义，不预先写生产实现。

交付前检查：

- 关键需求、质量约束和业务不变量都有设计落点，验收依据可定位。
- 用户需决定的关键取舍已确认，或在明确授权范围内完成选择；推荐项没有冒充用户决定。
- 本次需要的专项设计已完成，实施者不必自行补定共享 API、数据语义或关键技术路线。
- 总体、专项、契约、图示及决策记录一致，来源和设计基线明确。
- 会推翻方案的关键假设有足够依据；没有未处理的冲突或阻塞本次范围的问题。
- 变更范围、受保护范围、前置依赖、迁移／兼容顺序及验证办法可以承接。

据此说明状态：“草案”仍在探索；“可实施”完成所选范围的设计准备；“局部可实施”列出独立可开工范围、禁止启动范围及解除阻塞的条件；“受阻”说明关键障碍。不能用局部完成代表整体完成。

设计准备状态、用户关键选择和实施授权是不同信息。项目已有审批流程时沿用；不要求用户逐章批准，但不得跳过尚未决定的重大取舍。

## 方案使用摘要

按规模集中提供以下内容，可作为统一方案末尾的使用摘要，不强制另建文件或指定消费者：

| 信息 | 需要明确 |
|---|---|
| 入口与基线 | 方案入口、设计标识／修订状态、目标工程与代码基线；Git 项目说明相关未提交变更，没有 Git 则说明依据范围 |
| 决策与契约 | 用户选择／授权及限制、有效 ADR、权威接口／事件／类型／模型的位置与对应版本 |
| 完整设计 | 总体方案、相关专项、图源与实际验证记录；引用必须可访问，不能只给无上下文的文件名 |
| 实施边界 | 可开工范围、保持不变项、前置依赖、关键集成点、必要迁移与兼容阶段 |
| 验收与缺口 | 验收依据、验证办法／现有入口、开放问题、假设、风险及其阻塞范围 |

默认以 `spec.html` 为统一入口，引用 HTML 专题及权威契约，正文保持可直接读取的语义结构和稳定锚点；不要求额外 Markdown 副本。输入 PRD 可以是 `prd.html` 或既有其他格式，按其真实内容读取，不固定寻找 prd.md。独立阅读者应获得完整必要内容，不假设继承原对话；使用时核对工程变更是否使设计过时。

架构方案给出依赖与设计约束，不预设谁将使用它，也不规定任务调度、编码或测试执行方式。已有业务用例可按需引用，不从实现反推验收规则；用户可以单独审阅、补充测试设计或直接使用本方案。
