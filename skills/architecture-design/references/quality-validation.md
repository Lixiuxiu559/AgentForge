# 质量目标与关键风险验证

## 让约束驱动设计

针对本次范围识别少数决定架构的质量场景，按实际风险选择性能／容量、可靠性、一致性、安全、可维护性、可访问性、运行成本或恢复能力。说明触发条件、运行环境／负载、期望结果或指标、优先级、来源，以及它影响哪些决策。不要求每次覆盖全部维度或新增固定文档。

目标未明确时说明需要的业务或环境依据；会影响用户体验、预算或路线的目标及冲突交给用户讨论。事实、用户目标、设计建议、估算和实测分别标注。设计后回查质量场景如何得到满足，有何取舍和验证办法，不能只在末尾附一张指标表。

## 安全、数据与运行行为

安全设计由数据和攻击面触发，不取决于是否修改部署。按需追踪“资产／信任边界 → 威胁或滥用场景 → 控制位置 → 验证办法”，覆盖对象／租户隔离、输入与外部依赖、凭据、敏感数据访问及日志。说明数据保留、删除、归档与审计等相关生命周期约束；未知政策保留为业务问题，不代替用户制定。

沿关键调用链或异步处理链走读失败与过载：超时和重试如何组合，是否重复副作用，队列／并发／存储是否有上限，何时拒绝或降级，如何取消或恢复，怎样观测失败与积压。已有组件各自有重试不等于整体行为合理。

有持久化恢复或高可用要求时，按实际目标说明备份恢复、容忍的数据损失／恢复时间、单点及恢复验证；不要无依据承诺零丢失或固定恢复时限。部署设计执行边界不变：只设计，不据此执行上线或演练生产故障。

## 消减关键技术假设

识别少量“不成立就会推翻路线或使实施无法承接”的假设，例如依赖能力、目标版本支持、容量瓶颈、复杂迁移窗口或跨系统一致性。记录假设、失效影响、已有证据、最小验证动作和阻塞范围。

优先复用可靠的源码、现有测试／测量和适用版本的官方能力资料。需要实验时，可在已授权的隔离临时范围做最小 PoC／兼容性实验；不写生产实现，不修改正式数据或擅自安装整套基础设施。超出授权的访问或副作用先按实际边界处理，不能用验证名义执行部署。

记录实际验证基线、方法、观察和限制；验证失败则修订假设或重新比较方案。无法验证时区分可继续的独立范围与必须验证后才能承诺的范围。仅标“未验证”不足以消除关键风险，不能把依赖该假设的工作列为已准备好实施。

## 设计复核

关键业务场景、质量场景和失败路径应能贯穿流程、模块、契约、数据与验收。复杂或高风险任务可委派独立设计复核，重点反证关键假设与端到端行为；不要求每个任务固定增加评审角色，也不将独立复核代替主 Agent 的整体责任。
