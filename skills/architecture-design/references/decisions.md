# 方案比较与用户决策

架构师负责把选择讲清楚并给出推荐，用户保留重大取舍的最终决策权。用户要求“帮我设计”或材料充分，不能自动视为批准某个未展示的重大方案；但也不把每个设计选择都交给用户，否则用户会被迫评审本该由架构师处理的细节。

## 什么时候交给用户决定

同时满足以下两条的决策点，先比较再由用户决定：

1. **改起来代价大**：涉及不可逆迁移、对外契约或兼容、系统边界、安全边界，或推翻后需要重写一大块设计／实现。
2. **存在真实分歧**：至少有两个选项都满足硬约束，且各有明显代价，选择取决于用户的业务优先级。

质量目标之间存在明显冲突（如一致性与延迟、成本与可用性）且影响路线时，同样交给用户确定优先级。

不满足上述条件的决策由架构师直接选定：改动成本低、项目已有先例或规范、只有一个选项满足约束、属于已确认方向内的普通设计细节。在决策记录中写一句理由并标为“AI 选定，可推翻”，不停下来等待确认。字段、类名、文件划分等不做方案评选。

已有明确用户决策或项目硬约束直接沿用并标注来源；用户授权在限定范围内自行选择时，记录授权条件和实际取舍，不反复确认。

## 如何比较

按独立的决策点比较，不把多个决策捆成“整套方案 A／B／C”；只有决策点之间强耦合、必须一起选时才组合比较，并说明耦合原因。

每个决策点只列真实可行的选项，数量服从问题。明显不满足需求或硬约束的选项、用户已经否决的选项不列为候选；只有一个选项可行时，直接说明“只有这一条路”，加一句被排除方向的理由，不做比较表。用户提出的方案纳入同等比较。

只列影响本次选择的维度，如目标满足程度、限制与风险、改动范围、开发／运行／维护成本、兼容和迁移影响、可逆性。成本无可靠数字时用有依据的相对比较，区分估算和事实。给出清晰推荐及成立条件，同时说明推荐项的缺点和其他选项更合适的条件。边界或流程明显不同的候选可用简图帮助理解，选定后再深化完整图示。

## 讨论与推进

按依赖关系分轮提问。先理清决策点之间的依赖：互相独立的问题同一轮提出；依赖上游选项的问题，等上游决定后再问，不把依赖链压平成并列问题。每题给出比较要点和推荐，允许用户回答“按推荐”。

同一轮里，某个问题的推荐项下面如果还有子问题，可以把子问题的推荐作为“选推荐时的默认值”一并列出，用户回答“按推荐”即确认整条路径；用户选了其他选项，下一轮只追问该分支下的子问题。未被选中分支的子问题不展开。不把材料尚未讲清的选择题抛给用户。

尚未决定时，可继续不依赖选择的取证和方案整理；暂停依赖该决策的设计定稿与专项深化。不能把 AI 推荐、默认勾选、用户未回复或经过一段时间当成批准，也不能先将某一方案设计完来造成既成事实。用户明确要求探索多个候选时可以并行探索，但标为候选，不当成确定基线。

记录用户实际选择及理由或优先级；有明确上下文的确认可以复用，不要求固定口令。回答含糊且会改变路线时先核实。新证据或约束变化使已选方案失效时，说明变化和受影响决定，带更新后的比较回到用户，不能静默换方案。

## 决策记录

在方案中集中列关键决策：编号、结论、来源（用户选定／已授权选择／AI 选定，可推翻）、一句选择理由、受影响模块和验证缺口。AI 自主选择不能写成用户选定。

spec 正文只写选定结论和一句“为什么不选其他选项”；完整比较表、被否决选项的分析放入附录（见 [读者与写法](readability.md)）。尚待用户决定的比较材料可在正文展示，选定后移入附录。

子 agent 的方案是建议，不能代替用户选择；主 Agent 核实后统一组织比较和更新基线。长期影响的决策按项目约定落 ADR，其状态与上述记录一致。
