# Researcher 调查简报

## 通用交付格式

每个 researcher 只收集事实，不决定“应该重构”。返回：

```markdown
## 调查范围
- 负责方向：
- 文件 / 模块：
- git 基线或时间范围：

## 事实
1. 文件:行号 —— 观察
2. 文件:行号 —— 观察

## 支持架构改造的证据
- <具体摩擦、调用路径或历史变更>

## 反对架构改造的证据
- <稳定边界、ADR、兼容/性能约束或最小方案已足够的证据>

## 未确认项
- <缺少的证据>

## 置信度
高 / 中 / 低。原因：
```

禁止直接输出完整架构方案或改造代码。主 Agent 负责把事实转换成候选判断。

## 小范围（0 个 researcher）

主 Agent 直接读取代码、测试和约束。

## 单模块调查（1 个 researcher）

```text
调查目标模块的接口、调用链和测试入口。
找出理解该概念需要跨哪些文件，以及调用方是否依赖内部协调细节。
同时寻找反对改造的证据：稳定边界、ADR、性能或兼容性约束。
不要提出完整重构方案。
```

## 多模块调查（2 个 researcher）

### A：结构与调用链

```text
调查目标模块的模块关系、接口、调用链、跨模块依赖和信息泄漏。
标出具体文件与行号，说明哪些知识被调用方重复掌握。
不要提出完整架构方案。
```

### B：历史与变更热点

```text
读取最近相关 git history 和 diff。
找出反复修改的文件、经常一起变化的模块和变更扩散范围。
不要把高频修改直接等同于架构问题，必须报告支持和反对证据。
```

## 大范围调查（3 个 researcher）

在 A、B 的基础上增加：

### C：测试与约束

```text
调查目标模块的测试入口、fixture、覆盖范围、ADR、项目规范、公共调用方和兼容性约束。
判断当前接口是否可测试，以及潜在深化的迁移风险。
不要提出完整架构方案。
```

## 有争议时增加第 4 个

### D：反证与最小替代

```text
主动尝试证明结构性改造没有必要。
寻找现有边界合理的证据、最小整理即可解决的方案、稳定调用模式和改造风险。
如果候选只是“看起来不漂亮”，明确指出，不要帮它辩护。
```

## 并行规则

只有以下条件同时满足才并行：

- 各 researcher 的阅读范围明显独立
- 任务不依赖前一个 researcher 的发现
- 主 Agent 有明确的汇总问题
- 汇总收益大于启动和去重成本

没有这些条件时串行更好。**并行调查不等于并行做架构决策。**
