# 架构侦察验收案例

本文件规定技能**应该和不应该**提出什么候选。仅有 frontmatter 合法并不说明建议有用。

每个案例在独立、干净的会话运行。分别记录：是否正确触发、报告是否满足证据门槛、是否允许零候选、是否越界修改文件；不要只统计候选数量。

## 正例：真实浅模块

**输入**：入口、校验、持久化调用方重复掌握同一业务步骤，近两次变更要同步改 4 个文件。

**期望**：给出实际文件/调用路径、删除测试、反证、维持/最小/深化三方案；说明最小方案为什么不足。不要直接改代码。

## 反例：深模块

**输入**：一个稳定小接口封装了复杂实现，调用方无需知道内部步骤，测试直接通过接口完成。

**期望**：明确答复“暂未发现值得优先改造的机会”，不要为了凑卡片报 Speculative。

## 反例：热点但边界合理

**输入**：业务模块近期提交很多，但每次只在模块内部修改，对外契约稳定。

**期望**：热点只用来选调查范围，不能据此认定架构问题；报告其良好 locality 和反证。

## 反例：现有 ADR 限制

**输入**：乍看是多余适配层，但 ADR 规定必须为跨版本兼容保留。

**期望**：读 ADR，明确为何不能轻易删除；除非有新且足够强的证据，否则不推荐结构改造。

## 反例：最小整理足够

**输入**：问题来自重复命名或测试入口不清晰，改名或补测试即可解决；没有需要隐藏的额外协调知识。

**期望**：推荐最小整理或维持现状，而非新建模块层级。

## 高风险正例：值得改但暂不能开工

**输入**：真实跨模块摩擦，删除测试通过；但公共 API 调用方众多、缺测试保护、无法立即回滚。

**期望**：保留候选但降低强度，明确迁移风险与先补测试/调用方清单的步骤，不说“可以直接实施”。

## 多 researcher 并行案例

**输入**：多模块代码库，代码结构、变更历史、测试与 ADR 可分别调查。

**期望**：最多 2–3 个相对独立的 researcher 并行；各自返回具体证据与反证；主 Agent 按事实合并、去重，核对冲突，不投票。用户指定小模块时不派发多个 researcher。

## 文档产物与权限

**输入**：用户要求报告并希望保留。

**期望**：只写 `docs/research/` 下的 Markdown，报告路径在答复里可见；不改代码、`CONTEXT.md` 或 ADR；不依赖在线 CDN。

## 评分维度

| 维度 | 通过标准 |
|---|---|
| 候选精度 | 正例找到真实摩擦；反例不被硬凑成改造候选 |
| 证据覆盖 | 每个候选有可定位的文件、调用路径或历史改动 |
| 反证质量 | 主动找边界合理和最小方案已足够的事实 |
| 成本意识 | 比较维持、最小整理、结构深化及迁移/回滚风险 |
| 并行纪律 | 只在调查维度独立时并行；研究者不直接决定架构 |
| 零候选 | 正确回答“暂无值得优先改造”视为**成功** |
| 边界 | 不修改业务代码、ADR、词汇表，不启动无限追问 |

若发现误报，优先收紧**候选准入门槛**，不要用“报告少了不够好”驱动增加候选数。
