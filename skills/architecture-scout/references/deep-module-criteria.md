# 模块边界与候选准入判据

## 词汇

- **模块**：封装一组一致行为并暴露接口的单元；不等于一个目录或一个类。
- **接口**：调用方需要知道的行为、参数、状态和约束，不限于 HTTP API。
- **深模块**：接口相对简单稳定，内部承载较多变化与业务知识。
- **浅模块**：接口暴露了几乎全部实现细节，调用方仍需理解内部步骤。
- **seam**：不同职责相遇的可验证接缝；不是为了美观而添加的空包装。
- **locality**：理解或修改一个概念所需的知识能否集中在一处。

术语是分析工具，不是评分。文件多、层数多或某个类很大，都**不能单独证明**架构需要改造。

## 准入：每个候选都必须通过

### 1. 实际摩擦

至少举出一个真实修改场景，标注有关文件和调用方；例如最近两次同一业务规则变更都要同时改入口、适配器和三个调用方。提交热点仅用于引导找场景，不能代替场景本身。

如果只有“看起来不优雅”或“行数多”，停止推荐。

### 2. 当前接口为什么浅

指出调用方现在必须知道的内部知识：步骤顺序、跨模块数据拼装、重复参数组、错误语义或实现类型。解释这些知识为什么本应由模块自己承担。

若只是合理拆分不同职责、各文件内部自治，则不是浅模块。

### 3. 删除测试（硬门）

假设删除候选的包装层或合并模块：

- **复杂度集中**：调用方只需一个较小接口，原先外泄的协调逻辑被内部吸收 → 可以继续评估。
- **复杂度转移**：协调逻辑散到调用方、重复条件变多 → **不推荐此改造**。
- **无法证明**：缺少调用关系/约束证据 → 标记待调查，不给强推荐。

通过删除测试只说明值得深入比较，**不自动证明改造能回本**。

### 4. 主动寻找反证

至少查：已有 ADR 或兼容约束、稳定的接口与调用者、性能/部署理由、团队有意维持的边界、历史改造失败的记录。反证不是报告装饰；强反证应使候选降级或撤销。

### 5. 比较三个选项

| 选项 | 必须回答 |
|---|---|
| **维持现状** | 实际摩擦有多频繁？何时继续不改更划算？ |
| **最小整理** | 改名、局部收拢或补测试能否解除相同摩擦？ |
| **结构性深化** | 新接口隐藏了什么知识？相对于最小方案多获得什么？ |

**说明为什么最小整理不够**，否则不要推荐结构性深化。不得只画“漂亮的 after”而忽视不改的代价优势。

### 6. 迁移可行性

查公共 API 与调用者、数据/错误语义、测试保护、兼容期、阶段迁移、回滚方式。无需写完整实施方案，但“风险未调查”必须如实标注，不能建议马上开工。

## 候选强度

- **Strong**：有明确的重复摩擦、删除测试通过、最小方案不足、有足够测试和可控迁移路径。
- **Worth exploring**：收益可信，但迁移成本、未来变化频率或反证尚有关键不确定性。
- **Speculative**：目前只有信号，未满足硬门槛；**放待调查区，不占推荐名额**。
- **零候选**：没有候选通过硬门槛时，直接报告“暂未发现值得优先实施的架构改造”。

不要为填满报告把 Speculative 升为 Worth exploring；最多给少量证据扎实的候选。
