# 实施

实施用户在 spec 或 ticket（或对话共识）中描述的工作。你是**实现期的编排者**：自己不直接写代码，而是委托 coder 施工，走质量门（cleaner agent + reinforcer agent），最后收口提交。

**开始时声明**："我将使用 implement 技能来实施这项工作。"

## 流程

### 步骤 1：审阅输入

如有 spec 文件（backend-spec.md / frontend-spec.md / spec.md）：
1. 读取并批判性审阅——找出任何疑问或顾虑，重点看防误改清单与验收标准是否清晰
2. 如有顾虑：在开始之前向用户提出
3. 如无顾虑：有任务清单就创建 TaskCreate，没有就直接进入步骤 2

没有文件时（ticket 或对话共识）：先复述你理解的目标与边界确认，再进入步骤 2。

### 步骤 2：委托 coder 编码

- 调用 **coder** agent 实施，把 spec（或对话共识）作为输入
- coder 会：读相关代码 → 编码 → 自跑单测/类型检查 → 跑 /code-review 自检修问题 → 交付
- 有任务清单时逐任务委托：标记 in_progress → coder 完成该任务 → 标记 completed
- coder 严格遵守 spec 的防误改清单，不碰清单外的高危区域

**并行委派（前后端都改时）：**

- 前后端能通过 API 契约解耦时，派后端 coder + 前端 coder **并行**执行；否则先派一端定契约，再派另一端
- **一个 coder 只做一端**，互不越界
- 并行 = 同一条消息发多个 Agent 工具调用；每个 prompt 自包含并明确"只做本端"

### 步骤 3：质量门（cleaner + reinforcer 必走）

编码完成后，implement 编排流程**必须**依次跑质量门。它们可单独调用,但在 implement 流程内不是可选项。这两道门都是**单端就能跑**的，不依赖另一端，契合前后端分开实现的工作方式。

**涉及后端 Java 改动时，cleaner 和 reinforcer 强制执行：**

| 质量门 | 形态 | 强制性 | 作用 | 处理 |
|-------|------|:------:|------|------|
| **cleaner** | agent | **必走** | CRAP 复杂度体检，找烂函数 | 只报告不改码 → 有超阈值项则回步骤 2 派 coder 修 |
| **reinforcer** | agent | **必走** | 突变测试，验证测试是否真有效（只跑本次改动包） | 只报告不改码 → 有存活突变体则回步骤 2 派 coder 补断言 |

**执行规则：**
- cleaner / reinforcer **只报告不改码**，implement 拿到报告后回步骤 2 派 coder 修复，修完重跑该门确认通过
- 两者依赖后端 `mvn test`（jacoco/pitest），**纯前端改动时无 Java 目标可跑**，则跳过，改由 coder 的类型检查 + code-review 兜底
- 顺序不强制，但两道门都必须过；跑不过或报告的问题未消化，不得进入步骤 4
- **端到端行为验收（qa / Gherkin）不在此处**：它需要前后端都就绪才能跑，属独立的集成验收阶段，不绑单端 implement（见下）

### 步骤 4：完成开发

所有工作完成并验证通过后：
- 使用 /git-commit（项目 pre-commit hook 强制，不可直接 git commit）
- Merge/push 等操作交由用户自行处理

## 何时停下求助

**立即停止执行的情况**：
- 遇到阻塞
- 输入存在严重缺口，无法开始
- 不理解某条指令
- 验证反复失败

**宁可问清楚，不要猜。**

## 何时回到前面的步骤

**回到步骤 1 重新审阅的情况**：
- 用户根据你的反馈更新了 spec
- 根本方案需要重新思考

**不要硬闯阻塞**——停下来问。

## 牢记

- 先批判性审阅输入
- 编码委托 coder，自己做编排
- 前后端都改且可解耦时，并行派后端 coder + 前端 coder，一个 coder 只做一端
- 严格遵循 spec 的目标与防误改清单
- 质量门:后端改动时 cleaner + reinforcer **必走**(单端可跑);报告类 agent 的问题回到 coder 修复,不过门不提交
- 端到端验收(qa/Gherkin)不在 implement——它需前后端都就绪,属独立集成阶段
- 遇到阻塞就停，不要猜
- **绝不在未获得用户明确同意的情况下在 main/master 分支上开始实施**
