# 调研与调查工作流

## 目标

将一个问题转化为可验证、可复核的调查结果：

```text
定义问题 → 限定范围 → 收集证据 → 交叉验证
→ 区分事实与推断 → 评估置信度 → 输出结果/落盘报告
```

如果任务适合委派，主 Agent 应使用 `researcher` 子 agent 执行调查，自己只负责传递问题、接收结果和决定后续行动。

## 何时使用

- 技术、库、框架、协议和版本行为研究
- 官方文档或源码调查
- 代码库结构、调用链和实现方式调查
- 日志和异常行为排查
- 配置、依赖和构建问题调查
- 用户要求查询数据库或外部系统状态
- 需要为架构设计或实施方案准备事实依据

## 调查前

先明确：

- 要回答的具体问题
- 调查范围
- 代码版本、分支或时间范围
- 环境和系统边界
- 期望的交付形式

问题模糊时，先拆成可验证的问题列表，不要直接开始泛搜。

## 证据优先级

按可靠性优先使用：

1. 当前代码和配置
2. 当前测试、构建输出和原始日志
3. 官方文档、官方源码和版本说明
4. 项目历史、提交记录和变更记录
5. 第三方文章、问答和经验推断

关键结论尽量使用两类独立证据交叉验证。

## Researcher 委派

复杂或独立调查优先委派 `researcher`：

```text
研究任务：<问题>
范围：<目录/版本/时间>
必须回答：
1. <问题 1>
2. <问题 2>
交付：结论、证据、置信度、未确认项、建议。
如果研究内容较长，写入 docs/research/YYYY-MM-DD-主题.md。
```

适合委派给 researcher 的任务：

- 需要阅读大量代码或文档
- 需要调查日志时间线
- 需要比较多个技术方案
- 需要把结果形成长期文档
- 不希望调查过程污染主 Agent 上下文

简单问题可以由主 Agent 直接调查，不必为了使用子 agent 而委派。

## 结果要求

研究结果必须区分：

### 事实

已经直接观察到的内容，带文件路径、日志位置、时间或来源。

### 推断

根据事实得出的解释，必须说明推理链。

### 未确认项

当前权限、工具或证据不足以确认的部分。

### 置信度

使用高 / 中 / 低，并说明依据。

不要把：

- “可能”写成“确定”
- “没有查到”写成“不存在”
- “工具不可用”写成“系统没有数据”

## 长报告落盘

研究内容较多，或用户明确要求保存时，写入：

```text
docs/research/YYYY-MM-DD-主题.md
```

推荐报告结构：

```markdown
# 研究报告：<主题>

- 日期：
- 研究范围：
- 研究状态：draft / final

## 摘要

## 问题定义

## 研究方法

## 事实与证据

## 分析

## 结论

## 置信度

## 未确认项

## 建议

## 参考来源
```

落盘后必须在对话中报告文件路径，不要只说“已保存”。

## 异常调查

异常调查建议按时间线进行：

1. 复述现象和影响范围
2. 确定发生时间、版本和环境
3. 查看相关日志和错误堆栈
4. 检查最近提交和配置变化
5. 追踪调用链和依赖关系
6. 列出已排除的可能性
7. 输出根因假设与证据强度
8. 给出下一步验证，而不是直接跳到修复

如果需要数据库或外部系统查询：

- 先确认当前确实有访问能力
- 默认只执行只读查询
- 记录查询时间、条件和范围
- 无法访问时明确报告限制
- 不要假装查过数据库或日志平台

## 边界

本技能负责调查和编排，不负责擅自修改业务代码、不负责替用户做最终产品决策。实施阶段交给 `implementation-workflow` 和 `implementer`。
