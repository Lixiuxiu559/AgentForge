# 系统化调试

## 概述

随机尝试修复浪费时间、引入新 bug。快速补丁掩盖深层问题。

**核心原则**：永远先找根因，再尝试修复。修症状 = 失败。

**铁律**：
```
未完成根因调查之前，不得提出任何修复方案。
```

## 适用场景

任何技术问题：
- 测试失败
- 生产环境 bug
- 异常行为
- 性能问题
- 构建失败
- 集成问题

**尤其在这些时候必须用**：
- 时间紧迫（紧急情况最容易让人想猜）
- "改一下就行"看起来很明显
- 已经试了好几次修复
- 上一个修复没生效
- 你还没完全理解问题

## Phase 0：多问题并行拆解

**当你面对 2 个以上的 bug 或测试失败时，先判断能否并行处理。**

### 判断标准

```
多个问题？
  │
  ├── 否 → 直接进入 Phase 1
  │
  └── 是 → 它们独立吗？
              │
              ├── 否（改同一个文件 / 共享状态 / 可能互相影响）→ 串行处理，进入 Phase 1
              │
              └── 是（不同文件、不同子系统、不同根因）→ 并行派发
```

**独立**意味着：
- 改不同的文件
- 不共享状态
- 修一个不会影响另一个
- 每个问题可以独立理解，不需要另一个的上下文

**不独立**意味着：
- 改同一个文件
- 可能同一个根因
- 修一个可能导致另一个也变
- 需要全局理解

### 并行派发

确定独立后，**同时派发多个子代理**，每个负责一个问题域：

```
子代理 1 → 修 file-a.test.ts 的 3 个失败（时序问题）
子代理 2 → 修 file-b.test.ts 的 2 个失败（事件结构 bug）  ⎤ 同时跑
子代理 3 → 修 file-c.test.ts 的 1 个失败（异步没等够）    ⎦
```

**每个子代理必须**：
- 拿到**明确范围**：一个文件或一个子系统
- 拿到**清晰目标**：让这些测试通过
- 拿到**约束条件**：不要改其他代码
- 拿到**期望输出**：根因 + 改了什么

**子代理 prompt 模板**：
```markdown
修 src/xxx/xxx.test.ts 中的 N 个失败测试：

1. "测试名称 1" — 具体错误
2. "测试名称 2" — 具体错误

你的任务：
1. 读测试文件，理解每个测试在验证什么
2. 按系统化调试流程找到根因（Phase 1→2→3）
3. 修复根因（Phase 4），不要修症状
4. 禁止只加 timeout 来绕过问题
5. 不要改生产代码，只修测试

返回：根因是什么 + 改了什么
```

### 收尾集成

所有子代理回来后：
1. 逐个读摘要，理解每个改了什么
2. 检查是否有冲突（改到了同一处代码？）
3. 跑一遍全量测试确认无回归
4. 如果有冲突 → 手动解决后再跑全量

**关键约束**：
- **不要派发探索性任务**：你得先知道问题是什么，才能拆出去。不知道就去 Phase 1
- **不要接受"差不多"**：子代理返回的结果要检查，不能盲信
- **不要跳过全量测试**：并行修改可能产生意外交互

## Phase 1：根因调查

**在尝试任何修复之前，必须完成以下步骤**：

### 1. 仔细读错误信息
- 不要跳过任何 error 或 warning
- 完整读完堆栈跟踪
- 记下文件名、行号、错误码

### 2. 稳定复现
- 能稳定触发吗？
- 精确的复现步骤是什么？
- 每次都发生还是偶发？
- 无法复现 → 收集更多数据，不要猜

### 3. 检查最近的变更
- 什么改了可能导致这个问题？
- `git diff`、最近提交
- 新的依赖、配置变更
- 环境差异

### 4. 在多层系统中收集证据

当系统有多层（CI → build → signing, API → service → database）：

**在提出修复之前，加诊断 instrumentation**：
```
对每一层边界：
  - 记录进入该层的数据
  - 记录离开该层的数据
  - 验证环境/配置是否正确传播
  - 检查每一层的状态

运行一次收集证据，找到断裂点
然后聚焦调查那一层
```

### 5. 追踪数据流

当错误在调用栈深处时，参考 `root-cause-tracing.md`（本目录）。

**快速版**：
- 坏的值从哪里来的？
- 谁用坏的值调用了这里？
- 一直往上追，找到源头
- **在源头修，不要在症状处修**

## Phase 1.5：硬 bug 分支 —— 构建反馈回路

**触发条件**：Phase 1 第 2 步卡住——无法稳定复现（偶发 bug）、性能回归、或任何"盯代码看不出原因"的硬 bug。

**这就是硬 bug 的整个方法论。** 其余一切都是机械的。如果你对 bug 有一条**紧凑的**通过/失败信号——一条会在*这个* bug 上变红的信号——你就能找到原因；二分、假设检验、插桩都只是消费它。如果你没有，盯多久代码都救不了你。

在这里投入不成比例的精力。**要激进。要有创造力。拒绝放弃。**

### 构建方式——大致按此顺序尝试

1. **失败的测试**，在能触及 bug 的任意 seam 上——单元、集成、e2e。
2. **Curl / HTTP 脚本**，对着运行中的 dev 服务。
3. **CLI 调用**，带 fixture 输入，diff stdout 与已知正确的快照。
4. **无头浏览器脚本**（Playwright / Puppeteer）——驱动 UI，断言 DOM/控制台/网络。
5. **回放捕获的 trace。** 把真实的网络请求 / 载荷 / 事件日志存到磁盘；在隔离状态下回放它走一遍代码路径。
6. **一次性 harness。** 拉起系统的最小子集（一个服务、mock 依赖），用单次函数调用练习 bug 代码路径。
7. **属性 / 模糊循环。** 如果 bug 是"有时输出错误"，跑 1000 个随机输入找失败模式。
8. **二分 harness。** 如果 bug 出现在两个已知状态之间（commit、数据集、版本），自动化"在状态 X 启动、检查、重复"，这样你可以 `git bisect run` 它。
9. **差分循环。** 把同一输入跑过旧版本对新版本（或两种配置），diff 输出。
10. **HITL bash 脚本。** 最后手段。如果必须有人点击，用 `scripts/hitl-loop.template.sh` 驱动*他们*，让循环仍然有结构。捕获的输出回流给你。

构建出正确的反馈回路，bug 就修好了 90%。

### 收紧循环

把循环当作一个产品。一旦你有*一条*循环，**收紧**它：

- 能更快吗？（缓存 setup、跳过无关初始化、收窄测试范围。）
- 能让信号更锐利吗？（断言具体症状，而不是"没崩"。）
- 能更确定吗？（固定时间、种子 RNG、隔离文件系统、冻结网络。）

一条 30 秒的 flaky 循环几乎不比没有循环强；一条 2 秒的确定性循环是紧凑的——调试超能力。

### 非确定性 bug

目标不是干净复现，而是**更高的复现率**。把触发器循环 100 次，并行化，加压力，收窄时间窗口，注入 sleep。50% 的 flaky bug 可调试；1% 不可——持续提高复现率直到可调试。

### 当你确实建不出循环时

停下来，明确说出来。列出你试过什么。向用户要：(a) 能复现它的环境访问权，(b) 捕获的制品（HAR 文件、日志转储、core dump、带时间戳的录屏），或 (c) 添加临时生产插桩的许可。**不要**在没有循环的情况下继续假设。

### 完成标准——一条紧凑且能变红的循环

Phase 1.5 完成的条件是循环**紧凑**且**能变红**：你能说出**一条命令**——一个脚本路径、一次测试调用、一条 curl——你**至少已经跑过一次**（粘贴调用和它的输出），并且它：

- [ ] **能变红**——它驱动真实的 bug 代码路径并断言**用户的确切症状**，所以它能在这个 bug 上变红、修复后变绿。不是"运行不报错"——它必须能*抓住这个具体的 bug*。
- [ ] **确定性**——每次运行同样的判定（flaky bug：按上文，一个固定的、高的复现率）。
- [ ] **快**——秒级，不是分钟级。
- [ ] **Agent 可运行**——你能无人值守运行它；人只在 `scripts/hitl-loop.template.sh` 时介入。

如果你发现自己在写理论之前先读代码，**停下——直接跳到假设正是这个分支要防止的失败。** 没有能变红的命令，就没有 Phase 2。

## Phase 2：复现 + 最小化 + 模式分析

### 复现确认

运行循环（或按复现步骤操作）。看它变红——bug 出现了。

确认：

- [ ] 循环产生**用户**描述的失败模式——不是恰好就在附近的另一个失败。错误的 bug = 错误的修复。
- [ ] 失败跨多次运行可复现（或对非确定性 bug，以足够高的比率可复现以进行调试）。
- [ ] 你捕获了确切症状（错误信息、错误输出、慢的时机），让后面的阶段能验证修复确实解决了它。

### 最小化（硬 bug 时必做）

把复现缩小到**仍然变红的最小场景**。**一次一个地**砍输入、调用方、配置、数据和步骤，每砍一刀重跑循环——只保留对失败承重的东西。

为什么值得：最小复现缩小 Phase 3 的假设空间（剩下可怀疑的移动部件更少），并成为 Phase 5 的干净回归测试。

当**每个剩余元素都承重**时完成——移除任何一个都会让循环变绿。

### 模式分析（常规 bug 时必做）

**找到模式之后再修**：

1. **找能跑通的参照**
   - 在同一个代码库里找类似的能跑通的代码
   - 什么能跑、跟坏的有什么相似？

2. **对比参照物**
   - 如果要实现一个模式，**完整读完**参照实现
   - 不要略读——逐行读
   - 完全理解模式再应用

3. **识别差异**
   - 能跑的和不能跑的之间有什么不同？
   - 列出每一个差异，不管多小
   - 不要假设"那个应该不影响"

4. **理解依赖**
   - 这个组件还依赖什么？
   - 需要什么配置、环境变量？
   - 做了什么假设？

## Phase 3：假设与验证

**科学方法，防止锚定第一个貌似合理的想法**：

1. **提出 3–5 个排序的假设**
   - 在测试任何一个之前，先生成全部假设并排序。单假设生成会锚定第一个想法
   - 每个假设必须是**可证伪的**：陈述它做出的预测
   - 格式："如果 <X> 是原因，那么 <改 Y> 会让 bug 消失 / <改 Z> 会让它更糟。"
   - 陈述不出预测的假设是一种感觉——丢弃或锐化它
   - **把排序列表展示给用户再测试**。他们常有领域知识能瞬间重排（"我们刚部署了 #3 的改动"）。不要阻塞——用户不在时按你的排序继续

2. **最小化测试**
   - 用**最小**的改动验证假设
   - 一次只改一个变量
   - 不要同时试多个修复

3. **验证后再继续**
   - 生效了？→ Phase 4
   - 没生效？→ 提出新假设
   - **不要在失败的修复上叠另一个修复**

4. **当你不知道时**
   - 说"我不理解 X"
   - 不要假装知道
   - 去问、去查

---

## Phase 4：插桩与验证

每个探针必须映射到 Phase 3 的一个具体预测。**一次只改一个变量。**

工具偏好：

1. **调试器 / REPL 检查**，如果环境支持。一个断点胜过十条日志。
2. **定向日志**，打在区分假设的边界上。
3. 绝不"记录一切然后 grep"。

**给每条调试日志打唯一前缀**，例如 `[DEBUG-a4f2]`。收尾清理就是一次 grep。未打标签的日志存活；打了标签的日志死亡。

**性能分支。** 对性能回归，日志通常是错的。改为：建立基线测量（计时 harness、profiler、查询计划），然后二分。先测量，后修复。

---

## Phase 5：实施修复

**修根因，不修症状**：

1. **先写失败的测试用例**
   - 最简单的复现
   - 修复之前必须有一个失败的测试，确认它能复现 bug
   - **但只在有正确的 seam 时才写**：测试能练习**真实 bug 模式**、如同它在调用点发生的地方。如果唯一可用的 seam 太浅（bug 需要多个调用方时的单调用方测试、无法复现触发链的单元测试），那里的回归测试给的是虚假信心
   - **如果不存在正确的 seam，这本身就是发现。** 记下来——代码库架构在阻止这个 bug 被锁定，Phase 6 处理

2. **实施单一修复**
   - 解决已识别的根因
   - **一次只改一个**
   - 禁止"趁便"改别的
   - 禁止打包重构

3. **验证修复**
   - 测试通过了？
   - 没有引入新的失败？
   - 问题真的解决了？
   - 对原始（未最小化）场景重跑 Phase 1.5 的反馈回路

4. **如果修复没生效**
   - **停**
   - 数一数：你试了几次修复了？
   - < 3 次：回到 Phase 1，用新信息重新分析
   - **≥ 3 次：停下来质疑架构（见下方）**
   - 不要尝试第 4 次修复

5. **3 次以上修复失败 → 质疑架构**

   以下模式说明架构有问题：
   - 每次修一个地方，另一个地方又冒出问题
   - 修复需要"大规模重构"
   - 每次修复都在别处产生新症状

   **停下来质疑根本**：
   - 这个模式本身对吗？
   - 我们是不是"惯性坚持"？
   - 是不是该重构架构，而不是继续修症状？

   **在尝试更多修复之前，和用户讨论**

---

## Phase 6：清理 + 复盘

声明完成之前必须做：

- [ ] 原始复现不再复现（重跑 Phase 1/1.5 循环）
- [ ] 回归测试通过（或 seam 缺失已被记录）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（grep 前缀）
- [ ] 一次性原型已删除（或移到清楚标记的调试位置）
- [ ] 被证实正确的假设写进 commit / PR message——让下一个调试者学到

**然后问：什么本可以预防这个 bug？** 如果答案涉及架构变更（没有好的测试 seam、纠缠的调用方、隐藏耦合），带着具体细节移交给 `/improve-codebase-architecture` 技能。在修复落地**之后**再提建议，不要在之前——你现在掌握的信息比开始时多。

---

## 红旗信号

如果你发现自己在想这些话，**立即停，回到 Phase 1**：

- "先快速修一下，回头再调查"
- "试试改 X 看看行不行"
- "一次改多个地方，跑测试"
- "不用写测试，我手动验证"
- "应该就是 X，我来改"
- "不太确定但这个可能有用"
- "再试一次"（已经试了 2 次以上）
- 每个修复都在不同的地方暴露新问题
- 还没追踪数据流就开始提方案

## 常见借口

| 借口 | 现实 |
|------|------|
| "问题很简单，不需要流程" | 简单问题也有根因。流程对简单 bug 也很快 |
| "紧急情况，没时间走流程" | 系统化调试比猜测-改-试快得多 |
| "先试试这个，再调查" | 第一次修复就定了基调。一开始就做对 |
| "确认修复有效再写测试" | 没有测试的修复不持久。先写测试证明它 |
| "一次改多个更快" | 无法隔离哪个生效了。还会引入新 bug |
| "参照太长了，我改一下就行" | 部分理解 = 保证出 bug。完整读完 |
| "我看见问题了，直接改" | 看见症状 ≠ 理解根因 |

## 速查表

| 阶段 | 关键动作 | 成功标准 |
|------|---------|---------|
| **0. 拆解** | 判断独立性、并行派发、集成验证 | 独立问题并行处理，或不独立则串行 |
| **1. 根因** | 读错误、复现、查变更、收集证据 | 理解 WHAT 和 WHY |
| **1.5 硬 bug 分支** | 构建反馈回路、收紧、提高复现率 | 一条紧凑且能变红的命令 |
| **2. 复现** | 确认症状、最小化 / 找参照对比差异 | 最小承重复现 / 识别出差异点 |
| **3. 假设** | 3-5 个可证伪排序假设、最小测试 | 证实或推翻假设 |
| **4. 插桩** | 调试器优先、DEBUG 前缀、一次一变量 | 每个探针对应一个预测 |
| **5. 修复** | 写测试、修根因、验证 | bug 解决、测试通过 |
| **6. 复盘** | 清理插桩、记录根因、预防性问题 | 无残留、下一个调试者受益 |
