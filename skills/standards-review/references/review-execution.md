# 两轴执行细节

## 为什么建议分开执行

两轴关心不同的东西：

- Standards 轴要读**规范文档 + diff**
- Spec 轴要读**需求文档 + diff**

如果放在同一个上下文里跑，Spec 轴的"这个需求没实现"会影响 Standards 轴的判断（例如把"为了满足需求而不得不违反规范"报成单纯的违规），反之亦然。

理想做法是**各由一个独立的 subagent 执行，彼此看不到对方的结论**，最后由本技能汇总。

## 但不要假装已经派发

**关键约束**：只有当前环境确实提供了可用的 subagent 派发通道时才并行。

如果不可用，就**自己串行跑完两轴**，并在报告里如实说明是串行完成的。

**绝对不要**：
- 声称派发了 subagent 但实际是自己跑的
- 为了"看起来正规"而虚构执行方式

报告里的「执行方式」一栏必须如实反映实际情况。

## 派发时给什么

如果确实要派发，每个 subagent 的 brief 必须**自包含**——它看不到主对话，也读不到本技能的其它 reference。

**Standards subagent 的 brief 要包含**：

1. 基线 commit 与 diff 命令
2. 找到的规范文件清单
3. **12 条 smell 基线的全文**（它没有其它途径读到）
4. 任务：逐文件/逐 hunk 报告硬性违规（引规范文件 + 规则）与 smell（引名称 + 代码片段）
5. 区分硬性违规与判断项
6. 字数上限

**Spec subagent 的 brief 要包含**：

1. 基线 commit 与 diff 命令
2. spec 的路径或内容
3. 任务：报告（a）spec 要求但缺失/部分实现的；（b）diff 里 spec 没要求的行为；（c）看起来实现了但实现可疑的
4. 每条引 spec 原句
5. 字数上限

**字数上限是刻意的**：subagent 的默认失败模式是啰嗦。写死上限（例如 400 字）能显著提升报告可用性。

## 串行执行时的顺序

先 Standards 后 Spec。原因：规范违规通常是局部的、可以直接定位的；需求缺口需要先理解整体意图，放在后面做能带着对代码的完整认识判断。

两轴之间不要互相参考结论——串行执行时也要刻意保持这一点，写完一轴再开始另一轴。

## 找不到 spec 时

跳过 Spec 轴，**不要**：

- 从代码反推需求
- 用 commit message 当 spec（除非它确实描述了需求）
- 发明验收标准

报告里写明"无 spec 可用"，并明确说明**本次只完成了 Standards 轴**——让调用方知道评审是不完整的。

## 与其他能力的分工

本技能**不做**以下检查，遇到时不要顺手做：

| 检查 | 归属 |
|---|---|
| 逻辑错误、边界情况、安全漏洞、性能 | Claude Code 内置 `/code-review` |
| 复杂度风险、CRAP | `complexity-audit` 技能 |
| 测试是否真正验证逻辑 | `mutation-testing` 技能 |
| 实施编排与集成验证 | `implementation-workflow` 技能 |

各管一段，不重叠。混着做会让报告失去聚焦，也会让作者搞不清该找谁修。
