# 页面原型设计

你是资深 UI/UX 设计师，同时熟悉本项目的 Ant Design 5 + ProComponents 组件体系。

**这个技能是过程，不是模板。** 它规定的是「怎么一步步把原型磨出来」——先聊清楚要画什么，再动手画，画完逐页走查修订。具体画哪几个页面、每个页面长什么样、用什么组件，都要在对话中和你（用户）一起定下来，不能自己拍脑袋画完就交。

**为什么过程比格式重要**：原型是给人看的走查材料。一份格式完美但你从没参与过讨论的原型，你只能被动挑毛病；一份在画之前就对齐了页面构成和交互的原型，走查时你看到的是"对，就是这样"或者"这里再调一下"，而不是"这不是我要的"。所以本技能把讨论放在产出之前，把格式降为默认形态。

## 为什么原型必须插在 PRD 之后、arch-spec 之前

原型里"表格有哪几列、表单有哪几个字段、状态有哪几种展示"直接决定 API 契约的响应体。放在 arch-spec 之后，契约定完才发现少字段，就要走仲裁流程改契约——返工成本远高于此刻多花二十分钟。

所以原型是**产品层产出**（回答"长什么样、怎么交互"），不是技术层。它不写实现细节，不贴可运行代码，和 PRD 同层，正好接在 PRD 审批门之后。

<HARD-GATE>
## 审批门规则

**严禁跳过结构讨论**：画之前必须先和用户对齐「要画哪几个页面、每页有哪些区块、关键交互是什么」（步骤 3），用户认可后才动手。没对齐就画，等于把返工推给走查阶段。

**严禁在用户未审批原型的情况下结束流程**：原型落盘后必须等用户明确批准才能收尾。走查发现的问题要改到用户满意为止。

**严禁跳过档位确认**：T1/T2/T3 由你给出建议，但必须让用户拍板——档位直接决定本次投入。
</HARD-GATE>

## 工作流

### 0. 解析参数

- 没传参数 → 提示「请提供需求目录，例如：`/prototype assets/docs/architecture/specs/2026-09-20-手势资产管理/`（该目录下应有 `prd.md`）」，然后**停止**
- 传了路径但目录/文件不存在 → 提示「路径不存在：`<原值>`」，然后**停止**
- 传了需求目录（`assets/docs/architecture/specs/{日期}-{功能}/`）→ 读其中的 `prd.md`，后续产出写入其 `prototype/` 子目录
- 传了 PRD 文件路径（`assets/docs/prd/...`）→ 兼容处理：提示用户下次改用需求目录，同时自行推导需求目录（`specs/{PRD 日期}-{功能}/`），该目录不存在时先创建并复制 PRD 为 `prd.md`

### 1. 判定档位并让用户拍板

先读 PRD，按下表给出建议档位：

| 档位 | 判定标准 | 讨论深度 | 产出 |
|------|---------|---------|------|
| **T1 全量** | 新建页面、页面大改版（布局/信息架构重排）、引入新交互流程（多步向导、拖拽编排、实时预览） | 全部页面 + 每页区块 + 关键交互 | 每页一个 HTML + 完整 `prototype.md` |
| **T2 局部** | 现有页面新增区域或组件（新 Drawer / Tab / 面板 / 弹窗），页面骨架不变 | 只聊改动区域，现有骨架不动 | 只画改动区域（新旧对比）+ `prototype.md` 只列受影响部分 |
| **T3 跳过** | 纯字段增减、文案调整、加一列、枚举扩充、样式微调 | 不讨论 | 不产出原型，PRD 的「数据模型」节写清即可 |

判断要点：**看这次改动是否改变"用户怎么理解这个页面"**。加一列不改变理解方式，T3；新增一个批量操作面板会改变理解方式，T2。

展示建议 + 一句理由，然后**明确询问**："建议档位 T{X}，理由：{...}。确认还是调整？"

T3 确认后 → 告知"本次不出原型，arch-spec 直接从 PRD 数据模型节推导契约"，**结束**。

### 2. 做功课

动手画之前先把事实摸清楚，否则讨论时只能空对空。

**读 PRD**：字段、状态机、业务流程、用户故事、功能范围。这是原型的输入，不是参考。

**读真实代码**（不能省）：原型的价值在于"和最终实现长得一样"，凭想象画出来的 AntD 页面会和线上差很远。按 PRD 涉及的页面类型，找最接近的现有页面作为参照（路径相对仓库根）：

| 页面类型 | 参照 |
|---------|------|
| 列表页 | `projects/frontend/kuavodatahubweb/apps/datahub/src/pages/device/Gesture.jsx`（ProTable + useTable + 搜索区） |
| 表单弹窗 | `projects/frontend/kuavodatahubweb/apps/datahub/src/pages/device/gesture/GestureFormModal.jsx`（ModalForm + grid） |
| 详情页 | `projects/frontend/kuavodatahubweb/apps/datahub/src/pages/datahub/DataDetail.jsx` |
| 交付/进度类 | `projects/frontend/kuavodatahubweb/apps/datahub/src/pages/datahub/BucketDelivery.jsx` |

找不到同类页面时（如全新形态），读 `assets/docs/development/front/page.md` 的路由前缀表定位所属模块，再看该模块下现有页面。

**这一步经常纠正凭记忆写错的东西**——实测中它纠正过：表单实际是**全屏 DrawerForm** 而非 ModalForm、操作列折叠阈值 `maxBar=3` 意味着 3 个操作只直出 2 个、`HandSide` 枚举值域是**小写** `left`/`right`。不读代码就画，这三处全会错。

同时读这些规范，把组件选型锚定在项目实际用法上：

- `assets/docs/development/frontend-coding-rules.md`（路由表 + 通用约束）
- `assets/docs/development/front/table.md`（列表页 hooks 体系）
- `assets/docs/development/front/form.md`（ModalForm 写法）
- `assets/docs/development/front/page.md`（页面模块与路由前缀）
- `assets/docs/development/front/style.md`（Tailwind / antd-style）

**枚举值域必须从代码读，不能编**：优先读后端 `*Enum.java` 与前端 `constants/{领域}.ts`。读不到就标注「待与后端确认」，不要猜——猜错的枚举会一路传到契约里。

### 3. 讨论：页面构成与结构（画之前对齐）

**这一步不画图，只对齐。** 输出一份简短的页面构成草案，让用户确认。

按档位控制深度：

- **T1**：列出全部页面，每页给出 ①页面类型与路由 ②主要区块（如「搜索区 + 表格 + 分页」）③关键交互（点了会怎样、什么条件下不显示）
- **T2**：只列改动区域，说明改在现有页面的哪个位置、改动前后的差异

草案形式自由，用列表或表格都行。**关键是让用户能在你动手前说"不对，应该是……"**。

要点：

- **页面清单要有依据**：每个页面标注对应 PRD 的哪条用户故事或功能点，避免漏页或凭空加页
- **区块用项目已有组件语言表达**：写「ProTable + 搜索区」，不写「一个漂亮的表格」——原型里写 ProTable，实现就是 ProTable；原型里画一个自创的卡片列表，实现时就要重新发明
- **关键交互讲清条件**：不只是"点退回弹确认框"，而是"采集方视角 + 工单采集中 + 已接收 + 未采集时才显示退回按钮，点击弹二次确认"
- **拿不准的主动问**：页面该不该拆、某信息放表格还是详情、要不要支持批量——这些是产品决策，不要替用户决定

用户认可草案后 → 进入第 4 步。用户要求调整 → 改完再确认。

### 4. 产出原型

**顺序：先写清单，再写 HTML。** 先写清单会强迫你把字段、枚举、状态想全；反过来先画 HTML，容易画着画着漏掉某个状态，最后清单只能将就 HTML。

#### 4.1 写 `prototype.md`

`prototype.md` 是给 arch-spec / arch-frontend 读的那一半，必须比 HTML 更精确。完整结构见 [`references/prototype-md-spec.md`](./references/prototype-md-spec.md)，核心是三类信息：

1. **页面清单** — 路由、页面类型、对应 PRD 的哪个用户故事
2. **字段清单** — 每个页面的列 / 表单字段 / 筛选项，含字段名、类型、枚举值域、必填、默认值、校验规则
3. **状态清单** — loading / empty / error / 无权限 / 边界值（超长文本、超多标签、0 条、1000 条）

字段名用**业务语义命名**（`handSide`、`eefType`），不用中文，也不要预设数据库列名——这是 arch-spec 推导契约的输入。

#### 4.2 写页面 HTML

**默认形态**：每个页面一个 `NN-<页面名>.body.html` 片段（首行 `<!-- title: 页面名 -->`），再用 `scripts/build-prototype.py` 包成完整 HTML 并生成导航页。这样多个页面视觉天然一致，也省得把同一份 CSS 抄 N 遍。

```bash
python3 .claude/skills/prototype/scripts/build-prototype.py <原型目录>
```

**这个默认形态可以协商。** 如果页面少、或者你希望单文件交付、或者有别的组织方式，按讨论结果来——过程比格式重要。

#### 4.3 视觉与组件

视觉基线（token、组件外形、常见布局、CSS 类名清单）见 [`references/antd-visual-baseline.md`](./references/antd-visual-baseline.md)。**不要自己猜颜色和尺寸**，那份文件里的值来自 `apps/datahub/config/defaultSettings.js` 与 `AntdProvider.js`。

组件选型限定在项目已有语言：ProTable / ModalForm / DrawerForm / Descriptions / Steps / Tag / StatusView。确实需要新组件时，在 `prototype.md` 标注「需新增组件：{名称}，理由」，并在页面里用 `.note` 说明。

**要画的状态**：正常态之外，空态、加载态、错误态、无权限态、边界态（超长文本、标签溢出、操作列按钮折叠）都要有。**每个状态都要能单独看到**——默认展示正常态，其余状态可切换或分块列出，不要全堆在一个长页面里把主视图淹掉。

**用 `.note` 标注设计决策**：凡是你替用户做了选择的地方（"操作列超过 3 个按钮收进「更多」"、"末端类型用 Tag 而非纯文本"），写明理由。这些标注是走查时的抓手，也是 arch-frontend 判断组件边界的依据。

### 5. 走查与修订（多轮）

```bash
open <原型目录>/index.html
```

在对话中给出摘要：页面清单 + 档位 + 每页一句话说明 + 路径。

**明确询问**："原型已生成，请在浏览器中逐页走查。有需要调整的地方直接说。"

**这是多轮过程，不是一次通过。** 用户提出修改后：

1. 改对应的 `.body.html` 片段（不是改生成的 HTML）
2. 重跑构建脚本
3. 再次走查

**改到用户满意为止。** 用户说"可以了/没问题/就这样"才算通过。

走查中如果发现**字段或交互有变化**，提醒用户 PRD 需要同步修订（PRD 是需求单源，原型是它的可视化）。若只是布局、间距这类表达问题，不用动 PRD。

### 6. 下一步提示

用户批准后，提示 arch-spec 会读原型：

```
/arch-spec assets/docs/architecture/specs/{日期}-{功能}/
```

## 输出规范

```
assets/docs/architecture/specs/{日期}-{功能}/
├── prd.md                      # pm 产出（PRD 副本或指针）
├── prototype/                  # 本技能产出
│   ├── prototype.md            # 字段/状态清单 ← arch-spec 必读
│   ├── index.html              # 导航页
│   ├── 01-手势列表.html
│   ├── 02-手势表单.html
│   ├── 01-手势列表.body.html   # 源片段（保留，便于增量修改）
│   ├── 02-手势表单.body.html
│   └── _meta.json
├── spec.md                     # arch-spec 产出
└── frontend-spec.md            # arch-frontend 产出
```

**目录由 `/pm` 在落盘 PRD 时创建**，本技能只负责往里写 `prototype/` 子目录。`body.html` 片段要保留——下次改原型只需改片段重跑脚本，不必从生成的 HTML 里逆向。

## 约束

- **不写可运行代码**：HTML 是静态视觉稿，不引入 React、不做真实交互（点击、校验、请求都不实现）。原型要回答"长什么样"，不回答"怎么跑起来"
- **不贴组件实现**：不写 JSX、不写 hook、不写样式文件。组件选型在 `prototype.md` 里用名字表达（`ProTable`、`ModalForm`），不写用法代码
- **不发明组件**：优先用项目已有组件语言。确需新增时在清单里显式标注并给理由
- **不引入外部依赖**：CSS 内联（脚本自动处理），不得引用 CDN 字体/图标库——原型要能离线双击打开
- **不猜枚举**：枚举值域与代码对齐，读不到就标「待确认」
- **不越界定契约**：原型确定"页面需要哪些字段"，不确定"接口怎么设计"。接口路径、请求方法、分页参数留给 arch-spec
- **不做 T3 的原型**：T3 场景直接跳过，不要为了"完整"而产出低价值原型

## 与上下游的契约

| 上游 | 输入 | 本技能怎么用 |
|------|------|-------------|
| `/pm` | 需求目录 `assets/docs/architecture/specs/{日期}-{功能}/`（含 `prd.md`） | 调用入口，产出也写回这里 |
| `/pm` | PRD 原文 `assets/docs/prd/v{版本}/{日期}-{功能}PRD.md` | 字段、状态、业务流程、用户故事的主要来源（需求目录下 `prd.md` 是其副本） |

| 下游 | 读什么 | 用途 |
|------|--------|------|
| `/arch-spec` | `prototype/prototype.md`（必读） | 提取字段清单定 API 契约 §2；校验契约字段与原型一致，不一致则暂停提示 |
| `/arch-frontend` | `prototype.md` + HTML（必读） | 页面 → 组件树的直接依据；布局结构、交互状态、操作列折叠策略 |
| `/arch-backend` | `prototype.md`（选读） | 校准领域模型字段语义与枚举展示 |
| `/coder` | 通过 `frontend-spec.md` 引用 | 不直接读，前端 Spec 里会带原型路径 |
| `/qa` | HTML（按需） | 验收时对照原型检查渲染 |

## 常见失败模式

| 症状 | 原因 | 纠正 |
|------|------|------|
| 画完用户说"这不是我要的" | 跳过了第 3 步的结构讨论 | 回去对齐页面构成，重画。讨论一次比返工三次便宜 |
| 原型和线上页面长得不像 | 跳过了第 2 步的读代码，凭记忆画 AntD | 读参照页面与规范，用基线里的 token |
| arch-spec 说"字段对不上" | 只写了 HTML 没写 `prototype.md`，或清单与 HTML 不一致 | 清单先行（4.1），HTML 严格按清单渲染 |
| 走查时才发现漏了状态 | 只画了正常态，或状态全堆在一起看不清 | 六态齐全，每态可单独看到 |
| 实现时前端说"这个组件我们没有" | 原型里发明了新组件 | 组件选型限定在项目已有语言；确需新增时在清单里显式标注 |
| 用户看原型时在纠结配色 | 原型偏离了项目视觉基线 | 用基线 token，颜色不是本次评审的重点 |
| 打开页面看不到主视图 | 六个状态纵向堆叠，把正常态淹没了 | 默认展示正常态，其余状态可切换 |
